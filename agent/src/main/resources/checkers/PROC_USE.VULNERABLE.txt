A credential is compared with a method that is not constant time — `equals` on a password, token or
secret, directly or inside a password encoder whose `matches` is a raw-value equality, returning at
the first differing character — or a token-parse entry point hands back its claims without requiring
a valid signature, so an unsigned or forged token is read as authentic.

PROC_USE is "procedure use", not "process use". This is not command injection, and the absence of
`Runtime.exec` or `ProcessBuilder` proves nothing — a process launched from external data is
reported by a different checker. It is also distinct from the hard-coded-credential checkers, which
flag the literal; this one flags the COMPARISON that consumes it.

THE COMPARISON SHAPE IS ALMOST NEVER OBSERVABLE. An ordinary `String.equals` — directly, or inside
a password encoder whose `matches` is a plain equals of the raw value — is not constant time: it
returns at the first differing character, and earlier still on a length mismatch. Over secrets of a
few dozen characters, behind a web framework, that difference is nanoseconds, below JIT warm-up, GC
and scheduler noise. Any "wrong-at-character-1 beats wrong-at-character-20" assertion is flaky by
construction and a lucky red proves nothing, so `unprovable` is usually the honest state.

One variant of it IS deterministic: where the marker is attributed to a no-op or plaintext password
encoder, the consequence is not a timing channel but storage and verification in the clear, and the
persisted value is the literal secret. Do not settle that one as "cannot be shown". If you settle it
as intentional, settle it on the project's own stated intent — a comment, a suppression, a doc.

THE TOKEN SHAPE REALLY DOES FAIL. A JWT parse entry point that returns claims without requiring a
valid signature accepts a token whose header names `alg: none` and whose signature is empty, and
hands back the forged body; the signature-requiring entry point rejects the same string. Build the
token with the library's own builder rather than hand-rolling base64url, and assert on the claims,
status or view — never on an exception message. The rejection thrown after the fix is normally a
subclass of the library's general JWT exception, so a broad catch already present turns the fix into
a clean rejection; where nothing comparable is caught, the fix turns a forgery into a 500 instead of
a 401 and the catch must widen with it. Parsing a token the same method just built exposes no
defect, only a call shape.

WHAT GOES WRONG HERE.
Opening the marker looking for `exec`. "There is no `Runtime.exec` here" is true of every site and
decides nothing.

Trusting the flagged line. These markers often land on a closing brace or a `return`, with the
comparison a few lines up in the enclosing method; reading only the literal line is how a pass
concludes "no such construct whatsoever". Likewise when the anchor sits inside a long security
configuration method and the identical construct is unflagged in a sibling file: all that is
established is that something in that method is flagged, and the anchor is arbitrary.

Mistaking a neighbouring defect for this one. Probing a credential check can turn up a genuine
NullPointerException; that RED is real and it is a different defect. Nor does an unflagged twin
prove misfiling — identical credential comparisons elsewhere in the same codebase may carry no
marker, and a shape shared by the flagged sites is not the checker's rule.

Breaking what the code is for. A constant-time compare of the same value changes nothing observable
and is safe; hashing the stored secret, or demanding a verified signature, changes what the
surrounding code can still do — read what depends on the current behaviour first.
