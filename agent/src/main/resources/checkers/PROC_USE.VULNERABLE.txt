The checker asserts that a secret is checked by calling a procedure that is not fit to check a secret. Two shapes account for all 19 sites: `String.equals` comparing a credential (a password, a Basic-auth header, a cookie-derived value — including indirectly via `NoOpPasswordEncoder`, whose `matchesNonNull` is literally `raw.toString().equals(encoded)`, which is why both `WebSecurityConfig` files are flagged inside their `filterChain` chain), and jjwt's `Jwts.parser()...parse(token)`, which decodes a token without requiring a valid signature. PROC_USE is "procedure use", not "process use" — this is not command injection, and the absence of `Runtime.exec` proves nothing: the one WebGoat file that really does launch a process, `src/main/java/org/dummy/insecure/framework/VulnerableTaskHolder.java`, carries `FB.COMMAND_INJECTION` at line 69 and no PROC_USE marker at all. It is also distinct from `FB.HARD_CODE_PASSWORD`, which flags the literal (`IDORLogin.java:35` and `:41`) while PROC_USE flags the comparison (`IDORLogin.java:53`).

HOW YOU MAKE IT VISIBLE.
Split by shape; only one of the two can be made visible.

JWT shape — deterministic, and it really does fail. I ran it against WebGoat's own jjwt 0.9.1 on its real classpath: `Jwts.parser().setSigningKey(KEY).parse(t)` ACCEPTED a forged token `base64url({"alg":"none"}) + "." + base64url({"user":"Tom","admin":"true"}) + "."` (no signature) and returned the forged body, while `parseClaimsJws(t)` on the same string threw `UnsupportedJwtException`. So a test builds that three-field, empty-signature string, hands it to the method under test, and asserts on the result: RED = forged claims come back / the vote is accepted / 202-200; GREEN after `parse` -> `parseClaimsJws` = exception or 401. Assert on the claims or the status, never on an exception message.

But in WebGoat the JWT endpoints are where that acceptance is the assignment, and the repository says so itself: `src/it/java/org/owasp/webgoat/integration/JWTLessonIntegrationTest.java:149` and `:195` build exactly this `alg=NONE` token with `admin=true`, POST it, and assert `lessonCompleted` is true. For `JWTVotesEndpoint` (139/164/187, parsers at 141/177/200) and `JWTRefreshEndpoint` (91/121), a test that shows the forgery landing is showing the lesson working, and `parseClaimsJws` would break that existing integration test — settle those as the lesson and cite that test by line. `TokenTest.java:37` and `JWTLessonIntegrationTest.java:77` are different: they parse tokens they built themselves two lines earlier, so there is no defect to expose, only a call shape that would matter in production code.

`String.equals`-on-a-secret shape — you cannot demonstrate this, and the honest settlement is unprovable. The defect is a timing side channel (the compare returns at the first differing character) over passwords of 6 to 45 characters; the difference is nanoseconds, below JIT warm-up, GC and scheduler noise, so any "wrong-at-char-1 is faster than wrong-at-char-20" assertion is flaky by construction and a run that goes red by luck has proved nothing. Say that plainly rather than manufacturing a build.

WHAT GOES WRONG HERE.
The reading that already sank this family: a previous pass settled all 19 as false_positive, each verdict saying some version of "the checker claims a process is launched from externally-controlled data, but there is no `Runtime.exec()` or `ProcessBuilder` here." True of every line, and it decides nothing — command injection is routed to `FB.COMMAND_INJECTION` in this same corpus. Do not open a PROC_USE marker looking for `exec`.

Trusting the line number. Eight of the 19 land on a brace or a return: `UserValidator.java:35` is the closing brace of the class, `JWTVotesEndpoint.java:164` a closing brace, `SimpleMailAssignment.java:52` the `}` of an else, `ResetLinkAssignment.java:77` a `return failed(this)`, `SpoofCookieAssignment.java:78` a `return informationMessage(this)`. The construct is in the enclosing method a few lines up — `.equals` at UserValidator 31, SimpleMail 48, ResetLink 73, SpoofCookie 72. Reading only the literal line is how the previous pass concluded "no process invocation whatsoever."

An NPE mistaken for a proof. `UserValidator.validate()` line 31 calls `userForm.getMatchingPassword().equals(...)`, and `matchingPassword` is only `@NotNull` under bean validation, so invoking the validator directly with the field unset throws NullPointerException. That RED is deterministic and genuine — and it is a different defect. Reporting it as PROC_USE.VULNERABLE is the same mistake as the `;` payload against `Runtime.exec(String)`.

Fixing a lesson. `LogBleedingTask:43` compares against a UUID password the lesson deliberately leaks to the log at lines 30-33; `SqlInjectionLesson6b:34` compares the request parameter to the DB password the student is meant to extract by injection; `SpoofCookieAssignment:72-73` gates the `EncDec` cookie the student must forge. Swapping those for a constant-time compare of the same value is harmless, but hashing the stored secret, or hardening the two JWT endpoints, makes the assignment unsolvable. The four flagged sites outside lesson code — both `WebSecurityConfig` files, `UserValidator`, and the two JWT tests — carry no such constraint.
