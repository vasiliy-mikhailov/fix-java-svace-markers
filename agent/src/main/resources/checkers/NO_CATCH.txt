(?:\bnew\s+[A-Z]\w*|\.[a-z]\w*)\s*\(
A call site from which a raised exception can escape with no handler anywhere between that site and the top of the analyzed call chain. Two neighbours get mistaken for it: "a `try` with `finally` or resources but no `catch` clause" is a different construct, and "an exception swallowed by an empty `catch`" is the opposite complaint — NO_CATCH is that nothing catches. The sibling NO_CATCH.LIBRARY is the same defect with the exception's origin named. Since javac already enforces catch-or-declare, a NO_CATCH on code that compiles is necessarily about an unchecked exception or one raised inside library code, never a missing `throws`.

HOW YOU MAKE IT VISIBLE.
The defect is NOT "the callee throws" — throwing is the callee's documented contract. The observable is that the exception crosses the boundary of the FLAGGED method un-handled. Arrange the throwing precondition from outside, call the enclosing method, and assert that NOTHING ESCAPES. The assertion is assertDoesNotThrow, not assertThrows: a test asserting the throw passes on today's code and fails once a handler is added, which is backwards for a RED meant to go GREEN on the fix.

ARRANGE IT THROUGH A SEAM THE LIBRARY REALLY HONOURS — a resource loader that genuinely consults the thread context class loader, a factory that genuinely reads a system property — confirmed in the library's own bytecode. An invented hook the library never consults produces a GREEN that means nothing.

LOCATE WHERE IN THE STATEMENT THE THROW HAPPENS. Arguments are evaluated before the call that consumes them, so a throw raised while building an argument lands before any of the work that call would have done: an entry point that would otherwise start a server can be probed in milliseconds with nothing bound and nothing written. That cheapness belongs to the throwing path only. Once the fix removes the throw, the same call runs the whole program — so if the corrected path really starts a product, isolate it, override ports and data directories through whatever arguments the entry point forwards, and remember nothing closes what it started: non-daemon threads and lock files outlive the test for the rest of the fork.

AT PROCESS LEVEL THE RED SIGNATURE IS DEFINITIONAL AND THE GREEN IS NOT "EXIT 0". With the precondition arranged, a stderr first line of `Exception in thread "main" <type>: <message>` plus a non-zero exit is printed by the default uncaught-exception handler and by nothing else, which puts the RED on the escape rather than on the library's precondition check. But a program with non-daemon threads never terminates once the throw is gone, so never call waitFor() unbounded and never pair the RED with "afterwards it exits 0". Launch, read the streams under a timeout, assert the process did NOT die from an uncaught exception — a known start-up line appeared and stderr carries no `Exception in thread` — then destroyForcibly in a finally.

FIX SHAPES THAT BREAK THE PAIRING. Catch-and-rethrow leaves the assertDoesNotThrow test RED. Catch-then-System.exit(1) cannot go green in-process at all, since it kills the test JVM, and at process level it flips the signature to a non-zero exit with no `Exception in thread` prefix.

WHEN IT GENUINELY CANNOT BE SHOWN: if the throwing precondition has no seam a test can reach — an unreachable branch, a private path with no injectable input, an exception raised inside a container callback you cannot provoke — say so plainly and settle the marker on it, naming the precondition you could not arrange.

WHAT GOES WRONG HERE.
- Asserting the marker back at itself: asserting the library call throws when invoked directly. That tests the library's own precondition check, behaves identically before and after the fix, and says nothing about a missing handler. The call must go through the flagged method.
- Reading NO_CATCH as "try block without a catch clause", grepping for `try`, finding none and closing the marker as a false positive. That absence is the finding, not its refutation.
- Reading it as a swallowed exception and fixing with `catch (Exception e) {}` or a bare log around the whole method. That trades this defect for the opposite one and leaves the arranged test nothing to observe.
- Declaring it unprovable because the enclosing method "does too much to run in a test". Find where in the chained call the throw occurs first; it is often ahead of everything expensive.
- Line drift between stack trace and marker. A statement spanning several source lines is attributed by the LineNumberTable to the line it began on, so a frame can name a line above the marker while both describe the same statement. Do not retarget the finding because of it.
- Intentionality in both directions. Bootstrap and wiring code is not made deliberate by living in an intentionally flawed application; equally, do not carry a "not deliberate" conclusion across sites — where the crash is the point, or where a handler would hide a failure someone is meant to see, settle on that specific ground.
- Overstating reach. A packaging or classpath precondition is not attacker-controlled input, so "remotely triggerable" does not follow. What does follow is the failure mode: a bare stack trace and a non-zero exit with no indication of what was missing.
- Treating the regex as the finding. It only locates call sites and matches a large fraction of the lines in any Java file; the missing handler is invisible to any per-line pattern, so a match is a candidate to open, never a defect on its own.
