NO_CATCH marks a call site from which a raised exception can escape with no handler anywhere between that site and the top of the analyzed call chain. On StartWebGoat.java:24 the site is `.banner(new ResourceBanner(new ClassPathResource("banner-webwolf.txt")))` inside a `main` that contains no `try` at all — `ResourceBanner`'s constructor runs `Assert.isTrue(resource.exists(), "'resource' must exist")` and throws IllegalArgumentException, which leaves `main` and kills the JVM. Two neighbours get mistaken for it: "a `try` that has `finally`/resources but no `catch` clause" is a different construct (here there is no `try` on or near the line), and "an exception swallowed by an empty `catch`" is the opposite complaint — NO_CATCH is that nothing catches. Note also that javac already enforces catch-or-declare, so a NO_CATCH on code that compiles is necessarily about an unchecked exception or one raised inside library code, never a missing `throws`.

The defect is NOT "the callee throws" — throwing is the callee's documented contract. The observable is that the exception crosses the boundary of the FLAGGED method un-handled. So arrange the throwing precondition from outside, call the enclosing method, and assert on the escape.

WHAT GOES WRONG HERE.
- Asserting the marker back at itself: `assertThrows(IllegalArgumentException.class, () -> new ResourceBanner(new ClassPathResource("nope.txt")))`. That is a test of Spring's `Assert.isTrue`, passes on unmodified and fixed code alike, and says nothing about a missing handler. The call must pass through `StartWebGoat.main` — the flagged frame — or the RED is not about this marker.
- Reading NO_CATCH as "try block without a catch clause", grepping StartWebGoat.java for `try`, finding none, and closing the marker as a false positive. There is no `try` in the file; that absence is the finding, not its refutation.
- Reading it as "swallowed exception" and fixing with `catch (Exception e) {}` or a bare `catch (Exception e) { log.debug(...) }` around the whole of main. That trades this defect for the opposite one and leaves the arranged test with nothing to observe.
- Declaring it unprovable because "main starts two Spring Boot apps, you can't run that in a unit test". Measured false here: the throw lands while building the `.banner(...)` argument, ahead of `.run(args)`, and the whole probe finished in 199 ms. Locate where in the chained call the throw actually occurs before concluding the site is untestable.
- WebGoat intentionality, in both directions. `org.owasp.webgoat.server` is bootstrap code — no assignment depends on an uncaught banner failure, so "it's a teaching app, it's deliberate" does not apply to this site. Equally, do not carry that conclusion to every NO_CATCH: if one lands inside a lesson where the crash is the lesson, or where adding a `catch` would hide the flaw a student is meant to trigger, settle it on that specific ground.
- Overstating reach. The precondition is a classpath/packaging condition — banner-webwolf.txt ships in src/main/resources and is present in target/classes — not attacker-controlled input. "Remotely triggerable" does not follow from anything on line 24. What does follow is that the failure mode is a bare stack trace and exit 1 with no indication of which resource was missing.
- Treating the regex as the finding. It only locates call sites (13 of 46 lines in this file); the missing handler is invisible to any per-line pattern, so a match is a candidate to open, never a defect on its own.
