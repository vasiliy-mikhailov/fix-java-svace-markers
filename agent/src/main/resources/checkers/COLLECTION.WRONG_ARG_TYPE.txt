\.(?:contains|containsKey|containsValue|indexOf|lastIndexOf|removeAll|retainAll)\s*\(\s*(?!")|\.(?:get|getOrDefault|remove)\s*\(\s*[\w$]+\s*\.\s*[\w$]+\s*\(
A call to a collection or map method whose parameter is declared `Object` rather than the type parameter — `contains`, `containsKey`, `indexOf`, `remove(Object)`, `removeAll`, `Map.get`, `getOrDefault` — where the argument's static type is unrelated to the element or key type, so the lookup can never match. Generics do not guard those signatures: the call compiles silently and returns `false`/`null` forever instead of erroring. Do not confuse it with the type-correct neighbours that share the spelling — `List.get(int)` and `List.remove(int)` take an index, not a key, and `String.contains(CharSequence)` is not a collection call at all — nor with a broken `equals`/`hashCode`, where the argument type is right and the comparison misses anyway; that is a different defect with a different fix.

HOW YOU MAKE IT VISIBLE.
The call is silent — no throw, no warning — so you can never assert on it. Assert one level up, on the caller's observable result: the filter that never filters, the cache that never hits, the removal that never removes. The commonest shape is a write and a read disagreeing on the key type, `put(obj, v)` beside `get(obj.getName())`, where every read misses and each write therefore overwrites the previous entry; the observable there is the earlier value going missing. Assert membership of values you put in yourself, never a size or a total — shared or static fixtures make counts order-dependent and flaky.

If the always-false result flows into a branch the code handles identically there is no observable difference and no honest RED. Settle it as a real but undemonstrable type error, citing the two declarations: the collection's element or key type, and the argument's static type. Line drift is real in this family and looks exactly like a bad marker — run the regex over the whole enclosing method before concluding nothing is there, and if the mismatch was already repaired upstream, say so rather than reverting a fix to manufacture a RED.

WHAT GOES WRONG HERE.
Asserting the marker back at itself. `assertFalse(list.contains(x))` tests the language, not the program: it passes against the bug while demonstrating no consequence, and it inverts rather than holds after the fix. Any assertion whose subject is the flagged expression merely restates the marker.

Expecting an exception. `HashMap.get` and `ArrayList.contains` never throw for a wrong-typed argument; they hash and `equals` their way to a clean miss, so `assertThrows(ClassCastException.class, …)` goes RED for the wrong reason and can never go GREEN. Sorted collections — `TreeMap.get`, `TreeSet.contains` — do throw, which is why the habit exists; check which kind you have.

"It compiles, and the API takes `Object`, so it must be intended." `Collection.contains(Object)` is Object-typed for pre-generics compatibility, not as an invitation to pass anything. The mismatch is the entire defect, and this family produces real user-facing bugs: options that never take effect, caches that never hit.

Fixing at the wrong end. Casting the argument, or loosening the collection to raw or `List<Object>`, either keeps the miss or turns a silent wrong answer into a runtime `ClassCastException`. Fix the argument so its type is the one the collection holds.

And undemonstrable is not false. The type claim is verifiable by reading two declarations, which is a better settlement than either a wrong RED or a dismissal.
