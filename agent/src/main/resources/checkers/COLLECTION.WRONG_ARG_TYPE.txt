\.(?:contains|containsKey|containsValue|indexOf|lastIndexOf|removeAll|retainAll)\s*\(\s*(?!")|\.(?:get|getOrDefault|remove)\s*\(\s*[\w$]+\s*\.\s*[\w$]+\s*\(
A call to a collection or map method whose parameter is declared `Object` (or `Collection<?>`) rather than the type parameter — `contains`, `containsKey`, `containsValue`, `indexOf`, `remove(Object)`, `removeAll`, `Map.get`, `Map.getOrDefault` — where the static type of the argument is unrelated to the collection's element or key type, so the lookup can never match any element. Generics do not guard those signatures, so the call compiles silently and returns `false`/`null` forever instead of erroring: the flagged sites are `List<String>.contains(LessonName)` in LessonMenuService and `Map<WebGoatUser, Comments>.getOrDefault(String, …)` in CommentsCache, whose companion `put` two lines down uses the `WebGoatUser` key. Do not confuse it with the type-correct neighbours that share the spelling — `List.get(int)`/`List.remove(int)` take an index, not a key, and `String.contains(CharSequence)` is not a collection call at all — nor with a broken or absent `equals`/`hashCode`, where the argument type is right and the comparison misses anyway; that is a different defect with a different fix.

HOW YOU MAKE IT VISIBLE.
The call itself is silent — no throw, no warning — so you can never assert on it. Assert one level up, on the caller's observable result: the filter that never filters, the cache that never hits, the removal that never removes. Both flagged shapes are reachable from plain constructor-injected objects; no Spring context is needed.

Shape 1 — a wrong-typed `contains` used as a filter. `LessonMenuService` is `@AllArgsConstructor`, and `src/test/java/org/owasp/webgoat/container/service/LessonMenuServiceTest.java` already drives it with `standaloneSetup(new LessonMenuService(course, userTrackerRepository, List.of("none"), List.of("none")))` over a mocked `Course`/`UserProgressRepository`. Build it instead with `excludeLessons = List.of("SqlInjection")`, stub the mocked `Lesson` so `getTitle()` returns "SqlInjection" and `getName()` returns `new LessonName("SqlInjection")`, and assert via `jsonPath("$[0].children")` that the category has no children. Against the pre-fix `excludeLessons.contains(lesson.getName())` the lesson is still in the menu — RED, and RED for the real reason, because `List<String>.contains(LessonName)` is false against every element. GREEN once the argument is `lessonName.toString()`. The assertion subject is the rendered menu (the user-visible "EXCLUDE_LESSONS does not exclude"), never the `contains` expression.

Shape 2 — a wrong-typed map key, write and read disagreeing. In `CommentsCache.addComment`, line 91 reads with `userComments.getOrDefault(user.getUsername(), new Comments())` while line 93 writes with `userComments.put(user, comments)`, so every read misses and each private comment overwrites the previous one. Put a JUnit test in package `org.owasp.webgoat.lessons.xxe` (the `protected getComments` is visible there), construct `new WebGoatUser("bob", "pw")` — use the two-arg constructor; the protected no-arg one leaves the wrapped `user` null and `equals`/`hashCode` NPE — call `addComment(new Comment("bob", null, "first"), user, false)`, again with "second", then assert `getComments(user)` contains BOTH texts. RED: only "second" survives. GREEN with `getOrDefault(user, …)`. Two hazards that otherwise waste a build: `comments` and `userComments` are `private static final` and the constructor re-adds three default comments on every instantiation, so assert membership of your two texts, never a size or total; and `WebGoatUser.equals`/`hashCode` do delegate to the wrapped Spring `User`, so equal-valued instances genuinely match — the miss you are demonstrating is the type, not identity.

When neither shape fits: find the nearest package-visible or public entry point that consumes the lookup's result and assert the downstream consequence. If the collection is filled and queried inside one method and the always-false/always-null result flows into a branch the code handles identically, there is no observable difference and no honest RED — say so plainly and settle it as a real-but-undemonstrable type error, citing the two declarations (element type, argument type) as the evidence, rather than inventing an assertion.

Line drift is real in this family and will look like a false positive. `LessonMenuService.java:64` is a comment at HEAD; the construct sat at line 64 only before commit a3fc2177 ("Fix: EXCLUDE_LESSONS not excluding lessons as expected", #2175, which shipped with no test) and now reads `excludeLessons.contains(lessonName.toString())` at line 69. Run the regex over the enclosing method, and `git log -S` the expression, before deciding nothing is there. If the fix already landed upstream, no RED exists against HEAD and the honest settlement is "already fixed", named by commit — do not revert a fix to manufacture one.

WebGoat caveat: this family is bookkeeping, not curriculum — a mistyped lookup argument teaches nothing about security, and both flagged sites are menu building and comment storage. In `CommentsCache` the deliberate vulnerability is `parseXml` a few lines above (external DTD and schema left open unless `securityEnabled`); the map key on line 91 is not part of it, and fixing the key leaves the XXE assignment solvable. That does not make every collection under `lessons/` safe to change — check what the assignment's solution actually depends on before altering behaviour there.

WHAT GOES WRONG HERE.
Asserting the marker back at itself. `assertFalse(excludeLessons.contains(lesson.getName()))` or `assertNull(userComments.get(user.getUsername()))` tests the JLS, not WebGoat: it "passes" against the bug while demonstrating no consequence, and it inverts rather than holds after the fix. Any assertion whose subject is the flagged expression restates the marker; the subject must be what the caller returns — the menu's children, the comments the user gets back.

Expecting an exception. `HashMap.get`/`getOrDefault` and `ArrayList.contains` never throw for a wrong-typed argument; they hash and `equals` their way to a clean miss. An `assertThrows(ClassCastException.class, …)` here goes RED for the wrong reason and can never go GREEN. (Sorted collections — `TreeMap.get`, `TreeSet.contains` — do throw, which is why the habit exists; neither flagged site is one.)

"It compiles, and the API takes `Object`, so it must be intended." `Collection.contains(Object)` is Object-typed for pre-generics compatibility, not as an invitation to pass anything. The mismatch is the entire defect, and at the LessonMenuService site it was a real user-facing bug that upstream fixed by hand.

Fixing at the wrong end. Casting (`(String) lesson.getName()`, a genuine `ClassCastException` at runtime) or loosening the collection to raw/`List<Object>` either keeps the miss or turns a silent wrong answer into a crash. Fix the argument: `lessonName.toString()`, or the `WebGoatUser` rather than its username.

Verdict words that do not follow. "I could not build it, therefore false positive" — undemonstrable is not false. The type claim is verifiable by reading two declarations, and "real, not demonstrable here, evidence is the declared types" is a better settlement than either a wrong RED or a dismissal.

Counting instead of checking membership in `CommentsCache`: static fields plus a constructor that re-adds three defaults make any size assertion order-dependent and flaky.
