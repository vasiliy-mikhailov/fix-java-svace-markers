A value returned by a call that can return null is used on this line with no null check — dereferenced on the spot, or handed to a callee that dereferences it in its first statement. The `.RET` suffix is the load-bearing part: the null was produced by some callee's explicit `return null` (an absent key, a missing row, a lookup miss), so the proof starts at that callee and not at the flagged line. This is not the checker for a parameter or a field that arrives null from framework binding, and the flagged line need not contain a dot at all — in the interprocedural case it is a bare constructor or method call whose argument is the nullable value.

HOW YOU MAKE IT VISIBLE.
Read the callee that returns null, then read every guard between the nearest public entry point and the flagged line. Which of three regimes the site is in decides whether a RED exists at all.

(A) THE DEREF ESCAPES A PUBLIC ENTRY POINT. Drive the real path that makes the callee hand back null and let the exception escape. Assert the entry point's CONTRACT — the status and the body it promises — not the crash. An NPE unwinding out of a request handler is often re-wrapped and thrown at the caller rather than converted into a 500, so an expectation of a 500 never runs and the test errors for a reason the javadoc did not claim; assert the normal contract and let the escaping exception be the RED.

(B) THE DEREF IS SWALLOWED BY A CATCH-ALL. Still provable — the symptom is a substituted answer rather than an exception. Assert the response field that DISCRIMINATES the intended branch from the catch's branch; fields that read the same on both prove nothing. Assert on the response, never on log lines.

(C) THE FLAGGED LINE IS UNREACHABLE. Say so and prove it; do not invent a test. Such a refutation has to carry its steps: that a guard above the line is unsatisfiable for every value the upstream code can produce, and that the value being looked up is written by nothing in the code under analysis. Symmetrically, do not declare a line reachable because its siblings were.

ASSERT THE POST-FIX CONTRACT, NEVER THE CURRENT WRONG OUTPUT. A matcher copied from what the broken code does today passes on the defect and fails after the guard — that is the RED inverted, and it is the commonest way regime (B) goes wrong. Check both directions before believing a RED: the assertion must fail without the guard and pass with it, and the assertion you rejected must do the opposite.

WHAT GOES WRONG HERE.
Asserting the marker back at itself — that the callee returns null for a missing key, or that the dereferencing constructor throws when handed null. Both hold on fixed and broken code, neither executes the flagged line, and both restate a contract nobody disputed.

Fixing the wrong file. Where the dereference physically executes inside the callee, null-checking there makes the stack trace disappear while leaving the caller holding a half-built object and answering nonsense. The guard belongs at the call site.

Grabbing the nearest NPE. One method can hold several null-dereferences, some live and some dead. A RED whose stack frame names a different line is evidence for a different marker; read the line number in the frame before writing the verdict.

Stubbing the producer to return null and then claiming reachability. Forcing null makes the dereference visible and says nothing about whether null occurs in a running system. Either drive the real path, or state in the javadoc where the real null comes from and that the stub stands in for it.

"The guard would break the feature." Argue that from the code: when the null actually occurs the feature had no working path anyway, so the guard removes a crash and removes nothing else. Pair the RED with a second test asserting the feature still succeeds on its normal input, and keep it green.

Reasoning from the reputation of the surrounding code instead of from the flagged line. What the project, package or directory is known for settles nothing in either direction: a neighbourhood that looks like demonstration or sample code does not make an unhandled null on a missing row intentional, and a neighbourhood that looks production-critical does not make it real. By-design needs evidence of a choice that is checked in and that DEPENDS on the null propagating — documentation telling callers to expect the throw, a test asserting it, a comment or suppression naming it. Absent that, the identical dereference is an ordinary defect.

Leaving shared state broken. Where reaching null means deleting a row, a file or a key the rest of the suite depends on, restore it in a `finally` — otherwise later failures cascade and look like your change caused them. And do not close the upstream hole that produces the null when that hole is itself another marker's subject.
