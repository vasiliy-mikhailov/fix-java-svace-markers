(?i)(?:password|passwd|passcode|pwd|secret|credential)\w*["']?\s*(?:=|,|\()\s*(?:"[^"]|[A-Za-z_$]\w*)
The checker fires where a string literal lands next to something it reads as a password: a field or local whose name matches password/passwd/pwd/secret/credential initialised from a literal (`private static final String DEFAULT_PASSWORD = "webgoat";`), a literal handed to a `setPassword(...)`-shaped call, or a literal stored under a password-named constant key — `idorUserInfo.get("tom").put("password", "cat");` at IDORLogin:35 and the identical line 41 are that last form. It is a name-proximity heuristic, not a data-flow proof that the value ever authenticates anything, so the same shape fires on `.passwordParameter("password")` in container/WebSecurityConfig:62 (the literal is the HTTP form field name Spring should read, not a secret) and on `errors.rejectValue("matchingPassword", "password.diff")` in UserValidator:32 (a message key). The construct that matters is a literal that some comparison or persistence step treats as the secret; the neighbouring construct constantly mistaken for it is a literal that merely names a password field, a request parameter, or a hash algorithm (`getHash(secret, "SHA-256")`).

HOW YOU MAKE IT VISIBLE.
A hardcoded password is not a miscomputation. There is no input that makes the program produce a wrong answer, so the reflex test — read the constant back by reflection or scan the .java for a quoted string and assert it is gone — asserts the edit at itself and proves nothing. Do not build that.

What CAN be observed is authentication succeeding on a credential the deployer never chose, or a credential the deployer DID choose being silently overwritten by the constant. The second is the strongest RED in this repo and it lives at container/users/DefaultUserInitializer.java:27. Read run(ApplicationArguments): both branches of `if (userRepository.existsByUsername(ADMIN_USERNAME))` execute the same `userRepository.save(new WebGoatUser("webgoat-admin", DEFAULT_PASSWORD, ROLE_ADMIN))`, so the class javadoc's claim that existing credentials are "left untouched ... or re-ensured" is false: the admin password is reset to "webgoat" on every start-up. AdminController:161 exposes `POST /service/admin/users/{username}/reset-password`, which generates a random temp password via UserService.resetPassword — and the next restart reverts it. Test it with plain JUnit + Mockito, no Spring: Lombok's `@AllArgsConstructor` gives `new DefaultUserInitializer(userRepository, userService)`.
