(?i)(?:password|passwd|passcode|pwd|secret|credential)\w*["']?\s*(?:=|,|\()\s*(?:"[^"]|[A-Za-z_$]\w*)
A string literal sitting next to something the checker reads as a password: a field or local whose name matches password/passwd/pwd/secret/credential initialised from a literal, a literal handed to a `setPassword(...)`-shaped call, or a literal stored under a password-named key. It is a NAME-PROXIMITY HEURISTIC, not a data-flow proof that the value ever authenticates anything, so it fires just as readily on a literal that merely NAMES a password field — a form-parameter name handed to a security configuration — on a validation or message key, and on an algorithm name passed beside a secret. The construct that matters is a literal that some comparison or persistence step treats AS the secret; which one you have is decided by reading what the flagged call does with the value.

HOW YOU MAKE IT VISIBLE.
This is not a miscomputation: no input makes the program produce a wrong answer. So the reflex test — reading the constant back by reflection, or grepping the source from inside the test — asserts the edit at itself, and its outcome depends only on whether the edit was made. What CAN be observed is authentication succeeding on a credential nobody deployed, or a deployer-chosen credential silently overwritten by the constant. Bootstrap code whose javadoc claims existing credentials are left untouched, but whose branches all save the constant anyway, is the strongest shape: seed the store with an operator-chosen value, run the initialiser, assert the stored value survived. Check how the value is stored before choosing the assertion — with no password encoder wired in the string is kept verbatim, plain equality is right, and a `matches()` call has no hash to match.

FIRST, GREP THE LITERAL ACROSS THE WHOLE TREE, resources and tests included. When the same string comes back out of documentation, a resource bundle, a front-end script, or a test that types it in to exercise the feature, the value is published on purpose, and any build that "proves it fixed" must break one of those consumers — checkable evidence of intent, cited as file:line rather than asserted. Absence of such hits is not permission in the other direction; it only means the line needs its own argument. Some literals say it in the identifier itself: a constant whose name calls the value a sample, a demo, a default or a test credential is itself checkable evidence that it was published deliberately, and the declaration is citable as file:line like any other consumer.

DEMONSTRATE ON THE CONSTRUCT THE MARKER NAMES. Files that fire this checker come in clusters, and the nearest sibling is often the shapelier one to build on — a cleaner comparison, a store you can seed, a literal that is unambiguously the secret. A recipe built on that sibling proves nothing about the flagged line and settles nothing, however well it goes RED. Before you commit to a line, confirm it is the line the marker cites; if the convenient construct is elsewhere, the finding is about the marked construct anyway.

Two shapes that look testable and are not. A literal no comparison ever reaches — the surrounding code short-circuits on some other check first — admits no RED for any edit, whatever you conclude about the string, so trace the comparison path before choosing a line to demonstrate on. And a literal in the test tree is a fixture, never stored or transmitted as a product credential; the only assertion available would be about the test's own input.

WHAT ELSE GOES WRONG HERE.
A fix that leaves the build GREEN and breaks the product: the Java tests may import the constant by name while a non-Java consumer hardcodes the old string, so every test passes and the feature silently stops working. Grep the value, not just the symbol.

Editing fixtures that are deliberately unequal. Two near-identical literals often exist precisely because a test asserts the mismatch branch; folding them into one shared constant deletes that assertion and stays green.

Verdicts that do not follow. The reputation, name, package or directory of the code around the literal decides nothing, in either direction: "the surrounding code is security-flavoured, so the literal is meant to be there" is not an argument about the flagged line, and neither is "this is ordinary infrastructure, so it is a finding". Intent is shown by something checked in that DEPENDS on the constant staying what it is — documentation telling a caller to use it, a test that asserts on it, a comment or suppression naming the choice. Absent that, the identical literal is an ordinary defect. The decision comes from what the flagged line does with the value plus what the grep brings back.

Finally, the marker's line may have drifted off the construct; settle against the construct the file actually holds and say the line moved, rather than inventing a defect to fit stale text.
