DEREF_AFTER_NULL asserts that a reference the program itself has already admitted can be null — an earlier `x == null` branch, an `x = null` assignment, or a call whose own body has a `return null` path — is then dereferenced (`x.foo()`, `x.field`, `x[i]`) on a path where no guard dominates the use. The report anchors on the dereference, not on the null-producing site, and where the source is formatter-wrapped that anchor is the FIRST line of the statement: a bare `var x =` with the chain on the next line still means the whole statement, so an anchor with no visible dereference is not an empty marker. Two neighbours are routinely mistaken for it: NULL_AFTER_DEREF is the reverse order, dereference first and a redundant `!= null` check after, a readability finding no test can turn into a failure; DEREF_OF_NULL is the unconditional case, null on every path, whose NPE needs no path construction. This one is path-conditional, which is why demonstrating it means building the path.

HOW YOU MAKE IT VISIBLE.
Every instance has two sites and the marker gives you one. Name both before writing a test: D, the dereference on the flagged statement — enumerate them, a chain has one per receiver — and N, the program fact that says that reference can be null. The test is a route from N to D.

N must be something the PROGRAM can produce on real input: not something a stub can be told to produce, and not something you hand in through a constructor or parameter no caller ever passes null to. Ordinary sources are a `return null` branch in the same file, a `Map.get` miss, a lookup that returns null when nothing matched, `getCookies()` on a request that carries none, `getHeader`, `getParameter`, `getSession(false)`, `session.getAttribute`, `Optional.orElse(null)`, `System.getenv`. Finding a source is not enough — show it REACHES D. A null produced and then guarded before every use is not this defect, however real the null is.

RED shape: arrange N's precondition, call the smallest unit containing D, and pin WHICH dereference blew up rather than merely that some NPE escaped. Helpful NPE messages make that checkable — assert on text of the form `Cannot invoke "X.y()" because "<expr>" is null`, naming the expression from the flagged statement. Without the pin, an NPE thrown by your own arrangement counts as a pass and proves nothing. GREEN shape: assert the post-fix behaviour, the fallback value or graceful failure now returned, not the absence of an exception — "no exception thrown" also passes when the test stopped reaching the code at all.

When the only null that reaches D comes from a stub contradicting a documented contract, or from an argument no call site can pass, settle the marker as refuted and write out the guard and the contract you relied on. A drive that exercises the null path and passes before any change is a refutation artifact, not a RED; label it as one. Do not add a defensive `if (… == null)` on a path no input can reach: a dead guard is uncoverable and leaves the marker unfalsifiable instead of settled.

WHAT GOES WRONG HERE.
Mocking the null into existence. Stubbing a library call to return null when its contract says it never does proves only that the mock lied. Many APIs signal failure by throwing rather than by returning null, and a factory that hands back a handle hands one back unconditionally, whether or not the thing behind it exists.

Handing in the null yourself. A null passed through a constructor or parameter yields a perfectly pinned NPE message with no mock at all, so it looks legitimate — but if every real construction site supplies a value, that is a caller-contract violation, not the defect the checker claims. Likewise `assertThrows(NullPointerException.class, …)` with no message assertion on a method with several easily-nulled parameters: an NPE that fired four lines early is a false proof.

Assuming the NPE is observable as a thrown exception. A broad `catch (Exception e)` around the dereference turns it into an ordinary return — a success-shaped response carrying the NPE text in its body. A test expecting a throw fails there although the defect occurred; assert on the returned result or the response body.

Deciding the verdict from the neighbourhood. The verdict comes from the flagged statement and the paths that feed it, never from the name, package or directory around it, and that cuts both ways: a name suggesting demonstration or throwaway code exempts nothing from ordinary defects, and a name suggesting hardened code supplies no defect either. Intent shows only in something checked in that DEPENDS on the dereference behaving as it does — a test asserting the throw, documentation telling callers to expect it, a comment or suppression naming the choice. What constrains a fix is the behaviour the module's own tests already encode; read those before changing control flow, because an early failure return can change the result a correct input produces.
