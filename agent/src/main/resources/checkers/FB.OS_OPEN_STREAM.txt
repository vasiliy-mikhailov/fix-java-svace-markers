\bnew\s+\w*(?:Zip|Jar)File\s*\(|\bnew\s+\w*(?:InputStream|OutputStream|Reader|Writer)\s*\(|\.(?:readLine|getInputStream|getOutputStream)\s*\(
A stream or other Closeable is opened into a local variable and can reach a method exit without close()
on any path — no try-with-resources, no finally. Its neighbour OS_OPEN_STREAM_EXCEPTION_PATH makes the
weaker claim that a close() does exist but is skipped when an exception unwinds. The marker line is
often not the construction site but a later USE of the handle, so a flagged
`while ((line = in.readLine()) != null)` is a complaint about `in`, declared above, and never about
readLine or about the loop. Identify the subject variable before writing anything.

HOW YOU MAKE IT VISIBLE. The leak changes nothing an ordinary assertion can see — same return value,
same bytes written, same log lines. The observable is either the close() call itself or resource
accounting outside the method.

CONSTRUCTION INTERCEPTION is deterministic and needs no seam in the code: a mocking framework with an
inline mock maker intercepts an inline `new X(...)` executed inside production code on the test thread,
and you then verify close() on the constructed instance. Stub every method the code calls on that mock,
or an unstubbed call returns null, the NPE escapes a handler that catches only IOException, and you get
a RED for the wrong reason. Recent JDKs may also need dynamic agent loading enabled before the inline
mock maker can attach.

DESCRIPTOR ACCOUNTING is the blunter witness and works only for file-backed handles: read the open
descriptor count from the platform MXBean (guard with an assumption — it is not that type on every OS),
loop the method under test, compare the delta. Three conditions each produce a silent false GREEN. Use
a DISTINCT file per iteration, because the JDK refcounts a shared archive Source keyed by file key and
mtime, so reopening one file lends every iteration the same descriptor and genuinely leaking code
measures zero. Put no System.gc() anywhere, because these handles register a Cleaner and a forced GC
takes the delta straight back to zero. And do not measure the leaky and the fixed case in that order in
one JVM, or the fixed run reads a negative delta as the earlier leaks are cleaned under it. The leaked
count is capped by whenever GC first runs, so assert a large delta, never delta close to the iterations.

SOME HANDLES ARE RECLAIMED BY SOMETHING ELSE and accounting can never see them: a stream over a child
process's pipe is drained and closed by the JDK's reaper thread when the child exits, and a method that
reads to EOF cannot return before that happens. That is a fact about descriptor counting, not about
testability — interception still settles such a site, and "the accounting cannot see it" is never by
itself a reason to skip the build.

Closing an archive handle is the complete fix, because it closes the entry streams it handed out. But
do not assume a stream is closed by whatever consumes it: Files.copy(InputStream, Path, ...) leaves the
source open while some library copy helpers close both ends, and calls with opposite contracts turn up
on adjacent lines of one method. Read the contract of the call that is actually there.

WHAT GOES WRONG HERE. Aiming the fix at the method being called rather than at the handle it is called
on. Asserting the marker back at itself — with no output difference, a test that drives the entry point
and checks the response is GREEN before and after the close is added. Assuming two markers settle alike
because they share a checker, when whether the leak can be witnessed depends on which handle leaked and
on who else reclaims it. Concluding "resource leaks are untestable" as a family verdict, which is true
of handles the runtime reclaims and false of handles nothing reclaims. And over-fixing: the fix is the
close and nothing else.
