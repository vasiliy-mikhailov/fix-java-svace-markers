^\s*[\w$]+(\.[\w$]+)+\s*\([^;]*\)\s*;\s*(//.*)?$
A statement calls a method and discards its return value, and SpotBugs decided the callee — across every implementation it could resolve — has no effect beyond producing that return, so the statement is judged dead and deletable. Distinguish it from the siblings RV_RETURN_VALUE_IGNORED and RV_RETURN_VALUE_IGNORED_BAD_PRACTICE, which flag ignored returns of methods that DO act (`File.delete`, `InputStream.read`, `compareTo`, a transformation whose result you still need) and where the dropped value is the point; only the _NO_SIDE_EFFECT variant means "this call accomplishes nothing, remove it."

HOW YOU MAKE IT VISIBLE.
Decide on the premise, because it settles everything. If the premise is true — return discarded AND callee provably pure — then by construction there is NO observable difference between keeping the line and deleting it; that is exactly what "no side effect, return ignored" asserts. No assertion can separate keep from delete, so a genuine instance is not RED/GREEN demonstrable: it is a dead-code and readability finding to settle by reading.

But read the receiver's STATIC type first, because that is all SpotBugs reasoned over. When the declared type is an interface or a base class and the object arrives from deserialization, a factory, a plugin registry or a dynamic proxy, the implementation that actually runs is one the analyzer never saw. A proxy's invocation handler can execute arbitrary code, so a call that reads as a pure getter can be the live trigger for real behaviour, including starting a process. Where that is so the premise is false, the line is not dead, deleting it silently removes behaviour, and the honest record is that the checker is wrong about this line — not that the line is removable.

OBSERVABILITY IS RUNTIME-CONFIGURATION DEPENDENT, and this is where the demonstration usually goes wrong. The same call can perform its side effect in the deployed JVM and not in the test JVM, because module opens, security configuration, agent flags or resolved library versions differ between the two. A test that builds the impure object and then calls the flagged method may only be observing the construction step failing earlier, which shows nothing about the discarded call. Check the flags and dependencies the test harness actually runs with before claiming a test demonstrates the effect, and if a RED requires changing the harness, say so instead of presenting a passing test as the demonstration.

WHAT GOES WRONG HERE.
1) Asserting the return value: RED `assertNull(x.getName())`, GREEN once it is assigned. That tests the callee's value, which was never in dispute, and asserts the marker back at itself.
2) "Delete the line and the suite is still green" is not proof of a defect. With a pure callee it is exactly what the premise predicts; with an impure one it only means no existing test drives the impure implementation through that line.
3) Concluding "removable dead code" from the static NO_SIDE_EFFECT label when the receiver is an interface. The effect lives in a runtime implementation the analyzer could not resolve, so "no side effect" does not follow from the report.
