A statement calls a method and discards its return value, and SpotBugs decided the callee (across every implementation it could resolve) has no effect beyond producing that return value, so the statement is judged dead and deletable. Distinguish it from siblings RV_RETURN_VALUE_IGNORED / _BAD_PRACTICE, which flag ignored returns of methods that DO act (File.delete, InputStream.read, String.trim/replace on a value you still need, compareTo) where the dropped value is the point; only the _NO_SIDE_EFFECT variant means "this call accomplishes nothing, remove it." The one flagged line is contact.getFirstName(); at VulnerableComponentsLesson.java:49 — a getter call whose result is thrown away.

HOW YOU MAKE IT VISIBLE.
Decide on the premise, because it settles everything. If it is truly true — return discarded AND callee provably pure — then by construction there is NO observable difference between keeping the line and deleting it; that is exactly what "no side effect, return ignored" asserts. No JUnit assertion can separate keep from delete, so a genuine instance is not RED/GREEN demonstrable: it is a dead-code/readability finding to settle by reading, verdict "not provable by test." But first read the receiver's STATIC TYPE, because SpotBugs computes "no side effect" only over implementations it can resolve. On line 49 `contact` is declared as the INTERFACE Contact; ContactImpl.getFirstName() is a pure Lombok getter (all the analyzer saw), yet xstream.fromXML returns whatever the payload names. I ran it on xstream 1.4.5: the dynamic-proxy payload (line 50's comment cites CVE-2013-7285) makes fromXML return a jdk.proxy2.$ProxyN, and the discarded getFirstName() call fires its EventHandler — a ProcessBuilder actually starts, then the call throws ClassCastException (ProcessImpl->String). CHECKED AGAINST THE CHECKOUT BY A SECOND READER WHO RE-RAN THE CLAIMS ABOVE. Where the two disagree, THIS IS THE ONE THAT HOLDS.
First read the receiver's STATIC type, because that is what SpotBugs reasoned over. On line 49 `contact` is declared as the INTERFACE Contact; the only impl the analyzer could resolve is ContactImpl.getFirstName(), a pure Lombok getter — hence NO_SIDE_EFFECT. But xstream.fromXML returns whatever the payload names, and line 50's comment cites CVE-2013-7285: a dynamic-proxy payload makes fromXML return a jdk.proxy2 proxy whose getFirstName() fires a java.beans.EventHandler that invokes ProcessBuilder.start(). So line 49 is the deliberate RCE trigger of the lesson; the NO_SIDE_EFFECT premise is false and this marker is a FALSE POSITIVE — do not delete it (deletion silently removes the CVE trigger and disarms the lesson). Observability is configuration-dependent, and the note overstates it. In the SUREFIRE unit-test JVM (its argLine opens java.base/sun.nio.ch,io,util,lang.reflect,text and java.desktop/java.awt.font but NOT java.desktop/java.beans and NOT java.base/java.lang), the malicious proxy CANNOT be deserialized: xstream.fromXML THROWS ConversionException/InaccessibleObjectException while building java.beans.EventHandler, BEFORE getFirstName() runs, and NO process starts. That is exactly what the shipped VulnerableComponentsLessonTest already shows (3 tests pass; its captured exception chain is InaccessibleObjectException, swallowed) — so testIllegalTransformation/testIllegalPayload do NOT demonstrate the getFirstName() side effect; they observe fromXML throwing. The proxy-returns / getFirstName()-starts-a-ProcessBuilder / ClassCastException(ProcessImpl->String) behavior only occurs when java.desktop/java.beans + java.base/java.lang + java.base/java.lang.reflect are ALSO opened — which the project does for the DEPLOYED server JVM only (pom start-jar, ~lines 786-800), i.e. how the lesson runs live. I reproduced both: under surefire's opens fromXML throws and nothing runs; under the server's opens a process really starts and getFirstName() throws ClassCastException. Bottom line: this is a false positive whose side effect is real in the app runtime but NOT observable in the unit-test harness as-shipped. Treat it as a read-and-reason "do not delete" finding; to make it RED/GREEN in a unit test you must add --add-opens java.desktop/java.beans + java.base/java.lang(+.reflect) to surefire, otherwise a parse-then-call test only shows fromXML throwing, not the getFirstName() side effect the note promises.
