The checker asserts that a particular `new` allocation, stored into a local variable, never influences anything the method does: it does not escape (not returned, not stored in a field, not passed on, not thrown), and any mutation applied to it is lost when the reference is dropped. It is a claim about one ALLOCATION SITE, not about the variable — the same variable may be reassigned a line later and then used heavily. Two neighbours are routinely mistaken for it: DLS_DEAD_LOCAL_STORE is about a value assigned and never read, regardless of whether it was freshly allocated, and UC_USELESS_OBJECT_STACK is the same useless-object defect where the object was never assigned to a local at all (`new Foo();` standing alone as a statement).

DECIDE WHICH OF TWO VARIANTS YOU HAVE before planning a test, because only one of them is testable. The discriminator is mechanical and requires opening the file: does any mutation carrying real data reach THIS allocation before the reference is overwritten or falls out of scope?

(1) NOTHING WAS EVER PUT IN IT. Watch for a first read that looks reachable and is not: a reference reassigned on the first pass through a loop, or inside a branch taken before any read, kills the original object on every path — and if the loop body never runs, the object is dropped untouched, so work the indices and conditions rather than reading top to bottom. This variant cannot be made visible by a test: with and without the allocation the two programs compute the same value, which is precisely what "useless" means, and no reachable state, return value, response field or log line differs. Do not attempt a RED. An existing test over the enclosing entry point is still worth naming — it is the GREEN regression guard, and the deletion is correct exactly when that test keeps passing unchanged.

(2) IT WAS POPULATED AND THEN DISCARDED. If add/put/setter calls carrying real data run between the allocation and the point where the reference is lost, the checker may have found a genuine lost-data bug: values the author meant to reach a caller that silently never arrive. That IS observable. Call the public entry point with a distinguishable input and assert at the boundary that the value appears in the returned collection, the response body or the field. RED before the fix is a missing key or a short collection, not an exception.

WHAT GOES WRONG HERE.
Asserting the marker back at itself. Because variant (1) has no observable effect, agents reach for a "test" that reads the source text, counts allocations in the bytecode or profiles the heap. Those assert on the marker's own text and not on a defect.

"Harmless, therefore false positive." Not the same claim. A dead allocation really is dead; a true finding that no test can distinguish is not a false positive, and collapsing the two states something about the code that is false.

Deleting the initialiser can break the build. If the only remaining write to the variable sits inside a conditional, javac rejects the later use with "variable might not have been initialized". Initialising to null compiles but can trade this marker for a null-dereference warning there; the cleaner alternative is usually to restructure so the value is written through wherever it was meant to land.

Deleting the variable. It may be live on several later lines; an agent that greps the name, sees uses and declares the report bogus has checked the variable when the checker spoke about one allocation. And whatever the fix, the enclosing method's observable output must come out identical — tidying the surrounding logic while you are there is a different change that this marker does not warrant.
