\b(?:public|protected)\s+static\s+(?:(?:final\s+)?\S+(?:\[\s*\]|<[^>]*>)|(?!final\b|class\b|void\b)\S+)\s+\w+\s*[=;]
MS_PKGPROTECT fires on a static field that is public (or protected) and whose value can still be mutated by anyone able to name it — canonically a `public static final` array, because `final` freezes the reference and not the elements; the family also covers public static collections and public static non-final fields of any type. The complaint is about the declaration's VISIBILITY: the analyzer saw no access from outside the field's own package in the classes it was given, so it says the field could be package-protected. It is not MS_SHOULD_BE_FINAL (a static missing `final`), not MS_EXPOSE_REP (a static getter handing out the internal object), not EI_EXPOSE_REP (the instance-level version), and a public static final String, int or any other immutable value is never this checker — the regex above deliberately also matches immutable-typed declarations, which are the shape but not the defect.

HOW YOU MAKE IT VISIBLE.
Attack the ALIASING, not the modifier. The trap that kills most attempts: the checker's own remedy, narrowing the field, makes a RED written with a compile-time reference stop COMPILING rather than turn GREEN, and a non-compiling test is not a GREEN. The test source must name the field only at runtime, so the same source compiles in both states.

There are TWO distinct reflective accessors and confusing them decides whether you ever reach GREEN. The HOSTILE WRITE models an ordinary caller in another package and goes through `Class.getField`, which sees public members only — so after any real fix (narrowed, made private behind a cloning accessor, retyped to an immutable collection) the handle is simply not there, the write never lands, and the test goes GREEN, while a cosmetic fix that adds a defensive-copy getter and leaves the field public stays RED, correctly. The HARNESS READ, where the assertion needs the field's current contents, goes through `getDeclaredField` plus `setAccessible` and survives the fix on purpose: the test may have privileges the attacker does not, and the claim under test is whether an UNPRIVILEGED writer can still reach the value. Write only through the public handle, read only through the forced one. Reading the live value with `getField` is the obvious move and it silently destroys the test — after the fix that read handle is gone too, the loop over the contents iterates nothing, and the test is RED in both states. That dead end is what makes this marker look unprovable when it is not.

THE ORACLE MUST NOT BE THE FIELD. Building the expected contents by reading the same field is vacuous — the mutated value satisfies itself and the test passes in both states. Expected values are literals typed into the test, or the output of a pure function applied to such a literal.

WHEN THE WRITE CANNOT REACH THE CONSUMER, CHANGE CONSUMER. If a consumer snapshots an element during static initialisation, a post-init write cannot affect it, and you cannot front-run the initialisation because any reflective `get(null)` triggers it. The demonstrable consumer is then one that reads the field LIVE on each use — and there the live read is correct precisely because that lookup is the contract under test.

Snapshot the field before and restore it after: one write poisons every later test in the same forked JVM, and the fact that the test has to do this is itself the clearest statement of the defect. Put the test in a DIFFERENT package from the field; a test sitting next to the class quietly destroys the cross-package point.

WHAT GOES WRONG HERE.
Asserting the marker back at itself: `assertFalse(Modifier.isPublic(f.getModifiers()))` or `assertThrows(NoSuchFieldException.class, ...)`. It does flip RED to GREEN, but it restates the declaration and would pass identically for a public IMMUTABLE field, which is not this checker.

`arr[0] = "x"; assertEquals("x", arr[0]);` — proves that Java arrays are mutable. True of every array ever written.

Confusing a fix that breaks a consumer with a fix that breaks the build. Changing the CONTENTS changes behaviour for everything depending on the values. Narrowing the VISIBILITY changes no behaviour, but the analyzer said "could be package protected" only because it was shown one set of classes; other source roots wired in by the build may read the field from another package and stop compiling, so grep for cross-package readers first. Retyping an array to an immutable collection is not free either — it breaks every indexed use site.

The verdict trap in both directions. "This code is insecure on purpose, so this is intentional" does not follow unless something actually depends on the visibility. Nor is it a defect already happening in production, when no code in the repository writes the field: the failure needs a hostile or careless writer that YOU introduce. Settle it on the grep and on what depends on the field, not on the repository's reputation.
