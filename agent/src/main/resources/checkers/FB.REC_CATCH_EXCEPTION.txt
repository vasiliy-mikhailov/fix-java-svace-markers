catch\s*\(\s*(?:final\s+)?(?:java\.lang\.)?Exception\s+\w+\s*\)
SpotBugs reports REC_CATCH_EXCEPTION on a `catch (Exception e)` header when nothing inside the try is
declared to throw `java.lang.Exception` itself and no sibling clause over the same range catches
RuntimeException — so the only thing the clause reaches beyond the checked exceptions the author had in
mind is the unchecked ones, which it swallows silently. The checker is about the TYPE in the catch
header, not about what the handler body does: an empty or log-only body is the separate
ignored-exception family (DE_MIGHT_IGNORE), and `catch (Throwable)` is a different pattern again. A try
that calls something literally declared `throws Exception` does not fire it, and confidence drops when
several clauses share the range or the try can throw many distinct types — which is why an
identical-looking `catch (Exception e)` a few lines away may carry no marker without that meaning the
marked one is different in kind.

HOW YOU MAKE IT VISIBLE. The catch header is a behavioural fact, so it is testable — but only through a
seam that lets the test CHOOSE the exception type thrown inside the try. A collaborator handed in
through the constructor is the usual seam: stub it to throw an unchecked exception and assert that
exception propagates out of the method. Unfixed, nothing is thrown and the method returns as though the
work had succeeded; narrowing the clause to the checked type the body was written for makes it
propagate. Check any wrapper in between first — whether the wrapper calls its delegate before or after
building its own return object decides whether your exception arrives at the flagged line unwrapped.

THAT TEST ALONE IS A TAUTOLOGY. It reads the catch header back out loud. It becomes a statement about
behaviour only when paired with a second test that pins the swallow the author intended: throw the
CHECKED exception the handler exists for and assert it is still swallowed, green before and after. The
pair states the real defect — the clause cannot tell the anticipated, deliberately ignored failure from
a broken component, and continues silently on both. Run the existing tests of the code you narrowed as
the guard that the change touched nothing else.

Where the handler does not return void, the same seam applies and you assert on the RESULT instead of
on propagation: with the collaborator broken, the caller receives an ordinary success response carrying
a failure message, indistinguishable from a legitimate negative answer. Prefer the plain constructor
seam to standing up a whole framework context, since replacing a shared bean wholesale drags in every
other component's initialisation.

A genuinely seamless site is one where the datasource, client or parser is constructed INSIDE the
method and no argument or field can carry a substitute. If neither a constructor seam nor an observable
handler result exists, settle the marker as not demonstrable and say why, rather than asserting on
source text or on a log line.

WHAT GOES WRONG HERE.
Asserting the marker back at itself: stubbing a RuntimeException and asserting it propagates, with
nothing else, only restates the catch header.

Offering the checked-exception case as the RED. It is green before and after the fix; it is the
regression guard, not the demonstration.

Reaching for a log assertion. These handler bodies are frequently a bare comment — no logger, no
appender, no message to match.

"Fixing" by deleting the catch or rethrowing everything. The swallow can be load-bearing: a start-up
hook whose operation genuinely fails on every run after the first will take the whole component down
once that exception is let out. Narrow the type, keep the swallow.

Reading an unflagged `catch (Exception e)` nearby as proof the marker means something else. A tree can
hold dozens of them with only one in the queue.

Asserting on `e.getMessage()` text for an unchecked exception. JVM-generated messages are version
dependent and prove nothing about the width of the catch.
