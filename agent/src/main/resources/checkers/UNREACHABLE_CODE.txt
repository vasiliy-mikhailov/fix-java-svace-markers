^\s*(?:else\b|return\b|throw\b|break\b|continue\b|case\b|default\s*:|try\s*\(|catch\s*\()
The flagged statement is the head of a region no execution can enter: the analyzer's dataflow found no path to it. In Java it is never the textbook case of a statement sitting after a `return` or `throw`, because JLS 14.21 makes that a compile error. So a marker here is always one of three things: a branch killed by a value the analyzer folded but javac did not (a non-final local assigned only one value is not a "constant variable", so the branch is still emitted), a catch handler for an exception the analyzer proved cannot be thrown, or a line whose only unreachable code is compiler-synthesized and does not appear in the source at all. Do not read it as a dead-store report, which points at a value written and never read, nor as a constant-condition report, which points at the `if`; this points at the code that never runs, typically a line or more below the condition that killed it.

SPECIES A — A REAL DEAD BRANCH. A local assigned one literal and never reassigned degenerates a compound guard, so a later `else if` on the same variable can never be taken. Confirm with `javap -p -c -l` that the branch survives compilation and that the flagged line owns live bytecode — the analyzer, not javac, is the one that can see it — and read the history of the guard, since such an orphan usually dates from a commit that replaced a call with a constant and deleted the callee. The observable is negative: a documented output the program can never produce. If the surviving guard's inputs are enumerable, exhaust them and assert that output never appears. Then be plain about what that test is worth — GREEN before the fix and GREEN after. Removing unreachable code is behaviour-preserving by construction, so no behavioural test can go RED on the unpatched tree and GREEN on the patched one. Settle by exhaustion plus the bytecode and history reading, as confirmed-by-reading and not RED-provable, and do not upgrade that into a manufactured red.

SPECIES B — NOTHING ON THE FLAGGED LINE IS DEAD IN THE SOURCE. javac gives try-with-resources an unwind arm — `close()`, `addSuppressed`, `athrow` — and maps it back to the same source line as the resource declaration; a method's compiler-inserted `return` maps to the closing brace. The flagged line may therefore execute plainly, or carry no statement at all, while the unreachable instruction it owns is nowhere in the file. Read the LineNumberTable of the enclosing method before writing anything: when the line maps both to live bytecode and to a synthesized block, quote that and settle as not provable, nothing to remove. Never reject such a marker as "the line contains no construct" — report which synthesized instruction the line owns. There is no fix either; the only edit that removes the construct abandons try-with-resources, trading a phantom warning for a real resource leak.

SPECIES C — REACHABLE, JUST NOT REACHED YET. Before concluding that no seam exists, try to BUILD the state. A handler the analyzer called dead is often live code: opening a file throws, copying a stream throws, a decoder throws on malformed bytes. If the enclosing class can be constructed directly, arrange the environment — a directory standing where a file is expected, an unreadable file, input that fails to parse — and watch the line execute. That test is GREEN and stays GREEN, because there is no defect and nothing to remove, but an executing refutation is stronger and more honest than a report that no seam could be found. Where two paths produce the same result, equality proves nothing about which one ran; instrument the difference with a marker return or a call count before believing the observation.

A CATCH THE LANGUAGE REQUIRES CANNOT BE DELETED, however sound the dataflow behind the marker. When the flagged handler sits inside a lambda body and the functional interface's method declares no checked exception, every checked exception the body's callees declare must be caught before it can leave the lambda; javac decides that from the callee's `throws` clause alone and takes no interest in a proof that the throw never happens at runtime. Strike the handler and the file stops compiling — `unreported exception ... must be caught or declared to be thrown` — with nowhere to declare it, since the interface method's signature is not yours to widen. The same trap holds for any catch standing between a declared-throwing call and an enclosing method that does not declare the type. So for a handler that genuinely cannot be entered, deletion is not the fix and must not be proposed as one: attempt the compile, quote the error, and settle as nothing to remove. What is left — narrowing the caught type, or wrapping and rethrowing unchecked — changes behaviour and is not warranted by an unreachability report alone.

THE DISCRIMINATOR, in order: if an existing test already executes the flagged statement you are in B; if not, and you can enumerate the controlling guard's values and show every one goes elsewhere, you are in A; if neither, you are in C and must construct the state before writing "no seam". "Nothing exercises it today" is not "nothing can".

WHAT GOES WRONG HERE.
Manufacturing a RED out of the feature the dead branch used to serve, by asserting the output only the orphaned branch could produce. That fails today and fails identically after the branch is deleted, because it asserts a behaviour an old commit removed rather than the defect the marker names. Leftover fixture setup for the deleted check is not evidence the path is live.

Reviving the branch instead of removing it, by restoring the guard whose deletion orphaned it. That adds a gate the rest of the code no longer expects and can make the surrounding feature unusable. The converse holds just as firmly: an orphaned branch is no part of what the surrounding code does, and deleting it takes nothing away. Decide per construct, from the code's own success condition, not from which directory it lives in.

Asserting the marker back at itself: parsing a coverage report, or reflecting over bytecode, to assert the line never executed. That restates the analyzer's claim and passes whether or not the branch is removed.

The verdict that does not follow: "no test can distinguish before from after, therefore false positive". For species A the marker is exactly correct and the code is exactly dead; untestable and wrong are different findings. Nor does B's conclusion generalise — "unreachable code always means compiler noise" is refuted by any live `ifeq` guarding a block no input can reach.
