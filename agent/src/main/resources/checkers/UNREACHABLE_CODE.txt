UNREACHABLE_CODE asserts that the flagged statement is the head of a region no execution can enter: the analyzer's dataflow found no path to it. In Java it is never the textbook case of a statement sitting after a `return` or `throw`, because JLS 14.21 makes that a compile error — so a marker here is always one of three things: a branch killed by a value the analyzer folded but javac did not (a non-final local assigned only one value is not a "constant variable", so the branch is still emitted), a catch handler for an exception the analyzer proved cannot be thrown, or a line whose only unreachable code is compiler-synthesized and does not appear in the source at all. Do not read it as a dead-store/useless-assignment report, which points at a value that is written and never read, nor as a constant-condition report, which points at the `if`; UNREACHABLE_CODE points at the code that never runs, typically one or more lines below the condition that killed it.

REVISED DISCRIMINATOR (three steps, in order):
(a) Does an existing test already execute the flagged statement? If yes → species B: the only unreachable candidate is in `javap`, not in the file. Quote the LineNumberTable and settle as "not provable, nothing to remove".
(b) If not, can you enumerate the controlling guard's values and show every one goes elsewhere? If yes → species A: the code really is dead, the marker is correct, and no behavioral test can separate before from after. Settle by exhaustion plus bytecode/history, reported as confirmed-by-reading and not RED-provable.
(c) If neither — the statement is reachable in principle but nothing exercises it — do NOT stop. Name the state that would reach it and construct it (@TempDir layout, a directory where a file is expected, an unreadable file, a stream that throws). Only after that construction fails may you write "no seam". "Nothing exercises it today" is not "nothing can"; that inference is what cost the DM_DEFAULT_ENCODING family 33 markers.
