\.(getConnection|createStatement|prepareStatement|prepareCall|executeQuery)\s*\(
ODR_OPEN_DATABASE_RESOURCE says the method obtained a JDBC resource, kept it local — not returned,
not stored in a field, not handed to another object — and has no path out of the method on which
close() is reached. The marker's line is the ACQUISITION, because an omission has no line of its own.

FIRST SETTLE WHICH OBJECT IS BEING CLAIMED. The detector's resource-creation set is exactly
Connection.createStatement / prepareStatement / prepareCall (every signature) and getConnection on
DriverManager or a DataSource, so the flagged object is a Statement, PreparedStatement,
CallableStatement or a Connection — NEVER a ResultSet. `executeQuery` is not a creation site for this
checker; unclosed ResultSets belong to OBL_UNSATISFIED_OBLIGATION, and the two families are routinely
reported side by side in one method. If your marker's line IS an executeQuery call, the resource is
the Statement that line was called on, created above it, and closing only the ResultSet does not
settle it. The sibling ODR_OPEN_DATABASE_RESOURCE_EXCEPTION_PATH means "closed on the normal path but
not when an exception unwinds"; the plain form means closed on no path at all. Do not read the marker
as a complaint about the SQL string usually concatenated on the same line — that is a different
checker — and do not read it as a complaint about a Connection that is already in try-with-resources
while the Statement born from it is not.

HOW YOU MAKE IT VISIBLE. The observable is the state of the JDBC object the flagged line produced,
sampled after the method under test returns. The objection that stops agents building anything — "the
Connection gets closed, so its Statements go with it" — is worth settling on the driver in play
rather than from the spec: a driver may kill the server-side handle on Connection.close() while the
client object still reports isClosed() false. Where that holds, the sample distinguishes "this method
closed it" from "the connection took it down with it", which is the distinction the checker makes.
Closing a Statement likewise need not make its ResultSet report closed, so ResultSet state is never
evidence about the Statement.

GETTING A HANDLE ON IT. Where the code takes its DataSource by constructor, wrap a real one: a
getConnection() returning a dynamic Proxy over a real Connection that delegates everything and
records each Statement handed back. Two traps in building that. The Statement must come back as a
proxy implementing the interface the caller assigns to, chosen by instanceof, or a
`PreparedStatement st = ...` assignment throws ClassCastException; and the handler must unwrap
InvocationTargetException, or checked exceptions the code under test catches instead arrive as
UndeclaredThrowableException and the behaviour changes underneath you.

SCOPE THE ASSERTION TO THE MARKER'S OWN RESOURCE: such a recorder captures every Statement opened
anywhere under the call, including ones from helpers carrying their own markers, so record the
creating call site alongside the object — otherwise a correct fix leaves the test RED for a different
marker's leak. Assert the recorded list is non-empty BEFORE asserting anything about closure, or an
early-return branch gives a vacuous green. For a Connection-level marker, sample one level up: hold
the Connection handed out and assert isClosed() after the method returns.

DO NOT GO LOOKING FOR AN APPLICATION-LEVEL MALFUNCTION. With no pool underneath, every getConnection()
opens a fresh physical connection and closing it reclaims whatever the method leaked, so thousands of
consecutive runs through the leaky shape all succeed. A "hammer it until it breaks" RED is a wasted
build; the isClosed() observation is the settlement.

THE ONE SHAPE THAT NEEDS MORE THAN A TRY-WITH-RESOURCES is a method that creates a Statement and
returns its ResultSet, or that works on a Connection the caller owns: the resource is meant to
outlive the method, so the fix is to give the Statement the caller's lifetime, not to close it before
the result is read. The green there can be a driver accident — some drivers leave the escaped
ResultSet open and navigable after its Statement closes, and the same code throws on a driver that
streams — so a passing test is not evidence the JDBC contract was honoured.

WHAT GOES WRONG HERE. Fixing the SQL instead of the leak: the flagged line often concatenates input
into the query, and binding parameters there changes what the program does; the ODR fix closes a
resource and leaves the query string byte-identical. The inverse is equally wrong — "this code is
insecure on purpose, so the leak is on purpose too" — because no intended behaviour is delivered by
never closing a handle. Then there is asserting the marker back at itself: a test that greps the
source for "try (", or re-runs the analyser and asserts the line is gone, observes no program at all.
And "the Connection is in try-with-resources, therefore nothing leaks" is true about the eventual
outcome and irrelevant to the claim, which is about what THIS method closes.
