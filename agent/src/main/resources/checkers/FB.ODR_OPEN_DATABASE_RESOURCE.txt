\.(getConnection|createStatement|prepareStatement|prepareCall|executeQuery)\s*\(
ODR_OPEN_DATABASE_RESOURCE says the method obtained a JDBC resource — a Statement from Connection.createStatement/prepareStatement/prepareCall, or the ResultSet from executeQuery — kept it local (not returned, not stored in a field, not handed to another object), and has no path out of the method on which close() is reached. The marker's line is the *acquisition* call, because an omission has no line of its own: do not read it as a complaint about the SQL string that is usually concatenated on that same line (that is a SQL-injection checker), and do not read it as a complaint about the Connection, which at nearly every site in this repository is already inside a try-with-resources while the Statement born from it is not. The sibling ODR_OPEN_DATABASE_RESOURCE_EXCEPTION_PATH means "closed on the normal path but not when an exception unwinds"; the plain form flagged here means closed on no path at all.

HOW YOU MAKE IT VISIBLE.
The observable is the state of the JDBC object the flagged line produced, sampled after the method under test returns. That works here only because of a driver fact worth stating precisely, since the obvious objection ("the Connection is closed, so its Statements are closed too") is what stops agents from building anything: I measured HSQLDB 2.7.3 (the version this pom resolves) and it does NOT flip Statement.isClosed() when the owning Connection closes — the server-side handle dies (reusing the statement throws "connection exception: closed") but the client object still reports isClosed()==false. So the flag distinguishes "this method closed it" from "the connection took it down with it", which is exactly the distinction the checker is making.

Measured RED->GREEN on a verbatim copy of Assignment5.login's body (lines 42-57) against a real jdbc:hsqldb:mem database: as written, the PreparedStatement reported isClosed()==false after the method returned, so the assertion fails. With the only edit being try-with-resources around the statement and result set, isClosed()==true and it passes. In both runs the injection payload still solved the lesson, which is the guard that the fix stayed on the leak.

Getting a handle on the resource: LessonDataSource (src/main/java/org/owasp/webgoat/container/LessonDataSource.java) is a plain class with a public constructor taking a javax.sql.DataSource, and it already returns each Connection as a java.lang.reflect.Proxy — so a test does the same one level down. Build a DataSource whose getConnection() returns a Proxy over a real HSQLDB Connection with an InvocationHandler that delegates and appends every returned value that is `instanceof Statement` or `instanceof ResultSet` to a list; wrap it as `new LessonDataSource(recording)` and pass that to the endpoint's constructor. Unwrap InvocationTargetException in the handler the way LessonConnectionInvocationHandler.invoke does at lines 36-37, or SQLExceptions the lesson code catches arrive as UndeclaredThrowableException and the behaviour under test changes. Then assert the recorded list is non-empty *first*, then that every element isClosed(). Most endpoints take LessonDataSource on a public constructor (SqlInjectionLesson2:36, SqlInjectionChallenge:43, SqlInjectionLesson9:38, ...). JWTHeaderKIDEndpoint's constructor is private (line 44) — use setAccessible(true), or drive it through the Spring context the way src/test/java/org/owasp/webgoat/container/plugins/LessonTest.java does.

Assert Statement and ResultSet separately. Measured: closing a Statement does not make its ResultSet report closed on HSQLDB either, and the ResultSet stays fully navigable afterwards. A ResultSet-level marker therefore only goes green if the ResultSet is closed explicitly; ResultSet state is never evidence about the Statement.

What you cannot do, and should not spend a build discovering: there is no application-level malfunction to exhibit. DatabaseConfiguration.dataSource() (line 31) returns a DriverManagerDataSource — no pool — so every getConnection() opens a fresh physical connection and closing it reclaims whatever the method leaked. I ran 5000 consecutive calls through the leaky shape: all 5000 succeeded, no exception, no exhaustion. Do not build a "hammer it until it breaks" RED, do not look for a pool to shrink, and do not reach for a leak-detection agent; the settlement for this family is the isClosed() observation above, and it is a real one.

The one shape that needs more than a try-with-resources: SqlInjectionLesson9.getEmployeesDataOrderBySalaryDesc (lines 116-117) creates a Statement and returns its ResultSet, so the resource is meant to outlive the method; likewise SqlInjectionLesson8.log and SqlInjectionLesson9.getSqlInt operate on a Connection the caller owns. There the fix is to give the Statement the caller's lifetime (create it in the caller's try-with-resources and pass it down), not to close it before the ResultSet is read.

WHAT GOES WRONG HERE.
Fixing the SQL instead of the leak. Assignment5:44 and JWTHeaderKIDEndpoint:74-76 both concatenate user input into the query on the flagged line, and that concatenation is the assignment. src/it/.../ChallengeIntegrationTest.testChallenge5 posts password_login=`1' or '1'='1` and asserts a flag comes back; JWTLessonIntegrationTest.deleteTomThroughKidClaim posts kid=`hacked' UNION select 'deletingTom' from INFORMATION_SCHEMA.SYSTEM_USERS --` and asserts lessonCompleted. Binding parameters turns both to failures. The ODR fix closes a resource and does not touch the query string — and note that SqlInjectionLesson13:46 and Servers:50 are the *mitigation* lesson written with bound parameters, so making an injectable lesson resemble them erases the contrast the course is built on.

The inverse verdict is equally wrong: "WebGoat is deliberately vulnerable, so this is intentional." No assignment in this repository is solved by exhausting database resources, and the same leak sits in ordinary code and in the test tree — SqlInjectionLesson5Test.java:25-28 opens a Connection and a PreparedStatement in an @AfterEach and closes neither.

Asserting the marker back at itself: a test that greps the source for "try (", or that re-runs the analyser and asserts the line is no longer reported. Neither observes the program.

The vacuous green: calling allMatch(Statement::isClosed) on a recorder list that stayed empty because the code path never ran (a lesson method that returned early on a validation branch, or a mocked DataSource that never handed out a real statement). Assert the list is non-empty before asserting anything about its contents.

The green that is a driver accident: concluding a try-with-resources around SqlInjectionLesson9:116's Statement is safe because the lesson test still passes. It passes because HSQLDB leaves the escaped ResultSet open and navigable after its Statement closes — measured. That code returns the ResultSet and SqlInjectionLesson8.generateTable then calls results.beforeFirst() on it; on a driver that streams, that throws. A passing HSQLDB test is not evidence the JDBC contract was honoured.

The reasoning that sounds like a settlement and is not: "the Connection is in try-with-resources, therefore nothing leaks." True about the eventual outcome and irrelevant to the claim; the checker asserts what *this method* closes, and the measured client-side state says it closed nothing.
