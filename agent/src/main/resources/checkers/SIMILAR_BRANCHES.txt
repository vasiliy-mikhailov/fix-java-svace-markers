(?:\belse\b|\bif\s*\(|\bcatch\s*\()|^\s*(?:&&|\|\|)|\?[^?:"']{1,60}:[^:]
Two branches of one `if / else if / else` chain, or the two arms of a ternary, have bodies that are
textually the same or differ by a single token — the shape a copy-paste slip leaves behind. It is a
claim about the BODIES, never about the condition printed on the flagged line; the reported line is
only where a branch of the chain begins, which is why the anchor can land on a null check or on a
bare `&&` or `||` continuation of an `else if`. Expand from the flagged line outward to the whole
chain before judging anything. Do not confuse it with the neighbouring finding for duplicated
CONDITIONS (`if (a) … else if (a) …`), which makes a branch unreachable and is a real defect; here
the conditions are distinct and only the outcomes coincide.

USUALLY YOU CANNOT MAKE THIS VISIBLE, and the reason is definitional: identical bodies produce
identical observable behaviour, so no assertion can tell which one ran. Confirm it by diffing the
bodies rather than assuming, then refute the marker with that as the stated reason — two
independent, legitimate conditions leading to one documented outcome. Not "style only".

That both branches are separately reachable is not a counter-argument. Arranging each condition
gives you two tests carrying the same assertion and there is no third thing to assert. Coverage can
separate such branches; assertions cannot, and only an assertion settles a marker.

WHEN THIS FAMILY IS PROVABLE: the checker says SIMILAR, not IDENTICAL. If the bodies differ by
exactly one token — `left` where `right` was meant, `[i]` where `[j]` was meant, one message key
reused for two conditions — then the mistyped branch has an intended output and the RED is real:
arrange the second condition, assert the value that branch should have produced, watch it fail on
the copied value and pass after the fix. The evidence that they were meant to differ must come from
outside the branch — a sibling method, a message key, javadoc, a symmetric case in the same chain —
never from you deciding they ought to differ.

If you do collapse the branches, a test over them is a GREEN-before / GREEN-after regression check,
not a proof of defect. The merge itself is where a defect can be introduced: fusing an `else if` into
a single `||` reorders short-circuit evaluation, so a null guard that used to run first can end up
behind the dereference it was guarding.

WHAT GOES WRONG HERE.
- Reading only the flagged line and reconstructing a different checker from it. A null test reads
  like input validation and a `!= null` continuation reads like a dereference guard, but both are
  conditions, and this checker never complains about a condition.
- Manufacturing the difference to justify a RED: changing one branch's status code or message and
  then asserting the new value. That test only asserts the edit you just made. Check whether
  anything outside the chain asks the two outcomes to differ before deciding they do.
- Offering branch coverage, a log line, or "the two tests exercise different paths" as the failing
  observation; or presenting a still-passing test after the collapse as proof.
- Reaching for what the file is for as the refutation. A reason that works in a file with a purpose
  to protect but not in ordinary infrastructure carrying the identical construct is the wrong
  reason; the same chain gets the same verdict in both places.
