The checker asserts that a statement can never execute and that the reason is exception flow: on every path the analyzer traced, no exception of the caught type escapes the guarded block, so the catch handler is never entered. What identifies the family is the anchor — the flagged line is the *first statement inside a catch handler* (here `fail("Signing failed");` at CryptoUtilTest.java:32, the sole statement of the `catch (Exception e)` opened on line 31). Do not confuse this with plain unreachable-code-after-a-throw, which anchors on the statement *following* an unconditional `throw` or an always-throwing call; if the flagged line is itself the last statement of its block, that reading has nothing to point at and the claim must be about the handler. The regex is a screen, not the test — it hits handler clauses and the usual handler-body first statements (fail / throw new / printStackTrace); the deciding check is where the line sits, so open it.

HOW YOU MAKE IT VISIBLE.
Refuse the reflex answer first. The reflex is "unreachable code executes nothing, so nothing can observe it, so the marker is unprovable." That is reasoning about the analyzer's traced paths, not about the JVM, and it is wrong far more often than right. The marker makes a falsifiable claim — *this handler never runs* — and running it once settles the marker outright. So the question is never "how do I observe dead code" but "can I enter the handler?"

To enter a Java catch handler: pick a guarded call whose exception has a runtime-controllable trigger, arrange it, invoke. Levers that actually exist — the JCA provider set is mutable at runtime, so any `X.getInstance("ALG")` can be made to throw NoSuchAlgorithmException; filesystem/classpath state, for IOException (the sibling repro at src/test/java/org/owasp/webgoat/integration/LabelAndHintPropertiesNullDerefTest.java:56 uses a locale with no bundle); malformed input for parser/decoder exceptions; and, when the deciding property is read once at start-up, a test that starts a second JVM.

At this site it works, and I ran it. `testSigningAssignment` guards `CryptoUtil.generateKeyPair()`, whose first act is `KeyPairGenerator.getInstance("RSA")` (CryptoUtil.java:39). Enumerate providers with `getService("KeyPairGenerator","RSA") != null` (on OpenJDK 26 that was exactly one, SunRsaSign — enumerate, don't hardcode the name), note its 1-based index, then `Security.removeProvider(name)`. `getInstance("RSA")` then throws `NoSuchAlgorithmException: RSA KeyPairGenerator not available`, the handler runs, and the method throws `AssertionError: Signing failed` with `getCause() == null`. Restore with `Security.insertProviderAt(p, pos)` in a finally — `addProvider` appends and silently reorders provider precedence for every later test in the same surefire fork. So the handler is reachable and the marker's premise is false as stated.

But do not make "the handler ran" the assertion: it does not survive the repair. The repair is to stop catching — declare `throws Exception` on the test method; javac requires the handler today only because `generateKeyPair` (CryptoUtil.java:37-38) and `getPrivateKeyFromPEM` (135-136) declare checked exceptions — after which there is no handler left for such an assertion to mean anything. Assert instead on what the handler destroys. Under the arrangement above the developer sees "Signing failed" and nothing else; the exception naming the missing algorithm is gone. Write a separate repro that arranges the provider removal, reflectively invokes `testSigningAssignment()`, unwraps `InvocationTargetException.getCause()`, and fails when the observed Throwable is an AssertionError with a null cause. Inverse-assertion shape: any repair that lets the real exception through (dropping the catch, `fail(msg, e)`, `assertThatNoException()`) turns it GREEN without the test naming one particular fix. Catch `Throwable`, not `Exception` — AssertJ's `fail(String)` throws `java.lang.AssertionError`, an Error (verified against assertj-core 3.27.7: message "Signing failed", cause null, `instanceof Exception` false).

The honest other half: when the guarded block genuinely contains nothing that can throw the caught type — a `catch (Exception e)` wrapped around field reads and arithmetic — the handler really is dead, no arrangement enters it, and no JUnit test can distinguish the file from the same file with the handler deleted. Say that plainly and settle it structurally: list the guarded calls and their `throws` clauses (or absence) and show the caught type has no source. Do not manufacture a RED by editing the guarded code to throw; that tests your edit, not the marker.
