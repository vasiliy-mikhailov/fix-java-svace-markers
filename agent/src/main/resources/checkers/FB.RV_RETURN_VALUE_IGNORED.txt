^\s*[A-Za-z_$][A-Za-z0-9_$]*(?:\.[A-Za-z_$][A-Za-z0-9_$]*)+\s*\(.*\)\s*;\s*$
The checker asserts that a whole statement is nothing but a method call whose returned value is dropped: the value is not assigned, returned, passed on, or tested. The identical-looking neighbour is a call to a void method — same shape exactly, but there is no value to ignore and this checker has nothing to say about it. The second neighbour, often confused with it, is the resource-leak family, which complains that a returned object is never *closed* rather than never *read*. Formatter-wrapped source supplies a third look-alike: a continuation line can look like a bare call when it is really the tail of an assignment, so check the preceding line for a trailing `=` before believing anything was discarded.

HOW YOU MAKE IT VISIBLE.
Open the callee's signature and decide which of three things the dropped value IS. The method name will not tell you, and the provability is completely different in each case.

(1) The call has no side effect and the value is its only product — `s.trim();`, `bd.add(x);`, a stream pipeline with no terminal op. The statement is a no-op. Fully provable and easy: arrange an input where the transformed value differs from the input, exercise the caller, and assert the caller observes the *untransformed* one. RED before, GREEN once the result is consumed.

(2) The value is a status and the work really happened — `File.mkdirs()`, `delete()`, `createNewFile()`, `renameTo()`, `InputStream.read(byte[])`, `latch.await(t,u)`, `queue.offer(x)`. No boolean is stored anywhere, so no assertion can reach it directly; you must arrange the *failure* and assert a downstream consequence. Two questions decide whether that consequence exists: does the very next statement redo the same work through an API that throws, so the caller already learns of the failure, and does any code path actually READ the state the failed call left wrong. A status return is demonstrable only where failure is silent AND a later reader is misled by it — verify both.

(3) The value is data and the side effect is the point — a query run for what it changes with the rows dropped, a call made for its registration or its logging. Ask what binding the value would change. Where the work happens either way, the same state is left behind, the same result reaches the caller and the same resources are released at the same moment, the difference between dropping and storing is one bytecode and there is no state, output, timing or resource count for an assertion to attach to. Record that as not provable, with the reason, rather than manufacturing a test.

WHAT GOES WRONG HERE.
Asserting the marker back at itself: mocking the collaborator so the flagged call returns a stub, then verifying the stub was never touched. It goes RED before and GREEN after, but it only restates the syntax of the line — it passes just as happily for a version that stores the value and immediately drops it, and it can never fail for anything a user observes.

The silent fix: consuming the value without acting on it — `boolean ok = f.delete();`, `var unused = ...`, `if (!dir.mkdirs()) log.warn(...)`. The checker goes quiet and every behavioural test stays where it was, because nothing changed. If your RED only turns GREEN when the code throws or retries, that is a behaviour change to justify on its own merits, not something the marker asked for.

Reasoning from a specification instead of from the implementation the build resolves: "this method throws on failure, so the call lands in the catch." Drivers, filesystems and library versions differ, and a call executed for its effect may quietly return an empty result rather than throwing, so the RED fails for a reason unrelated to the marker. Sliding into the leak story is the neighbouring mistake: an assertion about an unclosed resource is a different checker, and where the owner is already in try-with-resources there is nothing to count.

Verdict words: "the returned value is discarded" is a fact about the text, not evidence of a defect — concluding "confirmed" from it, without naming the observation an assertion would make, proves nothing. Its mirror is equally wrong: what the surrounding code is FOR — the reputation of the package it sits in, the sensitivity or the triviality of the operation being invoked — says nothing about this checker, which is about the dropped value and not about what the call does. Note also that an edit stopping the flagged call from executing as written can break tests that depend on the surrounding behaviour; the marker asks only about the value.
