^\s*[A-Za-z_$][A-Za-z0-9_$]*(?:\.[A-Za-z_$][A-Za-z0-9_$]*)+\s*\(.*\)\s*;\s*$
The checker asserts that a whole statement is nothing but a method call whose returned value is dropped: the value is not assigned, returned, passed on, or tested. The identical-looking neighbour is a call to a void method — `stmt.setString(1, "GRANT_RIGHTS");` on line 85 of the same file has exactly this shape, but there is no value to ignore and this checker has nothing to say about it; the second neighbour, often confused with it, is the resource-leak family, which complains that a returned object is never *closed* rather than never *read*. This repo is google-java-format wrapped, so a continuation line can look like a bare call (SqlInjectionLesson3.java:49 is the tail of an assignment that began on line 48) — check the preceding line for a trailing `=` before believing anything was discarded.

HOW YOU MAKE IT VISIBLE.
Open the callee's signature and decide which of three things the dropped value IS. The method name will not tell you; the provability verdict is completely different in each case.

(1) The call has no side effect and the value is its only product — `s.trim();`, `bd.add(x);`, a stream pipeline with no terminal op. The statement is a no-op. Fully provable and easy: arrange an input where the transformed value differs from the input, exercise the caller, and assert the caller observes the *untransformed* one. RED before, GREEN once the result is consumed.

(2) The value is a status and the work really happened — `File.mkdirs()`, `delete()`, `createNewFile()`, `renameTo()`, `InputStream.read(byte[])`, `latch.await(t,u)`, `queue.offer(x)`. There is no boolean stored anywhere, so no assertion can reach it. You must arrange the *failure* and assert a downstream consequence: e.g. for `destinationDir.mkdirs();` at src/main/java/org/owasp/webgoat/webwolf/FileServer.java:71, put a regular file at that path (or drop write permission on the parent), POST an upload, and assert what the caller gets back. Then apply the discriminating question before writing the test: does the very next line already fail loudly? At FileServer:71 it does — `Files.copy` throws NoSuchFileException — and at ProfileUploadBase.java:52 `FileCopyUtils.copy` creates and truncates the file anyway, so the ignored `createNewFile()` boolean changes nothing an assertion can see. A status-return is only demonstrable where failure is *silent* and wrong state persists, e.g. `changeIndicatorFile.delete();` at FileServer.java:98, whose failure leaves the upload banner showing on the next GET — and even there, read the second trap before claiming it.

(3) The value is data and the side effect is the point — this marker. At src/main/java/org/owasp/webgoat/lessons/sqlinjection/introduction/SqlInjectionLesson5.java:65, `statement.executeQuery(query);` runs the user's SQL and drops the rows. Nothing downstream wants them: success is decided by `checkSolution()` re-querying INFORMATION_SCHEMA.TABLE_PRIVILEGES at line 87, and the failure path echoes only the query text. I ran the real driver this build resolves (hsqldb 2.7.3): `executeQuery("grant select on grant_rights to unauthorized_user")` does NOT throw, it returns an empty ResultSet, the grant lands (the INFORMATION_SCHEMA row appears), and the ResultSet is still navigable after its Statement is closed. So `ResultSet rs = statement.executeQuery(query);` with `rs` unused — or closed — is observationally identical: same rows in the DB, same AttackResult, same resources released at the same moment. There is no state, output, timing, or resource count for a JUnit assertion to attach to. The honest settlement for this marker is NOT PROVABLE, stated with the reason — the value has no consumer and the side effect occurs either way — rather than a manufactured test.

One WebGoat-specific constraint on case (3): line 65 is the injection point of the lesson; SqlInjectionLesson5Test.grantSolution (src/test/java/.../SqlInjectionLesson5Test.java:36) posts raw SQL and asserts lessonCompleted=true. RV says nothing about injection, so "the vulnerability is intentional" is not an answer to this marker — but any edit that stops `query` executing verbatim breaks that shipped test. The same construct at FileServer.java:71/98, MvcConfiguration.java:50 and Salaries.java:44 is ordinary infrastructure and gets judged purely on whether the dropped value is observable.

WHAT GOES WRONG HERE.
Asserting the marker back at itself: spying the Connection so `executeQuery` returns a Mockito ResultSet and then `verifyNoInteractions(resultSet)` or `verify(rs, never()).close()`. It goes RED before and GREEN after, but it only restates the syntax of line 65 — it passes just as happily for `ResultSet rs = statement.executeQuery(query); rs.close();`, which still ignores the data, and it can never fail for anything a user observes. That is not a demonstration.

The silent fix: consuming the value without acting on it — `boolean ok = f.delete();`, `var unused = ...`, `if (!dir.mkdirs()) log.warn(...)`. The checker goes quiet and every behavioural test stays exactly where it was, because nothing changed. If your RED only turns GREEN when the code throws or retries, that is a behaviour change you have to justify on its own merits, not something the marker asked for.

Reasoning from the JDBC spec instead of running the driver: "executeQuery on a non-SELECT throws SQLException, so line 65 lands in the catch on line 71." It does not on HSQLDB — I executed it. A RED built on that belief fails for the wrong reason, which is the same failure as the COMMAND_INJECTION `;` payload.

Sliding into the leak story: writing an assertion about the unclosed ResultSet. The Statement at lines 62-64 is already in try-with-resources, and HSQLDB returns a materialised result that stays navigable after the Statement closes, so there is no cursor to count and no leak to observe.

Verdict words: "the returned value is discarded" is a fact about the text, not evidence of a defect — concluding "confirmed" from it, without naming the observation an assertion would make, proves nothing. Its mirror is equally wrong: this file is a deliberately vulnerable lesson, but the dropped ResultSet is not the lesson; it is simply unobservable, and that is the reason to record.
