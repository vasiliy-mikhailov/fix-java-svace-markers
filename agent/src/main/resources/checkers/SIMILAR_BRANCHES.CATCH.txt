catch\s*\(\s*(?:final\s+)?[\w.]+(?:\s*\|\s*[\w.]+)*\s+\w+\s*\)
Two (or more) catch clauses of the SAME try statement have handler bodies that are identical after whitespace normalization; the marker is anchored on one clause of the pair — at the flagged site, the first and most specific one. The claim is only "these two handlers do the same thing": either the specific clause is dead weight subsumed by the broader one, or one body is a copy-paste that is false for its own exception. Do not confuse it with SIMILAR_BRANCHES (identical if/else bodies) or SIMILAR_BRANCHES.SWITCH (identical case bodies), and do not confuse it with the empty-catch / over-broad-catch family (REC_CATCH_EXCEPTION, DE_MIGHT_IGNORE, "exception swallowed"), which judges what a single handler does or fails to do rather than the duplication between two; nor is it "unreachable catch", since specific-before-general compiles fine and is exactly the shape that gets flagged.

HOW YOU MAKE IT VISIBLE.
FIRST FIND THE PAIR. The marker names one clause; the finding lives in the whole try. Read every catch of that try and compare normalized bodies — the twins need not be adjacent. At InsecureDeserializationTask.java:53, `catch (InvalidClassException e)` and `catch (Exception e)` at :57 both hold exactly `return failed(this).feedback("insecure-deserialization.invalidversion").build();`, with a differently-bodied `catch (IllegalArgumentException e)` (:55, "expired") sitting between them. A scan of all 112 catch clauses in src finds this one pair, so read the family shape off this instance rather than off the count.

THEN DECIDE WHICH OF TWO SETTLEMENTS YOU ARE IN, because only one is testable.
(a) Honest redundancy — both handlers really do mean the same thing. Then every available fix (delete the subsumed specific clause; fold siblings into `catch (A | B e)`) is behaviour-preserving by construction, and NO JUnit test can separate before from after. Say that plainly and settle it as redundancy; do not manufacture a RED.
(b) One body is false for its own branch — the shared text asserts something true of only one of the exceptions. That IS observable, through whatever the body emits: a return value, a message key, a log line, an HTTP status.

This marker is (b), and the observation needs no new machinery. `DeserializeTest extends LessonTest` (Spring Boot + MockMvc, with `messages` for key lookup) already POSTs `/InsecureDeserialization/task` and asserts `jsonPath("$.feedback")` against `messages.getMessage("insecure-deserialization.<key>")`. Arrange two tokens that take different clauses of this try:
  - the existing `wrongVersion` token (stream carries serialVersionUID 1, `VulnerableTaskHolder` declares 2) -> InvalidClassException -> :53;
  - a token that is LEGAL base64 of non-serialized bytes, e.g. `Base64.getEncoder().withoutPadding().encodeToString("this is not a serialized stream".getBytes())` -> the `new ObjectInputStream(...)` in the try-with-resources resource clause throws `StreamCorruptedException: invalid stream header` (I ran this on this JDK) -> :57.
Assert the two `$.feedback` values DIFFER — or that the second is not `insecure-deserialization.invalidversion`, whose text is "The serialization id does not match. Probably the version has been updated." Today both come back identical: RED, and RED for the right reason, since no serialization id was ever compared on the second token. It goes GREEN when the broad handler gets its own message key. `wrongVersion` stays GREEN because the specific clause survives — the fix direction the anchor line does NOT suggest.

Constraints the fix must respect: the InvalidClassException -> invalidversion mapping is lesson content (hint 2 tells the student the class "might have been updated with a next version number") and is asserted by DeserializeTest.wrongVersion, so leave it alone; and the broad `catch (Exception e)` must stay, because it is what turns a corrupt token into a graceful failed AttackResult instead of a 500 out of the controller. The taught vulnerability in this file is the unguarded `ois.readObject()` on attacker bytes (with `Runtime.getRuntime().exec` inside VulnerableTaskHolder.readObject); the handler bodies teach nothing and are ordinary controller code.

WHAT GOES WRONG HERE.
- Asserting the marker back at itself: a test that POSTs the wrongVersion token and asserts "invalidversion" is green before AND after every candidate fix (the twin returns the same string), so it witnesses nothing. Same for anything that reads the .java text or counts catch clauses reflectively.
- Claiming RED/GREEN for the merge. Deleting `catch (InvalidClassException e)` at :53 leaves observable behaviour bit-identical; any test passing after also passed before. If that is the fix you choose, the correct write-up is "not observable", not a fabricated RED.
- Wrong probe: a non-base64 token throws IllegalArgumentException inside `Base64.getDecoder().decode` and lands on the THIRD clause (:55, "expired"), which is not part of the duplicate pair — that RED would be for the wrong reason. The probe token must decode cleanly and only then fail as a stream.
- "It is WebGoat, therefore intentional" — the lesson is readObject on untrusted bytes, not duplicated handler bodies. The mirror error is as bad: rewriting both messages collides with hint 2 and DeserializeTest.wrongVersion.
- Escalating the fix into a rethrow, or dropping `catch (Exception e)`, converts junk input into HTTP 500 and breaks the assignment endpoint.
- Assuming the twins are adjacent, or that "similar" means "same exception type": here a differently-bodied clause separates them, and the pair is a subtype plus its supertype.
- Verdict slip: "the bodies are identical" is confirmed by reading, and "the specific clause is therefore dead" follows — but neither "so nothing is wrong" nor "so a defect is observable" follows. What decides it is whether the shared body is a true statement about BOTH exceptions.
