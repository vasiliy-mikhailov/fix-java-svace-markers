^\s*(?:[\w$]+\.)*[\w$]+\.(?:(?:mkdirs?|createNewFile|delete)\s*\(\s*\)|(?:renameTo|setReadable|setWritable|setExecutable|setReadOnly|setLastModified)\s*\([^;]*\))\s*;\s*$
A statement-position call to a JDK method that performs a side effect and reports success or failure ONLY through its return value, with that value discarded — in practice a `java.io.File` mutator (`mkdir`, `mkdirs`, `createNewFile`, `delete`, `renameTo`, the `set*` permission methods). These methods do not throw on failure, so the dropped boolean is the entire failure channel. Do not confuse this with RV_RETURN_VALUE_IGNORED / RV_RETURN_VALUE_IGNORED_NO_SIDE_EFFECT, which flag calls that have NO side effect (`s.trim();`, `bd.add(x);`) and where the whole statement is therefore a no-op — here the call may well have done its work, and the only question is whether it did. The roster of watched methods is fixed, so an equally discarded boolean from a library helper a few lines below a flagged line is not this marker.

HOW YOU MAKE IT VISIBLE.
FORCING THE FAILURE is the part agents get wrong. The reflex is `parent.setWritable(false)`; it works on a developer laptop, but a JVM running as root — which containerised CI usually is — ignores permission bits, and on Windows it does not block directory creation. The RED then passes because the directory got created, which is meaningless. Put a REGULAR FILE where a directory is expected instead: `mkdir`/`mkdirs` whose parent path is a plain file return false regardless of uid, `mkdir`/`mkdirs` on an existing directory return false, `createNewFile` on a path that is an existing directory returns false without throwing, and `delete` on an absent file or a non-empty directory returns false. `createNewFile` with a missing or non-directory parent THROWS IOException, so there you would be testing the exception path rather than the ignored boolean.

Feed the blocked path in through whatever the class exposes — constructor argument, injected field, configuration property. Two arrangement traps: a call guarded by `if (!f.exists())` is SKIPPED when a regular file occupies that path, so block one level up and let the code try to build the child; and confirm the flagged line is reached at all, because if an earlier statement throws under your arrangement a green `assertThrows` proves nothing about the marker.

WHAT TO ASSERT. Sites split three ways, and the split decides whether a RED exists at all.

DEMONSTRABLE: nothing downstream re-attempts the operation through an API that reaches the caller, so the method returns normally with its postcondition unmet and no caller ever learns. The failing observation is that the caller is NOT told — `assertThrows` around the call, RED because nothing is thrown, GREEN once the return is checked and turned into a reported failure. Do NOT assert the postcondition (`assertTrue(dir.isDirectory())`): checking a return value does not create a directory, so that assertion stays red after the correct fix, i.e. it fails for a reason the fix does not address. Where the silent failure also leaves visible harm — state that should have been persisted is missing, the only trace a log line — assert both halves. Before prescribing a throw, check the blast radius: if the method runs on every login or every request, an escaping exception breaks far more than it fixes. Fail fast only where the caller can absorb it, such as start-up wiring; elsewhere surface the failure through the method's own result and match the assertion to that.

MASKED: the very next statement redoes the same work through an API that DOES throw, so the failure already reaches the caller and only its attribution is wrong. `assertThrows` is GREEN before AND after the fix — a tautology dressed as a RED. Only the wording or type of the exception separates fixed from unfixed, and asserting on wording is a diagnostics preference, not evidence of a defect. Settle these as real but not demonstrable. Identify the first throwing statement precisely rather than guessing: an argument expression is evaluated before the call it is passed to, so the thrower is often not the line you expected.

NOT A DEFECT AS WRITTEN: the call returns false exactly when its postcondition is already satisfied, or the next line does the work unconditionally. A `delete` of a path nothing ever creates returns false on every call with the file already absent; a `createNewFile` whose successor creates and truncates the file regardless carries a boolean no code could act on. That is redundancy, not an unchecked failure, and no arrangement yields a RED that a defensible fix turns green. Defensible edits keep false-on-absent silent — `Files.deleteIfExists`, whose false is documented as "did not exist", or moving the call inside an existing `exists()` guard — or delete the redundant call. Turning that false into a throw or early return changes behaviour and can turn shipped tests red.

WHAT GOES WRONG HERE.
Asserting the marker back at itself: pre-create the directory, then `assertFalse(dir.mkdir())`. It really does return false, but the desired state holds, so nothing is wrong; `assertFalse(absent.delete())` is the same trap. A false return is evidence only when the postcondition is genuinely unmet.

Verdict words that do not follow: "the directory always exists in practice" argues that the false branch is unreachable, not that the return is checked, and "the next line throws anyway" is true only at masked sites — asserting it at a silent one is simply false, and the silent ones are where a real RED lives. Switching `mkdir()` to `mkdirs()`, or reordering the surrounding statements, changes behaviour and leaves the return discarded.

Intent, scoped correctly: an ignored boolean is never itself a designed feature, but the method around it can be behaviour-sensitive, and an edit that changes whether or where the write happens breaks something the marker never asked you to touch.
