^\s*(?:[\w$]+\.)*[\w$]+\.(?:(?:mkdirs?|createNewFile|delete)\s*\(\s*\)|(?:renameTo|setReadable|setWritable|setExecutable|setReadOnly|setLastModified)\s*\([^;]*\))\s*;\s*$
A statement-position call to a JDK method that performs a side effect and reports success or failure ONLY through its return value, with that value discarded — in this queue always a java.io.File mutator (`mkdir`, `mkdirs`, `createNewFile`, `delete`). These methods do not throw on failure, so the dropped boolean is the entire failure channel. Do not confuse this with RV_RETURN_VALUE_IGNORED / RV_RETURN_VALUE_IGNORED_NO_SIDE_EFFECT, which flag calls that have NO side effect (`s.trim();`, `bd.add(x);`) and where the whole statement is therefore a no-op — here the call may well have done its work, and the only question is whether it did. The roster of watched methods is fixed, which is why `FileSystemUtils.deleteRecursively(uploadDirectory);` at ProfileUploadBase.java:72 — a discarded boolean twenty lines below a flagged line, in a flagged file — is not in this queue.

HOW YOU MAKE IT VISIBLE.
FORCING THE FAILURE (the part agents get wrong). The reflex is `parent.setWritable(false)`; it works on a developer laptop but a root JVM — containerised CI, which this project's own build uses — ignores permission bits, and on Windows it does not block directory creation. The RED then passes for the wrong reason: the directory gets created and the assertion is meaningless. Use a REGULAR FILE as the parent instead. WHAT GOES WRONG HERE.
1. Asserting the marker back at itself: pre-create the directory, then `assertFalse(dir.mkdir())`. It really does return false (verified) — but the desired state holds, so nothing is wrong; the same trap is `assertFalse(absent.delete())`. A false return is evidence only when the postcondition is genuinely unmet.

2. FileServer.java:98 — the fix that breaks production. Nothing in this repository ever creates `<username>_changed`; grep across the sources finds exactly one other occurrence, line 94, which is the read. So `changeIndicatorFile.delete()` returns false on EVERY request to `/files`. The defensible edits are `Files.deleteIfExists(...)` (whose false is documented as "did not exist") or moving the delete inside the existing `if (changeIndicatorFile.exists())` block — both keep false-on-absent silent, which is what the code means.
