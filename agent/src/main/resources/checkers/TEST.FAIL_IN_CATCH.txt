(?:\w+\.)?\bfail\s*\(\s*(?:"[^"]*"\s*)?\)\s*;
The flagged line is a call to JUnit/AssertJ `fail(...)` inside a `catch` block that does not pass the caught exception on: the test converts a thrown Throwable into a failure carrying no reference to it. The marker points at the `fail()` line, not the `catch` line, and the regex can only locate the argument-less or message-only form — so read upward and confirm there is an enclosing catch, because a bare `fail()` on a normal path is a different construct. `fail(e)` and `fail("context", e)` are the repaired forms and deliberately do not match; `fail("some message")` inside a catch is the same family with a partial mitigation, naming the failure but still dropping the cause.

HOW YOU MAKE IT VISIBLE.
WHAT YOU ASSERT ON IS THE THROWABLE THE TEST HANDS THE FRAMEWORK, not pass or fail — the test fails either way; the defect is that the failure is empty. `Assertions.fail()` throws `org.opentest4j.AssertionFailedError` whose `getCause()` is null and whose `getMessage()` is the EMPTY STRING, not null (true across Jupiter 5.x and 6.x, opentest4j 1.2 and 1.3). An assertion on message nullness therefore passes on the defective code and reports "no defect". Assert on `getCause()`, or on the message containing the caught exception's text. `fail(e)` still leaves the message empty; only the cause changes.

PHRASE IT AS "the original failure is recoverable from what was thrown" — from the Throwable itself or its cause. Pinning the assertion to `AssertionFailedError` pins the defective shape: a legitimate repair may delete the try/catch and declare the method `throws`, after which the original exception propagates unwrapped and an over-tight demonstration goes red on the fix. JUnit 5 test methods may declare checked exceptions, so that repair is available.

THE HARD PART IS REACHING THE CATCH, and that is where this marker is won or lost. The guarded code is usually reachable only through a method you cannot call directly, so you must enter through the try: instantiate the class reflectively and drive its entry point, set the fields it needs with `setAccessible`, stand up an in-process stub for whatever it talks to at the address the class resolves by default, and — when the guard names a specific exception type — replace the throwing method with a static mock that throws exactly that. Static mocking needs the INLINE MOCK MAKER: mockito-core 5.x selects it by default, so `mockStatic` works with nothing added to the build; on 4.x and earlier, or wherever the subclass mock maker is in force, the same call fails with "static mocking is not supported by the current MockMaker", and the answer is the inline artifact or a `mock-maker-inline` entry in the `org.mockito.plugins.MockMaker` resource — not abandoning the route.

DO NOT SABOTAGE THE PLATFORM to trigger a guard on an exception the runtime "cannot" raise. Removing a security provider does make `MessageDigest.getInstance` throw, but the same removal breaks unrelated machinery — `SecureRandom` construction fails with an internal error — so the run dies before reaching the guard for reasons that have nothing to do with the marker. Replace the throwing method instead; the catch clause only cares about the type. Only when no seam can make the guarded call throw is "same construct, guard unreachable" the honest state, and that is still not "no defect".

Watch the build's own selection rules when naming the demonstration file: test plugins include and exclude classes by name pattern, and a demo matching an excluded pattern silently never runs while reporting success.

WHAT GOES WRONG HERE.
- Copying the try/catch/fail shape into the demonstration and asserting on the copy. That is asserting the marker back at itself; the demonstration must drive the real method on a real instance.
- Claiming "the stack trace is lost". If the catch also prints it, the trace still reaches stderr and the build attaches it to the report. What is lost is the ATTACHMENT: the recorded failure carries an empty message and one frame at the `fail()` line, while the real trace sits unlinked in interleaved output from every test in the fork.
- Claiming the catch "swallows the assertion message". `catch (Exception e)` does not catch `AssertionError`, so assertion failures raised inside the try propagate intact. What this catch converts into an empty failure is infrastructure exceptions — connection refused, malformed input, a bad cast.
- Settling the marker from what the surrounding code is for rather than from the flagged line. This is harness code: nothing depends on how a test reports its own errors, and no documentation, assertion or suppression anywhere asks for a failure that drops its cause. Equally, do not sweep in neighbouring constructs that were not flagged.
