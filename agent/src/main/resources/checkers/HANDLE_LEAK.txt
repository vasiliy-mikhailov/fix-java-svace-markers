(?:new\s+(?:Zip|Jar)File|new\s+File(?:Input|Output)Stream|new\s+(?:Server)?Socket|new\s+Object(?:Input|Output)Stream|new\s+Scanner|new\s+(?:FileReader|FileWriter|InputStreamReader|OutputStreamWriter|PrintWriter|BufferedReader|BufferedWriter)|Runtime\.getRuntime\(\)\.exec|(?:\w|\)|^\s*)\s*\.\s*(?:prepareStatement|prepareCall|createStatement|getConnection|getInputStream|getOutputStream)|Files\.(?:newInputStream|newOutputStream|newBufferedReader|newBufferedWriter|newDirectoryStream|lines|list|walk|find))\s*\(
HANDLE_LEAK flags an expression that acquires a releasable handle — ZipFile/JarFile, a File*Stream, a Socket, a Process, a JDBC Connection/Statement/ResultSet — whose result goes into a plain local or is discarded, with no try-with-resources and no close() on any path out of the method. The neighbouring construct it is constantly mistaken for is a handle that the *callee* closes: `FileCopyUtils.copy(in, new FileOutputStream(f))` matches this regex but is not a leak, because copy() closes the stream in a finally; likewise a Statement created on a Connection that is itself inside try-with-resources is closed for you when that Connection is returned to the pool. The flagged line is the acquisition site, which is not always the line where the handle is actually lost — read the whole method before deciding which of the three tiers below you are in.

HOW YOU MAKE IT VISIBLE.
Three tiers. Decide which one a marker is in BEFORE writing a test, because tier 3 cannot be shown by exhaustion at all and an agent who does not know that will write a RED that passes and blame itself.

TIER 1 — the handle owns an OS file descriptor (ZipFile, File*Stream, Socket, Process pipes). ProfileZipSlip.java:75 is this. Observable, and I measured it on this machine (JDK 26): loop N calls of the leaky shape, sample `((com.sun.management.UnixOperatingSystemMXBean) ManagementFactory.getOperatingSystemMXBean()).getOpenFileDescriptorCount()` before and after. Leaky: N=300 -> delta exactly 300, N=30 -> delta 30. With try-with-resources: delta 0. No Spring needed — ProfileZipSlip has a plain `ProfileZipSlip(String webGoatHomeDirectory)` ctor (ProfileUploadBase:36), so `new ProfileZipSlip(tmp.toString()).uploadFileHandler(new MockMultipartFile("uploadedFileZipSlip","p.zip",null,zipBytes), "tester")` in a loop is the whole harness. Two hard-won details: (a) ZipFile registers a java.lang.ref.Cleaner — I measured one `System.gc()` collapse a 300-fd delta to 0, so never call System.gc(), and never assume a helper does not; (b) natural GC does the same partially under allocation pressure — the same leak measured 114 rather than 200 once Files.copy and byte[] work were in the loop. So assert a threshold (`delta > N/4`, or GREEN `delta <= 5`), never `assertEquals(N, delta)`. Guard the whole test with `Assumptions.assumeTrue(bean instanceof UnixOperatingSystemMXBean)` — there is no Windows equivalent. One more: for ZipFile the fd is one per ZipFile, not one per `zip.getInputStream(entry)` (line 80) — those child streams share the same Source. If both lines are flagged in one file, that is one descriptor, not two.

TIER 2 — the leaked handle is the pooled Connection itself (`dataSource.getConnection().prepareStatement(...)` with nothing closing the Connection; that exact shape is live in the test tree at SqlInjectionLesson5Test.java:26). This is the best RED in the family: deterministic, one second, no GC anywhere. Measured with this repo's own HikariCP 6.3.3 + HSQLDB 2.7.3, `maximumPoolSize=1`, `connectionTimeout=1000`: call 1 succeeds, call 2 throws `SQLTransientConnectionException: HikariPool-1 - Connection is not available, request timed out after 1006ms (total=1, active=1, idle=0, waiting=0)`. With try-with-resources, all calls succeed. `assertThrows(SQLTransientConnectionException.class, ...)` on the second invocation.

TIER 3 — a Statement/ResultSet created on a Connection that IS inside try-with-resources. Assignment5.java:44 is this, and so is most of the SqlInjection lesson tree. There is no harm to observe, and I verified it rather than assuming: with Hikari 6.3.3 + HSQLDB 2.7.3, after the enclosing `conn.close()`, the leaked `PreparedStatement.isClosed()` returns true — the pool closes the statements it handed out when the connection is returned. 100 000 iterations of the exact Assignment5 shape ran in 707 ms with no fd growth, no pool exhaustion, no heap growth. Any exhaustion-style RED here will pass. The only honest observation left is the omission itself: hand the endpoint a DataSource whose Connection is a `java.lang.reflect.Proxy` returning Proxy Statements, and assert `statementsCreated == statementsClosed`. That is wirable without a Spring context — Assignment5 is `@RequiredArgsConstructor` over `LessonDataSource`, and LessonDataSource has a public `LessonDataSource(DataSource)` ctor, so `new Assignment5(new LessonDataSource(countingDs), flags)` compiles. (LessonConnectionInvocationHandler:30 issues an extra SET SCHEMA statement per proxied call, but only when SecurityContextHolder holds a WebGoatUser — empty in a plain unit test — and it closes that one anyway, so it adds no noise.) Say plainly in the finding which claim you are making: that test shows close() was never called, not that anything broke. If the pipeline demands a RED that shows harm, the correct settlement for tier 3 is "real omission, harm bounded by the enclosing try-with-resources on the Connection, not demonstrable by exhaustion" — write that down instead of manufacturing one.

NOT LEAKS (verified, do not file): `FileCopyUtils.copy(in, new FileOutputStream(f))` at Salaries.java:47-49 and ProfileUploadRetrieval.java:64 — I ran both overloads against a FileOutputStream subclass that records close(); `copy(InputStream,OutputStream)` and `copy(byte[],OutputStream)` each closed it. Purely in-memory streams (SerializationHelper.java:22 `new ObjectInputStream(new ByteArrayInputStream(data))`, :31 `new ObjectOutputStream(baos)`) hold no OS handle; fd count is flat closed or not, so there is nothing to exhaust.

LESSON SAFETY, specifically and not as a blanket: the leak is never the lesson here. ProfileZipSlip's assignment is the unnormalized `new File(tmpZipDirectory.toFile(), e.getName())` at line 79 — closing the ZipFile at line 75 leaves that traversal fully intact. Assignment5's assignment is the concatenated SQL at lines 45-49 — try-with-resources around the PreparedStatement changes nothing about the injection. Re-run the existing lesson tests (SqlInjectionLesson9Test, ProfileUploadTest and siblings under src/test) after any fix. On this repo's driver it does not — I ran HSQLDB 2.7.3 with TYPE_SCROLL_SENSITIVE/CONCUR_UPDATABLE and the ResultSet still read fine after its Statement was closed. TIER 1 — the handle owns an OS file descriptor that nothing else releases. In this repo that is ZipFile and File*Stream, NOT Process (see tier 3). ProfileZipSlip.java:75 is the case. PIN THE FIXTURE, NOT JUST THE THRESHOLD. This measurement is destroyed by allocation pressure, because ZipFile self-closes through a java.lang.ref.Cleaner as soon as it is unreachable. Measured, same leaky code:
  - one-entry zip, N=300, default heap: delta 300, 300, 300, 300, 300 (five runs). Stable enough to assert on.
  - five-entry zip, N=300: delta 2, 31, 5, 17, 18. A `delta > N/4` RED fails all five; a `delta <= 5` GREEN passes leaky code twice.
  - one-entry zip, N=1000: ~498. Raising N LOSES signal — do not "make it safer" by looping more.
So: use a single small entry, N=300, default heap, and assert `delta >= N/2`. Never call System.gc() and never call a helper that might — I measured one System.gc() take a 300-fd delta to 0. Guard with `Assumptions.assumeTrue(bean instanceof UnixOperatingSystemMXBean)`; there is no Windows equivalent. The fd is one per ZipFile, not one per `zip.getInputStream(entry)` (line 80) — child streams share the Source, so if both lines are flagged that is one descriptor, not two. GREEN with try-with-resources on line 75 only: delta 0 at N=30 and N=300 (verified; entry path at line 79 left untouched).

TIER 2 — the leaked handle is the Connection itself (`dataSource.getConnection().prepareStatement(...)` with nothing closing the Connection). That exact shape is live in the test tree at SqlInjectionLesson5Test.java:26 (formatted across lines 25-28). The harm is NOT pool exhaustion and `SQLTransientConnectionException` is unreachable here — I ran 500 leaked connections through the real DriverManagerDataSource and got no exception at any call and an fd delta of 0. The real harm is that each leak strands an HSQLDB session forever. Measured, through `new LessonDataSource(driverManagerDataSource)` on `jdbc:hsqldb:mem:`, counting with `select count(*) from information_schema.system_sessions`:
  RED: 200 leaked calls -> session delta 200. GREEN: 200 calls in try-with-resources -> session delta 0. After System.gc() the 200 are still there — GC does not reclaim them, so this RED is deterministic and needs no threshold and no timeout. This is still the most provable marker in the family; just count sessions, not pool timeouts.

TIER 3 — the omission is real but the release happens anyway, so exhaustion cannot show it. Two distinct sub-cases here, and an agent who does not know which one they are in will write a RED that passes and blame itself.
  (a) A Statement/ResultSet created on a Connection that IS inside try-with-resources — Assignment5.java:44 and most of the SqlInjection tree. Closing the Connection ends the HSQLDB session and the statement becomes unusable; I ran 2000 iterations of the Assignment5 shape and the session delta was 0, with no fd growth. NOTE THE CORRECTION: `leaked.isClosed()` returns FALSE here, not true — that "true" is Hikari ProxyConnection behaviour and there is no Hikari in the path. What is true is that the statement is functionally dead: reusing it throws `connection exception: closed`. Do not assert isClosed().
  (b) Process pipes — VulnerableTaskHolder.java:67-68, `Runtime.getRuntime().exec(taskAction)` plus a BufferedReader over `p.getInputStream()`, neither closed and the Process never destroyed. This looks like tier 1 and is not. Measured verbatim (taskAction "sleep 0", stdout drained to EOF, nothing closed): fd delta 0 over 200 iterations. The JDK's process reaper closes the pipes when the child exits. The instrument is fine — as a control, 20 live `sleep 30` children with pipes undrained show +60 fds — the leak simply does not accumulate for short-lived children, which is all this guarded code (`startsWith("sleep")||startsWith("ping")`, length < 22) can spawn.
  For either sub-case the only honest observation left is the omission itself: a counting proxy (`java.lang.reflect.Proxy` Connection handing out Proxy Statements, assert statementsCreated == statementsClosed) is wirable without Spring — Assignment5 is `@RequiredArgsConstructor` over LessonDataSource, which has a public `LessonDataSource(DataSource)` ctor, so `new Assignment5(new LessonDataSource(countingDs), flags)` compiles. LessonConnectionInvocationHandler:30 adds one SET SCHEMA statement per proxied call, but only when SecurityContextHolder holds a WebGoatUser (empty in a plain unit test) and it closes that one in try-with-resources, so it adds no noise. Say plainly which claim you are making: that test shows close() was never called, not that anything broke. If the pipeline demands harm, the correct settlement is "real omission, release guaranteed by the enclosing try-with-resources (a) / by the JVM process reaper (b), not demonstrable by exhaustion" — write that down instead of manufacturing a RED.

NOT LEAKS (verified, do not file): `FileCopyUtils.copy(in, new FileOutputStream(f))` at Salaries.java:47-49 and ProfileUploadRetrieval.java:64 — I ran a close()-recording FileOutputStream subclass against spring-core 7.0.8; both `copy(InputStream,OutputStream)` and `copy(byte[],OutputStream)` closed it. Purely in-memory streams (SerializationHelper.java:22 `new ObjectInputStream(new ByteArrayInputStream(data))`, :31 `new ObjectOutputStream(baos)`) hold no OS handle; there is nothing to exhaust. LessonConnectionInvocationHandler.java:30 is already inside try-with-resources — flat false positive. LessonDataSource.java:27 is ownership transfer, not a leak: the Connection is acquired and immediately handed to the caller wrapped in a Proxy, and the caller's try-with-resources closes it; closing it here would break every lesson.

WHAT GOES WRONG HERE.
1. Asserting the marker back at itself: counting close() calls with a proxy and reporting it as proof of harm. It proves the omission only. For tier 3 that is all there is — say so; for tiers 1 and 2 you have a real consequence, so use it.
2. `System.gc()` anywhere near a tier-1 fd test. Measured: it takes a 300-descriptor delta to 0, because ZipFile self-closes via a Cleaner once unreachable. The leak is real; the JDK masks it on demand. Same reason `assertEquals(N, delta)` is flaky — natural GC turned 200 into 114 in a heavier loop. Use a threshold.
3. Fixing an Assignment5.java:44-shaped marker and reporting "leak closed, pool exhaustion avoided". Verified false: `leaked.isClosed()` is already true after the enclosing connection closes, and 100k iterations showed no accumulation. Nothing was avoided.
4. Wrapping the `new FileOutputStream(...)` at Salaries.java:49 or ProfileUploadRetrieval.java:64 in try-with-resources. FileCopyUtils.copy already closed it — you have added a double close to code that had no leak.
5. "Cleaning up" ProfileZipSlip while closing the handle — adding `Path.normalize()` or a startsWith check around line 79. That deletes the zip-slip assignment. Close the ZipFile; do not touch the entry path. Symmetrically, do not decline the fix on the grounds that ProfileZipSlip is a lesson file: the unclosed descriptor is not what the lesson teaches.
6. Verdict words that do not follow: "the fd count did not move" is not "false positive" and not "not a defect" for tier 3 — it is "not demonstrable by exhaustion, harm bounded by the enclosing try-with-resources". And "it is in src/test" is not a reason to dismiss: SqlInjectionLesson5Test.java:26 leaks a pooled Connection, which is tier 2 and the most provable marker in this whole family.
