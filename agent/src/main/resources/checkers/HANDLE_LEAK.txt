(?:new\s+(?:Zip|Jar)File|new\s+File(?:Input|Output)Stream|new\s+(?:Server)?Socket|new\s+Object(?:Input|Output)Stream|new\s+Scanner|new\s+(?:FileReader|FileWriter|InputStreamReader|OutputStreamWriter|PrintWriter|BufferedReader|BufferedWriter)|Runtime\.getRuntime\(\)\.exec|(?:\w|\)|^\s*)\s*\.\s*(?:prepareStatement|prepareCall|createStatement|getConnection|getInputStream|getOutputStream)|Files\.(?:newInputStream|newOutputStream|newBufferedReader|newBufferedWriter|newDirectoryStream|lines|list|walk|find))\s*\(
An expression that acquires a releasable handle — archive file, File*Stream, Socket, Process, JDBC Connection/Statement/ResultSet — whose result goes into a plain local or is discarded, with no try-with-resources and no close() on any path out of the method. The sibling HANDLE_LEAK.EXCEPTION is the narrower case where a close exists but only on the normal path. The construct this is constantly mistaken for is a handle the CALLEE closes: a copy helper taking `new FileOutputStream(f)` as an argument matches the regex and is no leak if the helper closes in a finally. The flagged line is the acquisition site, not always the line where the handle is lost, so read the whole method and decide which tier you are in BEFORE writing a test — tier 3 cannot be shown by exhaustion at all, and an agent who does not know that writes a RED that passes and blames itself.

FIRST ESTABLISH WHAT THE HANDLE COSTS. For JDBC that means finding the DataSource implementation actually constructed. A connection pool on the dependency tree is not a pool in the path — an application that declares its own DataSource commonly suppresses the framework's pooled default, and then every getConnection() opens a fresh physical session. Do not build a harness around a pool the application does not use: it compiles, it goes RED, and it proves nothing about this application.

TIER 1 — the handle owns an OS descriptor nothing else releases (archive files, file streams, sockets). Loop the leaky shape N times through the smallest seam that reaches it, sampling `((com.sun.management.UnixOperatingSystemMXBean) ManagementFactory.getOperatingSystemMXBean()).getOpenFileDescriptorCount()` before and after. PIN THE FIXTURE, NOT JUST THE THRESHOLD: these types self-close through a java.lang.ref.Cleaner once unreachable, so allocation pressure inside the loop destroys the measurement. A minimal body over a small fixture gives a delta of essentially N run after run; adding real work makes the same leak read as a handful of descriptors, and raising N loses signal rather than buying safety. So keep the body small, assert `delta >= N/2` rather than equality, never call System.gc() or a helper that might — one collection takes a full delta to zero — and guard with an assumption that the bean is a UnixOperatingSystemMXBean, since there is no Windows equivalent. An open archive file is one descriptor however many entry streams are derived from it, since those share the underlying source.

TIER 2 — the leaked handle is the Connection itself, and what to count follows from the DataSource. Behind a pool the RED is exhaustion: one connection, a short acquisition timeout, and the second call throws a timeout exception in a second, deterministically. With no pool there is no exhaustion and often no descriptor movement either; the harm is that each leak strands a database session for the life of the process, so count sessions through the server's own catalog. Sessions are not reclaimed by GC, which makes that RED deterministic and free of thresholds.

TIER 3 — the omission is real but release happens anyway, so exhaustion cannot show it. (a) A Statement or ResultSet created on a Connection that IS inside try-with-resources: closing the Connection ends the session and the statement is functionally dead — reusing it throws — but isClosed() on it may still answer false, because that true belongs to a pool proxy which is not necessarily in the path. Do not assert isClosed() as though it were universal. (b) Process pipes: a stream over a child's stdout never closed and a Process never destroyed looks like tier 1 and is not, because the JVM's process reaper closes the pipes when the child exits, so short-lived children accumulate nothing; as a control that the instrument works, a few long-lived children with undrained pipes do show several descriptors each. For either sub-case the only honest observation is the omission itself: hand the code a Connection that is a `java.lang.reflect.Proxy` issuing Proxy Statements and assert statementsCreated == statementsClosed. Say plainly what that claims — close() was never called, not that anything broke. If harm is demanded, the correct settlement is "real omission, release guaranteed by the enclosing try-with-resources (a) or by the process reaper (b), not demonstrable by exhaustion" — write that instead of manufacturing a RED.

NOT LEAKS. Purely in-memory streams (ObjectInputStream over a ByteArrayInputStream and the like) hold no OS handle, so there is nothing to exhaust whether they are closed or not. A handle acquired and immediately returned to the caller, wrapped or not, is ownership transfer; closing it at the acquisition site would break every caller. An acquisition already inside try-with-resources is a flat false positive — check that first. On the returned-ResultSet shape, where a Statement is created, its ResultSet returned and the Statement never closed, the textbook hazard is that closing the Statement closes its ResultSet and the caller reads nothing; some drivers do not behave that way and a scrollable ResultSet may read fine afterwards, so assume it in neither direction and run the test.

WHAT GOES WRONG HERE.
- Counting close() calls with a proxy and reporting it as proof of harm. It proves the omission only. For tier 3 that is all there is; for tiers 1 and 2 a real consequence exists, so use it.
- Fixing a tier-3 marker and reporting "leak closed, exhaustion avoided". Nothing was avoided — something else was already releasing the handle.
- Wrapping an argument expression in try-with-resources when the callee already closes it, which adds a double close to code that had no leak.
- Hardening unrelated code in the same edit. A handle-lifetime fix should change handle lifetime and nothing else; validation added alongside changes behaviour the existing tests assert, so re-run them.
- Verdict words that do not follow: "the descriptor count did not move" is not "false positive" and not "not a defect" for tier 3 — it is "not demonstrable by exhaustion, release guaranteed elsewhere". And "it is in test sources" is no reason to dismiss; a leaked Connection is the same defect wherever it is written.
