(?:\blong\b[^=;]*=|[+\-*]=|\breturn\b|\(\s*long\s*\))[^;]*[\w)\]]\s*(?:<<|\*)\s*[\w(]
The checker asserts that a multiplication evaluated in 32-bit int has its int result widened to long afterwards, so any overflow has already happened by the time the extra 32 bits arrive. "Multiplication" includes `<<` by a constant, which is a multiply by a power of two — the detector matches the bytecode pair IMUL-or-ISHL immediately followed by I2L, so the flagged line need not contain a `*` at all. The widening is usually invisible in source: `longField += intExpr`, `return intExpr;` from a long-returning method, or `(long) (a * b)` where the cast landed outside the parentheses. Neighbours it gets confused with: ICAST_INT_2_LONG_AS_INSTANT (an int with no arithmetic used as a millisecond timestamp) and ICAST_IDIV_CAST_TO_DOUBLE (integer division widened to double); an int multiply whose result stays in an int is not this pattern at all, because there is no widening.

HOW YOU MAKE IT VISIBLE.
Nothing here throws, logs or changes control flow — the only observable is a number, so a test has to drive an operand past the 32-bit boundary and read the wrong result back through the public API. Both halves need arithmetic done on paper first: `a * b` overflows at |a*b| >= 2^31, and `x << k` at x >= 2^(31-k), so a shift by 3 first fails at 2^28.

REACHABILITY IS WHERE THESE MARKERS USUALLY DIE, and it is decided by lines you only get by reading around the flag. A clamp above the expression may cap the operand to the size of a real buffer, so an oversized count cannot be passed with a small array. An entry point that streams fixed-size blocks never reaches the threshold however large the total input. And where a long accumulator grows across calls but the overflowing product is computed per call, repetition never triggers it either — only one oversized call does. Name the route that reaches the expression; where every operand is provably bounded, say which bound blocks it and stop, rather than inventing a caller that cannot exist.

ORACLE. Do not reflect into the private accumulator, and do not recompute the value with the same arithmetic inside the test — both assert the buggy expression against itself and pass either way. Assert the public result against an independent implementation of the same computation.

The failure is all-or-nothing, which decides your inputs. The computed and true values are congruent mod 2^32, because widening a truncated int only ever loses multiples of 2^32, so every input below the threshold behaves bit-identically and there is no "slightly wrong at a convenient small size" to go looking for. The boundary is exact, so assert both sides of it: wrong at the threshold, agreeing one unit below.

Such a test is a big-allocation test, not a slow one. If it needs more heap than the build's forked test JVM inherits, raise the heap in the fork's JVM arguments. Do NOT reach for `Assumptions.assumeTrue(Runtime.getRuntime().maxMemory() > ...)` or `@Disabled` — a skipped test is not a RED, and it is exactly how this marker gets silently written off as unprovable.

WHAT GOES WRONG HERE.
Grepping the flagged line for `*`, finding none, and declaring the marker mislocated. The shift IS the multiplication: `<< 3` is `* 8`, and `ishl` followed by `i2l` is precisely what the detector matches.

Putting the cast on the wrong side. `(long) (x << 3)` casts after the int shift has already overflowed and changes nothing; the cast belongs on the operand, `(long) x << 3`. Both spellings compile and look equally fixed, so the RED must be re-run to see which one moved it.

Deleting the construct instead of correcting it. The one-token widening leaves every in-range result unchanged, so existing tests stay green; replacing the whole algorithm changes results other code may depend on and proves nothing about the arithmetic.

Generalising "int multiply can overflow, therefore always a defect". Arithmetic whose result stays in int has no widening and this checker has nothing to say about it, and an expression in which any operand is already long is 64-bit throughout. The operand types decide it, not the shape of the line.
