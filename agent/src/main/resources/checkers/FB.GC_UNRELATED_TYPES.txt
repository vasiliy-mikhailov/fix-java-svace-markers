\.(?:contains|containsKey|containsValue|containsAll|indexOf|lastIndexOf|remove|removeAll|retainAll|get|getOrDefault)\s*\(
A call to one of the java.util lookup methods whose parameter is declared `Object` rather than the collection's type variable is handed an argument whose static type is unrelated to the collection's declared element or key type. Generics do not police those signatures, so javac is silent and the lookup simply never matches: the expression is constant-false (or constant-null), and whatever feature it gates silently does nothing. Two neighbours get mistaken for it constantly: EC_UNRELATED_TYPES is a bare `a.equals(b)` between unrelated types with no collection involved, and other vendors ship the same defect under names like COLLECTION.WRONG_ARG_TYPE. A mismatch on a normally typed parameter is none of these, because the compiler already rejects it — if the expression you are examining is type-checked by javac, you are looking at the wrong expression.

KNOW THE CHECKER'S EXACT REACH before calling anything an instance of it. SpotBugs' FindUnrelatedTypesInGenericContainer checks a fixed table: `Collection.contains/containsAll/remove/removeAll/retainAll`, `List.indexOf/lastIndexOf`, `Map.containsKey/containsValue/get/remove`, `Deque.removeFirstOccurrence/removeLastOccurrence`, `Hashtable/ConcurrentHashMap.contains`, `ConcurrentMap.remove(Object,Object)`, plus the Guava collections. `Map.getOrDefault` is NOT in that table, even though the regex above matches it. So an always-missing `getOrDefault` is a real bug and is not this marker; report it as such rather than stretching the checker to cover it.

WHY THE LOOKUP MISSES, mechanically. `List.contains/indexOf` on the common implementations evaluate `argument.equals(element)` — the ARGUMENT's equals, not the element's — so a record's or value class's generated equals, which rejects anything that is not the same type, makes the test constant-false. Hash-based lookups are stricter still: `HashMap.get` and `HashSet.contains` consult `hashCode` before `equals`, so mismatched types can never collide into a hit. Genuine false positives are therefore narrow: the lookup CAN succeed when the argument's `equals` accepts the element's type — a cross-implementation `List.equals`, or a hand-written `equals` comparing against an interface such as `CharSequence`. Read that `equals` before deciding.

HOW YOU MAKE IT VISIBLE.
Test the feature the lookup gates, never the lookup itself. Find the smallest public entry point that reaches the call, configure it so the lookup SHOULD hit, and assert on the user-visible outcome — the item that should have been excluded is still listed, the cache entry that should have been found is rebuilt empty. RED at the flagged expression, GREEN once the argument's type matches the collection.

WAYS THAT RED GOES WRONG AND MUST BE RULED OUT BEFORE YOU BELIEVE IT.
An unstubbed collaborator returning null can short-circuit the entry point so that the "absent" outcome you asserted happens on broken and fixed code alike — always keep a control case asserting the item IS present when nothing is configured to exclude it.
A second filter upstream can stop the loop body from running at all, so the assertion succeeds vacuously. Configure every other filter to let your case through.
A value derived from `getClass().getName()` differs for a nested test class (`Outer$Nested`), so a hard-coded expectation fails identically before and after the fix. Derive the expected value from the object rather than typing it in.
A mocked collaborator whose accessor returns null never matches on broken OR fixed code — a test that is RED forever. Use a real subclass, or stub the accessor to a real value.
And watch the interaction with immutable collections: with a null argument, some implementations throw out of the lookup where an ArrayList would just return false, so your RED ends up being about a null guard rather than about the type mismatch.

IF THE FLAGGED LINE CARRIES NO OBJECT-PARAMETER LOOKUP AT ALL, conclude nothing yet — that is line drift, not a false positive. Recover the expression from history (`git log -p -- <file>`; note that `git log -S` may miss a fix that only changed the argument). If the construct is genuinely gone from the current tree, the honest settlement is that the code no longer contains the defect — fixed or stale, not that the checker was wrong. To watch it fail, restore that one expression locally and run the test.

WHAT GOES WRONG HERE.
Type-checking the wrong expression and calling it a false positive. This is the commonest failure on this checker: an agent confirms that some other call on the line takes exactly the type it is given, and concludes the report is bogus. A GC_UNRELATED_TYPES the compiler could catch cannot exist, so finding only compiler-checked calls on the flagged line means the line number drifted.

Asserting the marker back at itself: `assertFalse(List.of("x").contains(new Name("x")))` is a fact about java.util that holds identically on fixed and broken code, as is any test that reaches into the collection directly. The claim worth proving is that the FEATURE does not do what it says.

Verdict words that do not follow: "the construct is gone from the current tree" means fixed or stale, not false-positive; "I could not build a harness" means unproven, not false-positive.

And note that repairing the lookup makes a previously dead code path live. That is a behaviour change, and something downstream may have been built on the path never being taken — check before patching.
