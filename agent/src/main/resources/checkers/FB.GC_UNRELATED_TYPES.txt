\.(?:contains|containsKey|containsValue|containsAll|indexOf|lastIndexOf|remove|removeAll|retainAll|get|getOrDefault)\s*\(
A call to one of the java.util lookup methods whose parameter is declared `Object` rather than the collection's type variable — `Collection.contains/remove/indexOf`, `Map.get/getOrDefault/containsKey/containsValue/remove` — is handed an argument whose static type is unrelated to the collection's declared element or key type. Generics do not police those signatures, so javac is silent and the lookup simply never matches: the expression is constant-false (or constant-null), and whatever feature it gates silently does nothing. Two neighbours get mistaken for it constantly: EC_UNRELATED_TYPES is a bare `a.equals(b)` between unrelated types with no collection involved, and Svace's COLLECTION.WRONG_ARG_TYPE is this same defect under another vendor's name; a mismatch on a *normally typed* parameter (passing a String where `getLessons(Category)` is declared) is none of these, because the compiler already rejects it — if the expression you are examining is type-checked by javac, you are looking at the wrong expression.

HOW YOU MAKE IT VISIBLE.
Test the feature the lookup gates, never the lookup itself. The defect is behavioural and usually cheap to expose: find the smallest public entry point that reaches the call, configure it so the lookup *should* hit, and assert on the user-visible outcome.

WHAT GOES WRONG HERE.
Type-checking the wrong expression and calling it a false positive — both prior runs on this marker did exactly that, one "confirming" that `course.getLessons(category)` takes a `Category`, the other that `getChildren().sort(Comparator.comparingInt(LessonMenuItem::getRanking))` is well typed. Both are javac-checked, so of course they matched; a GC_UNRELATED_TYPES the compiler could catch cannot exist, and finding only compiler-checked calls on the flagged line means the line number drifted, not that the checker misfired.

Asserting the marker back at itself: `assertFalse(List.of("SqlInjection").contains(new LessonName("SqlInjection")))` is a fact about java.util that holds identically on fixed and broken WebGoat, as is any test that reaches into the collection directly. The claim worth proving is that EXCLUDE_LESSONS does not exclude.

RED for the wrong reason, in three flavours here: a null `UserProgress` from an unstubbed repository short-circuits `showLeftNav` to an empty menu; a nested lesson class whose real name is `Outer$Dummy` never matches a hard-coded `"Dummy"`; an `excludeCategories` value that swallows the category leaves the loop body unexecuted. Each hands you the assertion you wanted through a mechanism unrelated to the defect.

Verdict words that do not follow: "the construct is gone from HEAD" means fixed or stale, not false-positive; "I could not build a harness" means unproven, not false-positive. And a fix inside a lesson (the `CommentsCache` map key) makes a previously dead lookup live — a behaviour change an assignment may be built on, so read the lesson before patching it.
