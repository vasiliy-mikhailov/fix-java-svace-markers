(new\s+Random\s*\(|\bMath\s*\.\s*random\s*\(|\bThreadLocalRandom\s*\.\s*current\s*\(|\.\s*setSeed\s*\()
The checker flags a value drawn from `java.util.Random` (or `Math.random()`) — a 48-bit linear congruential generator whose entire future output follows from its current state — where that value is meant to be unguessable: a secret, a token, a session id, a reset link. It anchors on the construction of the generator and on `setSeed` with a guessable argument, and it does not fire on `java.security.SecureRandom` (`CryptoUtil.java:42` and `DOMCrossSiteScripting.java:33` both call `new SecureRandom().nextInt(...)` and are absent from this queue), so the complaint is about the generator class, not about "randomness near crypto". Do not confuse it with SpotBugs' DMI_RANDOM_USED_ONLY_ONCE, which fires on the very same `new Random().nextInt(n)` one-liner but complains that a generator was created and discarded (wasted seeding, poor distribution); a marker naming PREDICTABLE_RANDOM is not making that complaint, and the fixes differ.

HOW YOU MAKE IT VISIBLE.
A JUnit test can make this visible only when it has BOTH an observation channel (a drawn value reaches the test) and a continuation (a later value from the same generator instance, or a seed the test can reconstruct). Sort the flagged sites by which of those two actually exist — that sort decides the marker.

(1) SEED DERIVED FROM LOW-ENTROPY OR ATTACKER-SUPPLIED INPUT — fully demonstrable, deterministic, no brute force. `PasswordResetLink.java:18` does `random.setSeed(key.length())`, so the returned link depends on the key's LENGTH and nothing else. I compiled and ran it: `createPasswordReset("admin","abcd")` and `createPasswordReset("admin","zzzz")` both return `37a0f7228431a0e571435a49f2aac829`, and the value `Assignment7.java:89` actually mails — `createPasswordReset("admin","webgoat")` — is `a081235eff82092a319374c24aaa7574` in every JVM (verified identical across three separate JVM launches). RED: `assertNotEquals(createPasswordReset("admin","abcd"), createPasswordReset("admin","zzzz"))`, or assert the admin link differs across two fresh calls. Control that proves the assertion measures the seeding rather than `scramble`: `createPasswordReset("tom","abcd")` returned two different values in one JVM. GREEN once the seed comes from `SecureRandom` — and that GREEN makes challenge 7 unsolvable, because predicting admin's link IS the exercise.

(2) UNSEEDED `new Random()`, FULL-WIDTH DRAWS, LONG-LIVED INSTANCE — demonstrable by state recovery in ~65536 iterations, milliseconds. `HttpBasicsExternal.java:35` is the only site of this shape here: a `random` field on a singleton `@RestController`, and `PUT /HttpBasics/external` returns `Integer.toHexString(random.nextInt())` in the response body (line 55). Three back-to-back calls yield three consecutive `next(32)` outputs, each the top 32 bits of the state. Recover the missing 16 bits: for `lo` in 0..65535 take `s = ((long)o1 << 16) | lo`, advance `s = (s * 0x5DEECE66DL + 0xBL) & ((1L<<48)-1)`, keep the candidate whose `(int)(s >>> 16) == o2`, advance once more and you have `o3`. I ran exactly this and it predicted the third value bit-for-bit. RED: `assertNotEquals(predictedThird, actualThirdSecret)`. GREEN under `SecureRandom`: the same loop finds no 48-bit state consistent with the first two observations (verified). Two mechanics to get right or the test fails for the wrong reason — parse with `Integer.parseUnsignedInt(hex,16)`, since `toHexString` prints unsigned and any draw >= 0x80000000 is eight hex digits that `Integer.parseInt` rejects with NumberFormatException; and the three calls must be consecutive on that shared instance, so nothing else in the same Spring context may draw from it in between.

(3) UNSEEDED `new Random()`, ONE TRUNCATED DRAW, GENERATOR DISCARDED — the continuation does not exist, and predictability CANNOT be demonstrated. This covers `ImageServlet.java:21` (`nextInt(10000)` once per JVM in a static initialiser), `CSRFGetFlag.java:39`, `:45`, `:56` (a fresh Random per request, one `nextInt(65536)` each), `HashingAssignment.java:37` and `:55`, `EncodingAssignment.java:37`, `JWTSecretKeyEndpoint.java:38` (fresh Random, one `nextInt(5)`). Each seed is `seedUniquifier() ^ System.nanoTime()`; one truncated output leaks 14-16 bits of a 48-bit state, not enough to pin it, and even a pinned state predicts nothing because the next call builds a new generator. A test that observes one value and predicts the next here is not a weak RED — it is a RED that can only pass by luck. Say plainly that the marker is not provable at these sites; that is the settlement, and it is not the same as saying the code is fine.

What IS observable at those sites is a DIFFERENT defect, and mistaking it for this one is the failure mode. At `JWTSecretKeyEndpoint.java:38`, `HashingAssignment.java:37`/`:55` and `EncodingAssignment.java:37` the draw indexes `public static final String[] SECRETS` — five dictionary words compiled into the artifact, already imported by `JWTSecretKeyEndpointTest.java:9`.
