(new\s+Random\s*\(|\bMath\s*\.\s*random\s*\(|\bThreadLocalRandom\s*\.\s*current\s*\(|\.\s*setSeed\s*\()
The checker flags a value drawn from `java.util.Random` or `Math.random()` — a 48-bit linear
congruential generator whose entire future output follows from its current state — where that value is
meant to be unguessable: a secret, a token, a session id, a reset link. It anchors on the construction
of the generator and on `setSeed` with a guessable argument, it also reports
`ThreadLocalRandom.current()`, and it does not fire on `java.security.SecureRandom`, so the complaint
is about the generator class and not about "randomness near crypto". Do not confuse it with SpotBugs'
DMI_RANDOM_USED_ONLY_ONCE, which fires on the very same `new Random().nextInt(n)` one-liner but
complains that a generator was created and discarded; different claim, different fix.

HOW YOU MAKE IT VISIBLE. Predictability can be demonstrated only where BOTH an observation channel (a
drawn value reaches the test) and a continuation (a later value from the same instance, or a seed the
test can reconstruct) exist. Sort the site by which of the two is present; that sort decides the marker.

A SEED FROM LOW-ENTROPY OR CALLER-SUPPLIED INPUT is fully demonstrable and deterministic. Where
`setSeed` takes something like the length of a string, the output is a function of that alone: assert
that two inputs differing only outside the seed produce IDENTICAL output, or that a value repeats
across separate JVM launches. Add a control that varies the seed and shows the output changing, so the
assertion is known to measure the seeding and not whatever hashing sits downstream of it.

UNSEEDED `new Random()` WITH FULL-WIDTH DRAWS FROM A LONG-LIVED INSTANCE is demonstrable by state
recovery in about 65536 iterations, milliseconds. Consecutive `next(32)` outputs are each the top 32
bits of the state; recover the missing 16 by trying every `lo` in 0..65535 as `s = ((long)o1 << 16) |
lo`, advancing `s = (s * 0x5DEECE66DL + 0xBL) & ((1L << 48) - 1)`, keeping the candidate whose
`(int)(s >>> 16) == o2`, and advancing once more to predict the next value before it is issued. Under
`SecureRandom` no 48-bit state fits the observations, so handle "no candidate found" explicitly as the
GREEN branch — there is then no predicted value to compare. Two mechanics or the test fails for the
wrong reason: parse a hex-rendered draw with `Integer.parseUnsignedInt`, since unsigned printing makes
any value at or above 0x80000000 eight digits that `Integer.parseInt` rejects; and the observations
must be CONSECUTIVE draws on that instance, because anything else drawing in between — including a
malformed request that consumes a draw before failing validation — breaks the chain, and the recovery
then finds nothing, which looks exactly like the SecureRandom GREEN.

UNSEEDED `new Random()`, ONE TRUNCATED DRAW, GENERATOR DISCARDED has no continuation and predictability
CANNOT be demonstrated. The seed is `seedUniquifier() ^ System.nanoTime()`; one truncated output leaks
14 to 16 bits of a 48-bit state, not enough to pin it, and even a pinned state predicts nothing because
the next call builds a new generator. A test that observes one value and predicts the next there is not
a weak RED, it is a RED that can only pass by luck. Say plainly that the marker is not provable at such
a site; that is the settlement, and it is not the same as saying the code is fine.

`ThreadLocalRandom.current()` has the continuation — a long-lived per-thread instance — but usually not
the channel: if the value never leaves the method and its only effect is a one-bit decision, one bit
per call against a generator advancing by a golden-gamma addition through a mix64 finalizer is not
recoverable. TLR is also seeded per thread from system entropy and is not the `new Random()` weakness,
so such a marker is arguably a checker false positive — report that as the conclusion of reading the
line, not as grounds for dismissing the marker as a neighbouring construct.

THE FAILURE MODE IS PROVING A DIFFERENT DEFECT. Where the draw indexes a small compile-time constant
array, a test can assert the served secret is one of N. Where the value lives in a small range and the
endpoint checking it has no attempt limiting, a guessing test goes RED. Where a random seed feeds an
incrementing counter, successive values differ by exactly one. Each is a real observation and none is
this checker's claim. THE DISCRIMINATOR: substitute `SecureRandom` and re-run — a test still RED
afterwards was never measuring the generator.

DELIBERATE OR NOT: decide by reading around the line, not by the directory it sits in. A comment naming
the weakness, an annotation or suppression naming the choice, or a test that reaches its goal by
exploiting it are evidence somebody chose this; absent that, the identical construct is an ordinary
defect with an ordinary fix.

WHAT GOES WRONG HERE. Asserting the marker back at itself, by grepping for `new Random` or reflecting
the field out and asserting it is not a `SecureRandom`. Anchoring a RED on a constant elsewhere in the
source that looks like the reproducible value: such constants go stale relative to the code that once
produced them, so the assertion does fail, for the wrong reason. Drawing once from an unseeded
generator and asserting the value differs from a constant, which passes by coin flip and cannot be
re-run. Treating a neighbour as the flagged construct, since `SecureRandom`, `RandomStringUtils` and
`UUID.randomUUID()` are sometimes the same weakness in spirit and none of them is `java.util.Random`.
The verdict slip "SecureRandom is a drop-in, so fix it", when harmless-to-change is not
demonstrated-defect. And editing a generator without following the threads out of it, since another
component may hard-code a value this code produces, or the source text may itself be shipped somewhere,
leaving two copies of the system disagreeing.
