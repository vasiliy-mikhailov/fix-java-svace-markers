\.(?:getOriginalFilename|getProperty|getParameter|getHeader|getParentFile|getResource|listFiles|getModelAndView|getViewName)\s*\(|\b[a-z]\w*\s*\?\s*[a-z]\w*\s*\.\s*\w+\s*\(
A value that came out of a method whose return is declared nullable is dereferenced, or unboxed, on at least one path through the enclosing method, with no null check between the call and the use. "FROM_RETURN_VALUE" names where the null comes from — a callee's return — not how likely it is; the nullability is normally declared by an annotation on the callee, and framework jars increasingly carry those as runtime-visible type annotations, so the declaration is checkable rather than guessed. Do not confuse it with NP_ALWAYS_NULL (null on every path reaching the deref, a definite crash), with plain NP_NULL_ON_SOME_PATH (the null arises from a local branch or an earlier store rather than a call's return), or with the NP_NULL_PARAM family (the value is only handed on as an argument, so the NPE happens inside the callee). Unboxing counts as a dereference, so a ternary whose condition is a nullable Boolean is flagged as much as a `.method()` call on the same line.

CLASSIFY THE FLAGGED EXPRESSION BEFORE WRITING ANY RED. Direct dereference: NPE at the line. Unboxing: NPE at the condition. Passed to a parameter that forbids null: NPE inside the callee, and the finding must cite the real frame. Concatenated or logged: NO exception at all — concatenation absorbs null, and the observable is a corrupted value, such as a redirect target or path containing the literal text "null". That last case is still a defect and still demonstrable; settling a marker not-a-bug because "it didn't throw" is the commonest way to get this checker wrong.

HOW YOU MAKE IT VISIBLE.
Three moves: make the callee return null, invoke the ENCLOSING PRODUCTION METHOD, and assert the RED outcome — then, after the fix, the behaviour that should have happened instead. "It didn't throw" is not a GREEN; name the alternative outcome (the rejection result the caller expects, the corrected value that gets logged, the view that gets returned) and assert that.

THE TRAP THAT DECIDES MANY OF THESE MARKERS: the framework's own convenience test double may be unable to produce the null. Such constructors routinely coerce a null name or value to the empty string; the flagged expression then runs harmlessly, and whoever stops there reports the marker false when it is not. Read the double's own source or bytecode, and where it coerces, use a mocking framework or a short hand-written implementation of the interface that genuinely returns null.

REACHABILITY, STATED HONESTLY, IS PART OF THE FINDING. A RED built this way is a contract test at the method boundary. If the framework never binds the null-producing case from a real request — a request part with no filename may not bind to a file object at all, so binding fails long before the flagged line — say so; "an attacker sends X and the server crashes" is then a claim you cannot demonstrate. The opposite overreach is just as wrong: shipped configuration that happens to set the property is not grounds for not-a-bug, because the method accepts any context, the value is overridable, and the guard is one line.

ADJACENT MARKERS ON THE SAME NULLABLE VALUE ARE NOT INTERCHANGEABLE. Where two lines both dereference the same call, a stub returning null every time always throws at the FIRST of them, and only a stub returning a good value once and null on the second call reaches the second line — which no real implementation does. Assert at the method boundary, capture the stack trace, and say in the finding where the throw actually landed; "line N throws" when the trace says otherwise is a RED that did not fail for the reason given. One hoisted local plus a guard settles both lines.

WHAT ELSE GOES WRONG HERE.
Two dereferences on one line — an unboxed Boolean and a dereferenced String, say — and a fix that addresses only one. Both are the flagged construct.

Asserting the marker back at itself: asserting that the stub you told to return null returns null, or that an NPE happened somewhere, without ever calling the production method.

"Fixing" with `Objects.requireNonNull(...)` or an `assert`: still an NPE, the RED stays red, nothing settled. Wrapping the body in `catch (NullPointerException e)` silences instead of fixes, and can swallow the failure result callers depend on.

Swapping the nullable accessor for a different, non-null one that returns a DIFFERENT value. The unit test goes green while the feature quietly rejects every input, because the substitute returns something that never satisfies the surrounding condition.

Reading the verdict off the surroundings rather than off the line: what a file is for does not settle whether a nullable return is checked, and its name, package or directory is no evidence either way. Intent is shown by something checked in that DEPENDS on the null reaching the dereference — documentation telling callers the value may arrive null here, a test asserting the resulting throw or corrupted value, a comment or suppression naming the choice. Absent that, the identical unguarded dereference is an ordinary defect.
