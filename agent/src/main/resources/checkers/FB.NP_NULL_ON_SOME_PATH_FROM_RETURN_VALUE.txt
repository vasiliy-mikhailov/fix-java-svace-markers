\.(?:getOriginalFilename|getProperty|getParameter|getHeader|getParentFile|getResource|listFiles|getModelAndView|getViewName)\s*\(|\b[a-z]\w*\s*\?\s*[a-z]\w*\s*\.\s*\w+\s*\(
A value that came out of a method whose return is declared nullable is dereferenced, or unboxed, on at least one path through the enclosing method, with no null check between the call and the use. "FROM_RETURN_VALUE" names where the null comes from — a callee's return — not how likely it is; the nullability is normally declared by an annotation on the callee (in this repo Spring 7 carries JSpecify @Nullable as a runtime type annotation: verified on org.springframework.web.multipart.MultipartFile.getOriginalFilename() in spring-web-7.0.8 and on PropertyResolver.getProperty(String) / getProperty(String, Class) in spring-core-7.0.8). Do not confuse it with NP_ALWAYS_NULL (null on every path reaching the deref, a definite crash), with plain NP_NULL_ON_SOME_PATH (the null arises from a local branch or assignment rather than a call's return), or with the NP_NULL_PARAM family (the nullable value is only handed on as an argument, so the NPE happens inside the callee) — and note that unboxing counts as a dereference, which is why StartWebGoat.java:44 is flagged for `sslEnabled ?` as much as for `url.replace(...)`.

HOW YOU MAKE IT VISIBLE.
The observable is a NullPointerException thrown at the flagged expression when the nullable call really returns null — so the arrangement is always the same three moves: make the callee return null, invoke the *enclosing production method*, and assert both the NPE (RED) and, after the fix, the behaviour that should have happened instead (GREEN). "It didn't throw" is not a GREEN; name the alternative outcome.

ROUTE A — the null comes from a parameter object (ProfileZipSlip.java:58, `!file.getOriginalFilename().toLowerCase().endsWith(".zip")`).
The endpoint is an ordinary public method on an ordinary object; no Spring context is needed. `new ProfileZipSlip(tempDir.toString()).uploadFileHandler(stub, "test")` works, and the GREEN value is constructible too — AttackResultBuilder.build() only calls `assignment.getClass().getSimpleName()`.
THE TRAP THAT DECIDES THIS MARKER: MockMultipartFile cannot produce the null. Its 4-arg constructor coerces a null originalFilename to the empty string — the bytecode in spring-test-7.0.8 is literally `aload_2; ifnull -> ldc ""`. So `new MockMultipartFile("uploadedFileZipSlip", null, "application/zip", bytes)` yields `""`, `"".toLowerCase().endsWith(".zip")` is false, the method returns a normal `failed(...)` result, and an agent who stops there reports the marker false when it is not. The RED needs a MultipartFile whose getOriginalFilename() genuinely returns null: a Mockito mock (`when(file.getOriginalFilename()).thenReturn(null)`, plus getBytes()/getInputStream() stubs if the fixed path reaches them) or a short anonymous implementation of the interface. Mockito and spring-test both arrive via spring-boot-starter-test, already on the test classpath.
Say plainly in the finding what this RED does and does not show. It shows the method violating the declared nullability contract of its own parameter type. It does NOT show an HTTP-reachable crash: Spring materialises a part as a MultipartFile only when the Content-Disposition carries a filename; a nameless part becomes a plain request parameter, so `@RequestParam("uploadedFileZipSlip") MultipartFile` fails to bind (400) and line 58 is never reached. Through MockMvc the worst you can inject is `""`. "An attacker uploads a nameless file and the server 500s" is a claim you cannot demonstrate here.
GREEN: hoist and guard, keeping the existing rejection path — `var filename = file.getOriginalFilename(); if (filename == null || !filename.toLowerCase().endsWith(".zip")) return failed(this).feedback("path-traversal-zip-slip.no-zip").build();` — then assert the returned AttackResult's feedback key and `lessonCompleted == false` with the same null stub.

ROUTE B — the null comes from configuration (StartWebGoat.java:44, fed by lines 39/41).
Two nullable returns are dereferenced on one line: `sslEnabled` (a Boolean from `getProperty(..., Boolean.class)`) is unboxed by the ternary condition, and `url` (from `getProperty("webgoat.url")`) is dereferenced by `.replace(...)` on the true branch. No mocking framework is required: `var env = new MockEnvironment();` (org.springframework.mock.env, present in spring-test-7.0.8) `var ctx = new GenericApplicationContext(); ctx.setEnvironment(env);` — leave both keys unset for the unboxing NPE, or set only `server.ssl.enabled=true` for the `url` NPE. `printStartUpMessage` is private static, so reach it with `ReflectionTestUtils.invokeMethod(StartWebGoat.class, "printStartUpMessage", ctx)` (that `invokeMethod(Class<?>, String, Object...)` overload exists, and ReflectionUtils rethrows the target exception unwrapped so `assertThatThrownBy(...).isInstanceOf(NullPointerException.class)` catches the real NPE) rather than widening the method or calling `main`, which would boot two Spring Boot applications.
The caveat that shapes the settlement, and which belongs in the finding: application-webgoat.properties ships both keys (`server.ssl.enabled=${WEBGOAT_SSLENABLED:false}`, `webgoat.url=http://...`) and WebGoat.java loads that file via `@PropertySource`, so in the shipped configuration neither null occurs. This RED is a contract test at the method boundary, not a reproduction of a startup crash — do not dress it up as one. It is also not grounds for NOT-A-BUG: the method accepts any ApplicationContext, both keys are environment-overridable (WEBGOAT_SSLENABLED, config-location overrides), and the fix is one line — `getProperty("server.ssl.enabled", Boolean.class, false)` or `Boolean.TRUE.equals(sslEnabled)`, plus a default or guard for a missing url. Assert the logged message contains the https URL, not merely that nothing threw.

ROUTE C — the nullable value is only passed on (the FileServer.java:75/79 shape, `destinationDir.toPath().resolve(multipartFile.getOriginalFilename())`). The NPE surfaces from inside the callee, so the assertion is still "invoking importFile throws NPE", but check the flagged line's own construct before writing it up: if nothing there dereferences the value itself, the honest description is "nullable return passed to a parameter that forbids null". Same MockMultipartFile trap; additionally `fileLocation` is a private `@Value` field (set it with `ReflectionTestUtils.setField`) and the method needs an Authentication (`new UsernamePasswordAuthenticationToken("test", "")`).

WEBGOAT-SPECIFIC. In ProfileZipSlip the deliberate vulnerability is the extraction loop at lines 79-81 (`new File(tmpZipDirectory.toFile(), e.getName())` with no containment check) — that IS the zip-slip lesson and must survive the fix untouched. The null dereference at line 58 belongs to no lesson: no hint or assignment depends on a null filename, and the exploit uploads a real `.zip`. src/it/java/org/owasp/webgoat/integration/PathTraversalIntegrationTest.java (~line 140) posts a crafted zip and asserts `lessonCompleted`; it is a failsafe test needing a running server, so use it as the "did I break the lesson" guard, never as the RED. StartWebGoat and FileServer are plain infrastructure with no lesson at stake.

Settling such a marker NOT-A-BUG because "it didn't throw" repeats the charset mistake in a new costume.

WHAT GOES WRONG HERE.
- Reaching for MockMultipartFile, seeing no NPE, and settling the marker false. The null-to-"" coercion in its constructor makes the RED look GREEN before any fix exists. This is the single most likely way to get a ProfileZipSlip-shaped marker wrong.
- Asserting the marker back at itself: `assertThat(file.getOriginalFilename()).isNull()`, or asserting only that a mock you told to return null produced an NPE, with nothing said about the endpoint. The RED must call the production method (uploadFileHandler, printStartUpMessage, importFile) and the GREEN must assert the real alternative outcome — the `path-traversal-zip-slip.no-zip` AttackResult with lessonCompleted=false, the logged https URL — not the absence of an exception.
- "Fixing" with `Objects.requireNonNull(file.getOriginalFilename())` or an `assert`: still an NPE, the RED stays red, nothing settled.
- Swapping `getOriginalFilename()` for `getName()` in ProfileZipSlip. getName() is the form field name, `uploadedFileZipSlip`, which never ends in `.zip`, so the gate rejects every upload and the zip-slip assignment becomes unsolvable — while the unit test still passes.
- Overclaiming reachability: writing "a request with no filename crashes the endpoint" when Spring never binds a nameless part to a MultipartFile parameter. That is a RED that could not fail for the reason given.
- On StartWebGoat:44, fixing `url` while missing that `sslEnabled ?` unboxes a nullable Boolean on the same line, or the reverse. Both dereferences are the flagged construct.
- Settling NOT-A-BUG because "the property is set in application-webgoat.properties", or because "on some path" sounds hypothetical. The shipped defaults are why the RED is a contract test rather than a crash report; they are not a reason the construct is safe.
- Silencing instead of fixing: wrapping the body in `try { } catch (NullPointerException e)`, or deleting a null check elsewhere so the analyser's path disappears. In the lesson endpoints a blanket catch also swallows the failure feedback the assignment depends on.
- Assuming that because the file sits under lessons/pathtraversal everything in it is intentional. The traversal is; a missing null check on a Spring accessor is not. Read what the assignment actually needs before deciding either way.
