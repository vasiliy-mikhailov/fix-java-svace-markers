An OS or JDBC handle — file descriptor, socket, archive file, Connection/Statement/ResultSet — acquired and then abandoned along a path where an exception is thrown before anything releases it. The report anchors on the ACQUISITION, not on the throwing call and not on the place a close is missing, so the enclosing method must be read in full before the marker can be judged. The `.EXCEPTION` suffix names the witness path, not the absence of a close: it fires both when a close() exists but sits only on the normal path (last statement of a try block, after a loop, in one branch of an if) and when there is no close anywhere, since a never-closed handle also leaks exceptionally. Plain HANDLE_LEAK is the handle released on no path at all; this one is about the throwing path, so drive that path or you have not shown what was reported.

SETTLE OWNERSHIP FIRST. Much of this family is refuted there, and a refutation with the right reason is worth more than a RED that could never have failed. Ownership belongs to the callee, so read the callee instead of recalling it: some helpers close a stream handed to them and close it on the exception path too, which appears as a close inside the callee's exception table when the javadoc is silent, while others document the opposite — `Files.copy(InputStream, Path, CopyOption...)` never closes what it reads. And JDBC transitivity is not a law of the language. A pooling DataSource usually hands out a proxy Connection that tracks its statements and closes them on return; a plain non-pooling one hands out the raw driver object, and closing it ends the session while the statement handles go on reporting `isClosed() == false`. A pool present in the dependency tree is not a pool in the path — find the DataSource actually constructed, because where ownership is not transitive an outer try-with-resources on the Connection does not save the statements created inside it.

MAKING AN OS HANDLE VISIBLE. These types mostly have no isClosed(), so count descriptors: sample `((com.sun.management.UnixOperatingSystemMXBean) ManagementFactory.getOperatingSystemMXBean()).getOpenFileDescriptorCount()` around a loop that drives the throwing path a few hundred times, and assert a threshold, never an exact delta. That bean ships with the JDK, works on Linux and macOS and has no Windows equivalent, so guard with an assumption. Its honest weakness: several JDK handle types register a Cleaner and self-close once unreachable, so a collection between the two readings closes the handles being counted. Never call System.gc() or a helper that might, keep the loop large relative to the tolerance, and treat a marginal delta as inconclusive. For a thrown failure instead of a threshold, fork — a child JVM under `ulimit -n <small>` turns the leak into a hard "Too many open files"; the limit is process-wide and cannot be lowered in-process, and a test is allowed to start a JVM.

FOR JDBC HANDLES, ASK THE HANDLE. isClosed() exists on Connection, Statement and ResultSet. Where the DataSource is injectable, supply one whose Connection is a delegating wrapper recording every Statement it issues, drive the throwing path, then assert isClosed() on the recorded handles. Either result is an answer: false is the defect where ownership is not transitive, true is the refutation where it is. Neither is "the harness cannot observe this", and false is not evidence that the wrong handle was instrumented.

WHAT GOES WRONG HERE.
- Asserting the marker back at itself: asserting the source text contains "try (", or verifying close() on a stream the test injected where production has no injection point. A mock at a seam that does not exist proves only that the mock was called.
- "No close() on this line, therefore a leak." The next line may hand the handle to a callee that closes it on both paths. Mirror trap: a correct try-with-resources a few lines above reads as proof the author knew better and slipped here, and is evidence of nothing either way.
- Assuming a try-with-resources on the flagged line means the site is fine. These reports routinely land on an outer resource while the complaint is about a handle created inside it.
- Line drift: markers are produced against a copy that may be formatted differently, so the flagged line can acquire nothing at all. A test that closes over every handle the method opens settles the marker under either reading.
- Treating an unreachable throw as a witness. If the only call between acquisition and handoff throws solely for arguments that are constant here, the exceptional path does not exist — refute on unreachability and name the throw you ruled out, rather than "no test could be written".
- Intent in either direction. The name, package, directory or reputation of the surrounding code does not make a handle lifetime deliberate; intent is shown by something checked in that DEPENDS on the handle outliving the method — documentation telling a caller it must close what it received, a test asserting that, a comment or suppression naming the choice. Absent that the identical construct is an ordinary defect, and the inverse is no safer: an unclosed reader inside code that looks important is still an unclosed reader. Check whether any observable result depends on handle state before claiming design, and verify per marker that the close you add does not change what the method returns.
