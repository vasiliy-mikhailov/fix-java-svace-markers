HANDLE_LEAK.EXCEPTION marks an OS or JDBC handle — file descriptor, socket, ZipFile, Connection/Statement/ResultSet — that is acquired and then abandoned along a path where an exception is thrown before anything releases it; the report anchors on the *acquisition* line, not on the throwing call and not on the place a close is missing, so the enclosing method has to be read in full before the marker can be judged. The `.EXCEPTION` suffix names the witness path, not the absence of a close: it fires both when a `close()` exists but sits only on the normal path (last statement of a try block, after a loop, inside one branch of an if) and when there is no close anywhere, since a never-closed handle also leaks exceptionally. It is not the neighbouring "you didn't use try-with-resources" style complaint — a try-with-resources on an *enclosing* handle frequently does discharge it, because JDBC ownership is transitive, and that is the difference between the true and false positives in this family.

HOW YOU MAKE IT VISIBLE.
SETTLE OWNERSHIP FIRST. Most of this family is refuted there, and a refutation with the right reason is worth more than a RED that could never have failed.

Three ownership facts, each checked against the artifacts on disk, not from memory:

(1) Spring's FileCopyUtils closes what you hand it. `javap -c org/springframework/util/FileCopyUtils.class` out of spring-core-7.0.8.jar shows `copyToByteArray(InputStream)` wrapping `readAllBytes()` in a try-with-resources, and `copy(InputStream, OutputStream)` closing both — in each case the `close()` appears on the exception-table path, not only the fallthrough. So ProfileUploadBase:126 (`getResourceAsStream` → `FileCopyUtils.copyToByteArray` on the next line) leaks on NO path, throwing included, and the null case is handled too (`copyToByteArray(null)` returns `new byte[0]`). Settlement: refuted, evidence = the callee's bytecode, no JUnit run involved. Do NOT generalize this: `java.nio.file.Files.copy(InputStream, Path, CopyOption...)` explicitly does not close the stream, which is why ProfileZipSlip:80–81 accumulates entry streams.

(2) JDBC ownership is transitive and it is honoured in this app. Closing a Connection closes its Statements; closing a Statement closes its ResultSet. WebGoat runs Spring Boot's default HikariCP (HikariCP is in the resolved tree) behind `LessonDataSource`, whose `getConnection()` returns a `java.lang.reflect.Proxy` forwarding every call — `close()` included — to the Hikari proxy connection, which tracks the statements it hands out and closes them when the connection is returned. So in SqlInjectionChallenge the `Statement`, `ResultSet` and `PreparedStatement` created inside `try (Connection connection = dataSource.getConnection())` are all released on the throwing path, because the try-with-resources close IS the finally path. Refuted.

(3) A handle nothing owns is a real leak and the flag stands. `ProfileZipSlip.processZipUpload` opens `new ZipFile(...)` at :75 with no `close()` anywhere in the method, and `catch (IOException e)` at :85 returns with the handle live. `VulnerableTaskHolder`:68 has the same shape — the `BufferedReader` over the child process's stdout is abandoned when `readLine()` throws into the catch at :73.

MAKING A REAL ONE VISIBLE. `ZipFile` has no `isClosed()`, so count descriptors:

  var os = (com.sun.management.UnixOperatingSystemMXBean) ManagementFactory.getOperatingSystemMXBean();
  long before = os.getOpenFileDescriptorCount();
  for (int i = 0; i < 300; i++) { /* drive the endpoint down the throwing path */ }
  assertThat(os.getOpenFileDescriptorCount() - before).isLessThan(20);

`com.sun.management.UnixOperatingSystemMXBean` ships with the JDK and works on Linux and macOS; no new dependency. Arranging the throwing path for zip-slip is cheap: a zip entry named `sub/x.jpg` where `sub` was never created makes `Files.copy` at :81 raise `NoSuchFileException` into the swallowing catch. Drive it through the wiring the app actually uses — `ProfileUploadTest` extends `LessonTest` and posts a `MockMultipartFile` through MockMvc; copy that seam rather than calling the private method reflectively.

FOR JDBC HANDLES, don't count fds — ask the handle. `Statement.isClosed()`, `ResultSet.isClosed()` and `Connection.isClosed()` are real JDBC 4 methods, and `LessonDataSource` is constructor-injected, so a test can supply a DataSource whose Connection is a delegating wrapper recording every Statement it returns; `LessonConnectionInvocationHandler` is that exact wrapper pattern, already in the tree. Assert `isClosed()` on the recorded handles after the endpoint returns. Expect GREEN before any fix — that is fact (2) established by measurement instead of assertion, and it is the correct settlement, not a failed attempt.

THE FD TEST'S HONEST WEAKNESS: `ZipFile` and `FileInputStream` both register JDK Cleaners, so a GC between the two readings closes the very handles being counted. Never call `System.gc()`, keep the loop large relative to the tolerance, and treat a marginal delta as inconclusive. When a threshold isn't good enough and you want a thrown failure, fork: `ProcessBuilder` running `sh -c "ulimit -n 64 && exec java -cp <cp> Runner"` turns the leak into a hard `Too many open files`. The fd limit is process-wide and cannot be lowered in-process — a test may start a JVM.

FIXING ONE DOES NOT DISARM A LESSON. Handle lifetime is orthogonal to what these assignments teach: closing the `ZipFile` leaves zip-slip fully exploitable, because the traversal lives in `new File(tmpZipDirectory.toFile(), e.getName())`, not in how long the handle stays open. Verify per marker all the same that the close you add doesn't change the `AttackResult` returned, since the `LessonTest` suites assert on `lessonCompleted` and `feedback`.

WHAT GOES WRONG HERE.
- Asserting the marker back at itself: a test that reads the .java file and asserts it contains "try (", or `verify(mockStream).close()` on a stream the test injected where production has no injection point. `defaultImage()` gets its stream from `getClass().getResourceAsStream` — there is no seam, so a mock there only proves the mock was called.
- "No close() on this line, therefore leak." ProfileUploadBase:126 hands the stream to `FileCopyUtils.copyToByteArray` on the very next line, which closes it on both paths. Read the callee before writing RED. The mirror-image trap: ProfileUploadBase:112, fourteen lines up, does use `try (var inputStream = new FileInputStream(...))`, and it is tempting to read that as proof the author knew better so :126 must be the slip. It is evidence of nothing either way.
- Line drift. The SqlInjectionChallenge marker says line 56, but line 56 in this checkout is `if (attackResult.assignmentSolved()) {`, which acquires no handle at all. The file carries two blank lines spotless would delete (line 16, between the `java.sql` and `org.owasp` imports; line 38, between the annotation block and the class declaration); in canonical formatting line 56 is `try (Connection connection = dataSource.getConnection()) {`, which is line 58 here. Writing the note or the test off the literal `if` yields a RED about nothing.
- "The default charset mistake" in a new costume: "the fd limit is process-wide, so no test can vary it." True in-process, and the conclusion does not follow — fork a JVM under `ulimit -n`.
- A verdict word that does not follow: an fd-delta or `isClosed()` test that comes back flat/closed is NOT "the harness can't observe this". Under try-with-resources plus Hikari's statement tracking, flat IS the answer, and the settlement is refuted-with-reason.
- Assuming try-with-resources on the flagged line means "already fine". The marker anchors on the acquisition, and .EXCEPTION reports routinely land on an outer `try (Connection ...)` while the checker's complaint is about a handle created inside it. Identify which handle the trace is about before deciding.
- Over-claiming lesson intent in either direction. "WebGoat is deliberately vulnerable, so this is on purpose" does not hold here: no assignment grades a student on a leaked descriptor, and none of the `AttackResult` branches in these methods reference handle state. Nor is the inverse safe — `VulnerableTaskHolder`:68 sits inside the insecure-deserialization lesson and its unclosed reader is still just an unclosed reader.
- Assuming an unreachable throw is still a leak. `LessonDataSource.getConnection()`:27 acquires `targetConnection` and would leak it if `Proxy.newProxyInstance` threw, but that call throws only `IllegalArgumentException` for a malformed interface array, and the array here is a compile-time constant. Refuted on unreachability — say that, rather than "no test could be written".
