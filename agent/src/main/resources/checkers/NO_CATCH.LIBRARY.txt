\bnew\s+(?:File|FileInputStream|FileOutputStream|FileReader|FileWriter|RandomAccessFile|Scanner|URI|URL|ProcessBuilder)\s*\(|\b(?:Integer|Long|Double|Float)\.parse[A-Za-z]+\s*\(|\b(?:URI|UUID)\.(?:create|fromString)\s*\(|\bEnum\.valueOf\s*\(|\bPaths\.get\s*\(
A call to a JDK or third-party method on the flagged line can raise an exception that no handler between that call and the top of the enclosing method covers, so it escapes. The `.LIBRARY` suffix names the ORIGIN of the exception — an unanalyzed library method, identified from its documented `@throws` — not the absence of a `try`. That is the whole difficulty of this family: a `try/catch` is usually sitting right there on the flagged line and is irrelevant, because it names a checked type while the escaping exception is unchecked. Do not confuse it with the swallowed-exception family (empty or over-broad `catch`), which complains that something WAS caught and discarded; this one complains that nothing catches it at all.

HOW YOU MAKE IT VISIBLE.
Work the line in three steps: list the LIBRARY calls on it, since project methods are not the origin the checker means; read their javadoc `@throws` including the unchecked ones — a constructor raising NullPointerException on a null argument, a parse method raising NumberFormatException, a factory raising IllegalArgumentException on a malformed string; then find which of those types no enclosing `catch` covers.

The observable is NOT the exception — it is the intent of the surrounding control flow. Where the enclosing method means "for each input, do the work, or report an error and move to the next", an unchecked escape aborts the whole thing and THE LATER INPUTS ARE NEVER PROCESSED. Assert that: the work that silently did not happen, observed wherever the method reports its results. Pair it with a control that must pass on today's code — feed an input raising a type the existing handler DOES cover and check the remaining inputs still complete. Without the control, a RED caused by a broken fixture is indistinguishable from the defect. GREEN is a handler covering the unchecked type as well while keeping the report-and-continue behaviour, not one that turns the loop into an abort.

A `public static` method is directly callable from a test, and that is what makes such a probe legitimate — it is public API of the class. Say so plainly rather than implying the runtime environment could really supply the argument you passed.

WHAT GOES WRONG HERE.
- "There is a `try` right here, false positive." The commonest wrong verdict on this family. A handler for a checked type is walked straight past by an unchecked one; presence of a handler is not coverage of the type.
- Widening to `catch (Exception e)` and then asserting "no exception is thrown". That asserts the marker back at itself and swallows real failures. The behavioural claim is that the remaining work still gets done, so assert the work.
- Asserting on the exception's message. Many JDK exceptions are thrown with no message at all, so a handler printing getMessage() prints null; assertions on message content are fragile, assert the effect.
- Reaching for a SecurityManager to provoke an unchecked SecurityException. On current JDKs a SecurityManager can no longer be installed, so that arrangement is a dead end whatever the code looks like.
- Hunting for input DATA that makes the project's own algorithm throw. This exception originates in the library call on the flagged line; auditing the surrounding computation for an overflow is work on a different marker.
- "The runtime could never supply that argument, therefore unprovable." True premise, wrong conclusion — the same shape as calling a defect unobservable because a JVM-wide setting is fixed at start-up. A test may call the method directly with the argument the library documents as fatal.
- Wrong axis on intent. That the enclosing code deliberately demonstrates a weak algorithm or an insecure practice says nothing about whether an uncaught library exception in it is deliberate; this checker is about the handler. Decide that per call site, and check first whether anything depends on the behaviour the fix would change.
