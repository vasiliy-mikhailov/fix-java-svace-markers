The claim is about an ARGUMENT: at the flagged call the analyzer believes some value passed in can be
null, and the callee dereferences that parameter or declares it non-null — `new String(bytes, UTF_8)`
where `bytes` is reachable as null, not `bytes.length` on a null receiver. The anchor is the call
site, not where the null was produced and not where the NPE is thrown; the throw lands one frame
deeper, inside the callee. Checkers with similar names make different claims and must be settled
separately: DEREF_AFTER_NULL, DEREF_OF_NULL.RET(.LIB) and NP_NULL_ON_SOME_PATH_FROM_RETURN_VALUE are
about a receiver or a returned value dereferenced in this method's own frame. Two markers sitting on
one statement are two claims, and answering one does not answer the other.

TELLING THE FAMILY APART WHEN IT ACTUALLY THROWS. A helpful NullPointerException (JEP 358) names the
CALLEE'S parameter — `Cannot read the array length because "bytes" is null` — and the throwing frame
is inside the callee, with the flagged line the frame below. A receiver dereference instead reads
`Cannot invoke "X.y()" because "<local1>" is null` and throws in the flagged frame itself. Use that
to identify what you are looking at; do not assert on the message.

HOW YOU MAKE IT VISIBLE. Reach the null-producing path with real objects where you can — a `catch`
that returns null is reached by an input that makes the guarded call fail — and otherwise stub the
collaborator that hands the null over. Then assert the method's CONTRACT: a fallback value, a
non-null return, a defined outcome. That errors with the NPE before the repair, passes after, and
does not pin one particular repair. `assertThrows(NullPointerException.class, ...)` is the wrong
assertion and the one most likely to be reached for: it is GREEN on the broken code and RED after the
fix, which is asserting the marker back at itself. Where the flagged call also carries intended
behaviour, pin that behaviour in the same test, so the repair cannot be a guard that quietly disables
the feature instead of fixing the null.

A FIX THAT CHANGES NOTHING OBSERVABLE MEANS THE FINDING IS REFUTED, NOT FIXED. String concatenation
never evaluates to null (JLS 15.18.1), so a null check on a concatenated argument cannot be
distinguished before from after by any test. The same holds for an argument that is only null on a
path no caller can produce — a private helper whose every call site passes a substring, a library
method the analyzer mis-modelled as nullable. The settlement there is a refutation naming the
unreachable path, not a defensive `Objects.requireNonNull`.

CHECK THE LINE STILL HOLDS THE CONSTRUCT BEFORE SPENDING A BUILD. Analyzer output can be produced
against an older tree than the checkout, and the reported line is the FIRST line of the statement —
under a wrapping formatter that is often just the assignment head (`var x =`) with the call on the
next line. So do not conclude "the arguments here are obviously non-null" from the flagged line
alone. Read the line's history: if a later commit interposed the guard, that is still provable
honestly, by the same test passing at the checkout and failing against a copy of the pre-commit
method body compiled in a scratch directory, with the repository untouched.

Grepping for "NullPointerException" is a trap; it lands on the exception name inside a log message or
a canned stack-trace string, where nothing is dereferenced at all.
