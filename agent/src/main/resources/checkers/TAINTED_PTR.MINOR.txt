\b\w*(?:[Ee]xecute|[Pp]repareStatement|[Qq]uery)\w*\s*\(\s*[A-Za-z_$][\w$]*\s*[,)]
A taint-flow finding, not a null-pointer one: a value that entered from the HTTP request reaches a sensitive use — here a JDBC statement — with no validation and no parameter binding between source and sink. The anchor line is frequently the FORWARDING call rather than the sink: the flagged line is `return injectableQuery(query);` (SqlInjectionLesson5.java:57), which contains no SQL at all; the sink is `statement.executeQuery(query)` eight lines below at :65, on a `Statement` created with TYPE_SCROLL_INSENSITIVE/CONCUR_UPDATABLE. Distinguish from its siblings: plain TAINTED_PTR (Critical) and TAINTED_PTR.COOKIE (Major, source is a `@CookieValue` parameter) are separate checkers with separate notes — and the `.MINOR` suffix grades confidence in the SOURCE, not damage at the sink, which is why the one `.MINOR` marker here (an unannotated `String query` parameter on a `@PostMapping`, bound implicitly) reaches a far rawer sink than the Critical ones, which all sit on explicit `@RequestParam` values.

HOW YOU MAKE IT VISIBLE.
THE OBSERVABLE IS DATABASE STATE, NOT THE HTTP RESPONSE. Measured on the real endpoint: POST /SqlInjection/attack5 with `query=drop table access_log` returns HTTP 200, `"lessonCompleted": false`, body `"Your query was: drop table access_log"` — and the table is genuinely gone. Confirmed by listing `TABLE_SCHEM from INFORMATION_SCHEMA.SYSTEM_TABLES where TABLE_NAME='ACCESS_LOG'`: `[webgoat-user test]` before the POST, `[webgoat-user]` after. An assertion on status code or body would have watched a successful destructive injection and called it a failure, because `injectableQuery` catches every exception (lines 71-76) and reports the same shape whether the statement ran, ran destructively, or blew up.

ARRANGEMENT that works: extend `org.owasp.webgoat.container.plugins.LessonTest` (SpringBootTest on `WebGoat.class`, `@WithWebGoatUser`, per-user Flyway migration, `mockMvc` ready in `@BeforeEach`), `@Autowired LessonDataSource dataSource`, POST the parameter through mockMvc, then read `INFORMATION_SCHEMA` yourself via `dataSource.getConnection()`. Connections are proxied by `LessonConnectionInvocationHandler`, which issues `SET SCHEMA "<username>"` on every call, so the verification query lands in exactly the schema the endpoint wrote to. About 7-9s per class. Note the column is `TABLE_SCHEM`, not `TABLE_SCHEMA`.

FOR THIS MARKER THAT TEST ALREADY EXISTS AND IS GREEN — asserting the defect works. `src/test/java/org/owasp/webgoat/lessons/sqlinjection/introduction/SqlInjectionLesson5Test.java:32` (`grantSolution`) posts `grant select on grant_rights to unauthorized_user` and asserts `lessonCompleted` is TRUE; I ran the class: 3 tests, 0 failures, 7.2s. `SqlInjectionLessonIntegrationTest` (sql_5, lines 18 and 52) asserts the same over real HTTP. `checkSolution` at :79-92 exists solely to detect the injected GRANT and reward it, and `SqlInjection_introduction_content4.adoc` tells the student: "Try to grant rights to the table `grant_rights` to user `unauthorized_user`". So there is no honest RED here: the only test that fails-then-passes is one asserting the endpoint REJECTS arbitrary SQL, and making it pass breaks `grantSolution`, `differentTableShouldNotSolveIt`, `noGrantShouldNotSolveIt` and the integration test. Settle by-design citing the .adoc and the green tests — the citation, not a build, is the evidence.

DO NOT GENERALIZE THAT TO THE FAMILY. Outside an assignment the identical construct is an ordinary defect and the arrangement above is a real RED. Apply this test, in order, to the enclosing class: (1) does it implement `AssignmentEndpoint` / carry `@AssignmentHints`, and does its own success check reward the injected effect? (2) is there a lesson doc under `src/main/resources/lessons/**/documentation` instructing a student to send this payload to this endpoint? (3) does a checked-in test assert the attack SUCCEEDS? Any yes and the flow is the assignment. All no — container code, controllers, resolvers, the admin panel, the whole `src/test` tree — and it is a plain defect, provable and fixable normally. Package name is NOT the discriminator: `lessons/sqlinjection/mitigation/Servers.java` sits in a package called "mitigation" and its `SqlInjection_order_by.adoc` still says "try to perform an SQL injection through the ORDER BY field".

WHAT GOES WRONG HERE.
"PTR" reads as pointer, so agents test the null path. Measured: omit the parameter entirely — it is an unannotated `String query`, so Spring binds it required=false to null — and you get HTTP 200 with `"…SqlInjectionLesson5 : General error<br> Your query was: null"`. The catch at :71-76 swallows it; nothing escapes, there is nothing to assert, and that construct belongs to DEREF_OF_NULL anyway.

Importing the shell-injection habit. A `;`-chained payload here does actually reach the second statement (HSQLDB answered `object not found: ACCESS_LOG in statement [drop table access_log]` after I had already dropped it), so the mirror-image mistake is available too — but chaining is beside the point: the parameter IS the whole statement, and the payload that proves anything is a bare `grant …` or `drop table …`. Choosing a payload by analogy to metacharacters instead of by reading `executeQuery(query)` is how a RED ends up unable to fail for the right reason.

Asserting the marker back at itself. A test that posts an injection payload and asserts 200-and-success is green on its first run and stays green after any change that leaves the response shape alone; it demonstrates the flow and proves nothing about a fix. Likewise, swapping `createStatement()` + `executeQuery(query)` for `prepareStatement(query)` is not a fix — the entire string is user-supplied, there is no structure left to bind, and `grantSolution` keeps passing.

Reading only the flagged line. Line 57 has no SQL on it; an agent that stops there settles "no sink, not a defect". Across this family the anchor lands variously on a parameter declaration (JWTVotesEndpoint.java:135, the `@CookieValue` line), on the sink (Servers.java:54, `executeQuery()`), or on a line that is blank in the current checkout (SpoofCookieAssignment.java:55 — the scan ran on another revision, so line numbers drift). Read the enclosing method in both directions before concluding anything.

Treating "flagged" as "uniquely bad". The identical `return injectableQuery(query);` line appears unflagged at SqlInjectionLesson2.java:43, Lesson3.java:38, Lesson4.java:39 and Lesson10.java:44. A missing marker on a sibling is not a verdict about the sibling, and a marker here is not evidence this one differs from them.
