(?:\bnew\s+\w*(?:InputStream|OutputStream|Reader|Writer)\s*\()|(?:\.\s*(?:prepareStatement|prepareCall|createStatement|executeQuery|getConnection|getInputStream|getOutputStream|newInputStream|newOutputStream|newBufferedReader|newBufferedWriter)\s*\()|(?:\b(?:Connection|(?:Prepared|Callable)?Statement|ResultSet|\w*(?:InputStream|OutputStream|Reader|Writer))\s+\w+\s*=\s*$)
SpotBugs OBL_UNSATISFIED_OBLIGATION ("method may fail to clean up stream or database resource") runs
a dataflow over one method and reports the line that ACQUIRES a tracked resource — Connection,
Statement/PreparedStatement, ResultSet, InputStream/OutputStream/Reader/Writer — when some path
leaving that line reaches the method exit with the resource still open. The flagged line is the
acquisition, not the leak. Where several resources sit on or near it, work out which one is unguarded
before answering: a connection already inside try-with-resources discharges its own obligation while
the statement born from it does not, and on an `executeQuery` line the obligation reported may be the
ResultSet's. It is not the stream-only OS_OPEN_STREAM nor the JDBC-only ODR_OPEN_DATABASE_RESOURCE,
and the ..._EXCEPTION_EDGE sibling is the same claim restricted to the thrown-exception edge. It is
also not a style rule demanding try-with-resources: a resource returned to the caller, or passed to a
callee that closes it, discharges the obligation with no try block anywhere.

HOW YOU MAKE IT VISIBLE. close() is an ordinary method call, so the observable is whether it was
invoked on the object the flagged line produced — but only if you hold that object. Driving the code
end-to-end against a real backend is GREEN before and after, because the handle is never exposed and
the objects simply become unreachable. The discriminating power comes entirely from interposing
something that captures the resource: a fake or recording wrapper injected where the code takes its
factory — a data source, a resource loader, any collaborator passed in — or a dynamic proxy that
delegates to the real thing and records every close(). Then assert that this resource was closed
after the method under test returned. The stronger form, and the one matching what the detector
claims: program the fake so the operation throws, and assert the resource was closed anyway; that
fails even where the happy path happens to close.

A chained acquisition, consumed by the next call without ever being assigned, offers no local to
assert on — but "never given a name" does not mean "cannot be shown": the fake holds the reference
the source never names, and only the FIX has to introduce a local first. What is genuinely awkward is
a resource produced by a static factory with nothing to interpose on; settle that on the read.

WHERE IT CANNOT BE SHOWN, AND WHAT TO DO INSTEAD. When the acquisition goes straight into a callee
that closes it — a copy helper closing both ends is the common case — read the callee; a test
asserting the resource ends up closed is then a refutation of the marker, not a proof of it. When the
resource is returned, the obligation transfers to the caller, the demonstration belongs at the
caller, and closing it locally hands the caller a dead object. When the acquisition sits in code
nothing constructs — a fixture hook, a lifecycle callback with no injection point — there is no fake
to inject and no RED available; settle on the read.

WHAT GOES WRONG HERE.
- Asserting the marker back at itself: checking that the CONNECTION is closed, that no exception was
thrown, or that the feature still works. All GREEN before any change. The only assertion carrying
information is about the resource the marker names.
- Fixing the neighbour instead of the finding. The acquisition line very often also builds the query,
path or command, and "while I'm here" turns into changing that. The obligation fix is the
try-with-resources head and nothing else; the string on that line must come out identical. The
converse error is as bad: an unclosed resource is nobody's intended behaviour, so "this code is
deliberately odd" settles nothing here.
- Wrapping a resource that escapes, so the caller receives a closed handle and fails where it reads.
Right instinct, wrong site.
- "Resource leaks need a profiler, not a unit test." A true premise (a leak is a heap fact) with a
conclusion that does not follow: close() is a method call, and interposition makes it observable.
- Settling it as a false positive because the enclosing connection's try-with-resources closes the
children anyway. That is an argument about IMPACT, and weaker than it sounds — a driver may leave the
child reporting isClosed() false, and a pooled connection may not cascade at all. If you settle,
settle on the callee-closes or returned-resource facts.
- "OBL is an experimental, try-with-resources-noisy detector, therefore false positive." Noisiness is
a prior, not evidence; twenty lines of reading tell you whether the acquisition escapes unclosed. The
regex will likewise sometimes land on an in-memory writer owning no OS or database handle — say that
because you read it, not because the detector has a reputation.
