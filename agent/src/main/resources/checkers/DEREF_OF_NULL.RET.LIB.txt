The checker asserts that a value returned by a *library* method whose contract permits null (JDK or third-party — not a value this code produced) is used without a null check: dereferenced with `.`, indexed, or passed into a parameter that forbids null. The nullable term is the library call itself, not the receiver it hangs off — on ProfileUploadBase.java:86 the nullable term is `getParentFile()`, while the adjacent `getCanonicalFile()` in the same chain never returns null (it throws IOException). Do not read it as a flow finding about a null the code assigned itself, and do not read it as "this line NPEs": it says the library is *permitted* to hand back null here, which is a claim about the API contract, not about reachability.

HOW YOU MAKE IT VISIBLE.
The observable is a `java.lang.NullPointerException` thrown at the flagged line. A RED test must do two separate things, and for this family they fail for different reasons: (a) drive the library call to actually return null, and (b) reach the flagged line with it. Work them in that order.

STEP 1 — name the nullable term and look up when it is really null. `File.getParentFile()` returns null only when the pathname has no parent segment: the Unix root `/`, or a bare relative name like `foo.txt`. `File.listFiles()` returns null when the receiver is not a directory or an IO error occurs (probe-verified: `new File(dir,"plain.txt").listFiles()` → null). `Class.getResourceAsStream`, `MultipartFile.getOriginalFilename` (Spring @Nullable), `HttpServletRequest.getHeader/getParameter`, `System.getProperty/getenv` are genuinely nullable. `File.getCanonicalFile()/getCanonicalPath()` and `ResourceLoader.getResource()` are NOT — the first throws IOException, the second returns a possibly-nonexistent Resource. Guarding one of those is a fix that changes nothing.

STEP 2 — check whether the receiver can be in that state. This is what settles the two flagged lines, and the answers differ. Line 82's receiver is `new File(uploadDirectory, fullName)` (line 51). I probed the constructor: `new File(parent, child)` always resolves to `parent.path + "/" + child` (empty child yields the parent itself; a leading-`/` child is appended, not substituted), and `uploadDirectory` is `<webgoat.server.directory>/PathTraversal/<username>`. So the result always contains a separator and `getParentFile()` on line 82 is never null — there is no null to make visible. Line 86 is a different construct despite looking identical: `getCanonicalFile()` collapses `..`, and `new File(uploadDirectory, "../../../../../../../..").getCanonicalFile()` is `/`, whose `getParentFile()` IS null (probe-verified). WHAT GOES WRONG HERE.
1) Asserting the marker back at itself. `attemptWasMade` and `solvedIt` are private; the tempting RED is reflection (or a test subclass) invoking `solvedIt(new File("/"))` and expecting NPE. It passes — but what it asserts is that `new File("/").getCanonicalFile().getParentFile()` is null, a property of java.io.File. It is green against any implementation of this class and stays green if the fix is wrong. Manufacturing by reflection the precondition the production path forbids is not a demonstration.

2) Guarding the wrong term. On line 86 the chain is `getCanonicalFile().getParentFile().getName()`; only the middle call is nullable. A null check on `getCanonicalFile()` (or on `getCanonicalPath()` at line 82) is dead code that reads like a fix — those throw IOException, they never return null. And on line 82 `getParentFile()` itself is never null, because the receiver came from `new File(dir, child)`; a guard there is also dead.

3) `new MockMultipartFile("uploadedFile", null, ...)` to fake a filename-less part. Bytecode-verified in spring-test 6.2.19: the 4-arg constructor does `this.originalFilename = (originalFilename != null ? originalFilename : "")`. Null becomes `""`, the NPE at ProfileZipSlip.java:58 never fires, the test goes green, and the agent concludes "not reproducible" for a reason that is purely an artifact of the mock. Use a Mockito mock or a hand-written MultipartFile and call the method directly.

4) Expecting an NPE because a null reached a Spring utility. `FileCopyUtils.copyToByteArray(null)` returns `new byte[0]`; `StringUtils.arrayToCommaDelimitedString(null)` returns `""`. A RED written against ProfileUploadBase.java:127 or ProfileUploadRetrieval.java:117 can never fail. Concluding "no bug" from that no-fail is right by accident; the defensible statement is "the sink tolerates null", and it should cite the bytecode.

5) Verdict words that do not follow. "getParentFile() may return null" is a true JDK fact and gives you nothing about this line — the receiver's construction decides it. Symmetrically, "the existing tests never NPE" does not give "unreachable": ProfileUploadTest sends `../John Doe` and `../../test`, never a fullName that canonicalizes to root, so that suite was never evidence either way. Unreachability here rests on the `catch (IOException)` at ProfileUploadBase.java:63 swallowing the write to `/`, and that is what a note should record.

6) Lesson damage, but only where it applies. ProfileUploadBase.java lines 80-93 ARE the grading logic of the Path Traversal assignment: `attemptWasMade` picks "Nice try" over success, and `solvedIt`'s `.endsWith("PathTraversal")` is the win condition.
