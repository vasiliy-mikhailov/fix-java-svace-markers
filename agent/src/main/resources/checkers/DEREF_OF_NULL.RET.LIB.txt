\.(getParentFile|listFiles|getResourceAsStream|getResource|getOriginalFilename|getHeader|getParameter|getProperty|getenv|getModelAndView|getCookies)\s*\([^;]*\)\s*[.\[]|=\s*.*\.(getResourceAsStream|listFiles|getHeader|getParameter|getProperty|getenv|getOriginalFilename)\s*\(
A value returned by a *library* method whose contract permits null — JDK or third-party, not a value this code produced — is used without a null check: dereferenced with `.`, indexed, or passed into a parameter that forbids null. The nullable term is the library call itself, not the receiver it hangs off, and in a chain usually only one link is nullable. Do not read it as a flow finding about a null the code assigned itself, and do not read it as "this line NPEs": it says the library is *permitted* to hand back null here, which is a claim about the API contract, not about reachability.

HOW YOU MAKE IT VISIBLE. A RED must do two separate things, and they fail for different reasons: drive the library call to actually return null, and reach the flagged line with it. Work them in that order.

STEP 1 — name the nullable term and look up when it is really null. `File.getParentFile()` returns null only when the pathname has no parent segment: the root, or a bare relative name. `File.listFiles()` returns null when the receiver is not a directory or an IO error occurs. `Class.getResourceAsStream`, `getHeader`/`getParameter`/`getCookies`, `System.getProperty`/`getenv` and Spring's `@Nullable MultipartFile.getOriginalFilename` are genuinely nullable. `File.getCanonicalFile()`/`getCanonicalPath()` and Spring's `ResourceLoader.getResource()` are NOT — the first throws IOException, the second returns a handle to a resource that may not exist. Guarding one of those changes nothing.

STEP 2 — check whether the receiver can be in that state, because construction decides it. `new File(parent, child)` always resolves to parent plus separator plus child, so such a File always has a parent; one extra link flips the answer, since `getCanonicalFile()` collapses `..` and can land on the filesystem root, whose parent IS null. Two lines that read identically can settle differently for exactly that reason.

STEP 3 — reachability through a real entry point. An upstream operation may fail before the flagged line is reached, its throw caught and turned into an ordinary failure result. Cite the guard or the caught throw that stops the path: that is an honest unreachability finding, not a proof that no null exists, and not a passing test to be dressed up as one.

CHECK THE SINK BEFORE PREDICTING A CRASH. Some library sinks absorb null — Spring's `FileCopyUtils.copyToByteArray(null)` returns an empty array, `StringUtils.arrayToCommaDelimitedString(null)` returns `""` — so no exception is possible and the defect surfaces as degraded output, an empty body or an empty listing. Verify that against the version actually on the classpath, since it is version-specific. An absorbed null is still demonstrable when the null is certain rather than merely possible: the RED asserts the output is non-empty, and the GREEN makes the library call stop returning null. A guard that returns the same empty value leaves that RED red, which is the point — it pins the fix that removes the null instead of hiding it.

The cleanest end-to-end case in this family is a request value dereferenced directly, `request.getHeader("x").equals(literal)`: the client produces the null by omitting the header, and the fix inverts the comparison so the literal is the receiver. Where such a dereference sits in an `&&` chain, keep every other condition satisfied — a wrong earlier operand short-circuits before the dereference and hides the defect behind a passing test. Contrast the contract-only case, where a framework layer diverts the null-bearing input before it reaches this code; the defensible artifact there is a direct call with a hand-written value returning null, reported as exactly that, and not written up as a reachable attack. Where the nullable return is already checked, nothing is unprotected and a second guard is dead code that reads like a fix.

WHAT GOES WRONG HERE.
Asserting the marker back at itself. Reaching a private method by reflection or a test subclass and handing it the precondition the production path forbids gives a passing NPE test that asserts a property of the JDK — green against any implementation of the class, and still green if the fix is wrong.

Guarding the wrong term. Only one call in the chain is nullable; a check on a call that throws instead of returning null, or on a receiver whose construction guarantees non-null, is dead code.

Test doubles that sanitise your null. Some mock helpers normalise a null constructor argument to an empty string, so the NPE never fires and the run reads as "not reproducible" for a reason that is purely an artifact of the double. Use a Mockito mock or a hand-written implementation and call the method directly.

Verdict words that do not follow. "This method may return null" is a true library fact that tells you nothing about this line — the receiver's state decides it. Symmetrically, a suite that never sends the input which produces the null was never evidence of unreachability either way; unreachability rests on a named guard or a named caught throw.

Where the flagged line is part of the module's decision logic, a guard that flips a branch on an input currently accepted changes behaviour the module's own tests encode; confine any edit to the null case current inputs cannot reach. That caution does not generalise across the family.
