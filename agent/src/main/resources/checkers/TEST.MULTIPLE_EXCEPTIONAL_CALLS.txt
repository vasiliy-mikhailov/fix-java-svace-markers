assertThrows\s*\(|assertThatThrownBy\s*\(|expectThrows\s*\(|@Test\s*\(\s*expected\s*=|catch\s*\(
One exception expectation in a test standing over MORE THAN ONE call that could raise the expected type: an `assertThrows` / `assertThatThrownBy` lambda holding a chain like `((Contact) x.fromXML(s)).getFirstName()`, a JUnit-4 `@Test(expected=...)` over a whole method body, or `try { ...; fail(); } catch (X e)`. The complaint is not that the test fails — it is that when it passes you cannot tell WHICH call threw, so the green does not mean what the method name says. The neighbouring shape this gets confused with is an ordinary try/catch that merely handles an error: that is this construct only when the catch stands in for the expectation, and a catch that swallows and prints is a different defect (a test that cannot fail) which is worth reporting under its own name rather than this one.

HOW YOU MAKE IT VISIBLE.
READ THE CALLS IN ORDER FIRST, because most instances of this construct are harmless and the order is why. A later call runs only if the earlier one RETURNED, so a chain is ambiguous only when an earlier call can succeed while a later one throws something the expected type still accepts. Two things decide it: how wide the expected type is (`Throwable`, `Exception`, `RuntimeException` accept a `ClassCastException` from the cast or an NPE from the follow-on call; a narrow type like `StreamException` usually accepts only the one call that can produce it), and whether the assertions AFTER the expectation already pin the thrower — `assertThat(e.getCause().getMessage().contains("START_DOCUMENT")).isTrue()` identifies the parser and leaves nothing ambiguous.

HOW YOU MAKE IT VISIBLE, and it is NOT the usual RED-then-GREEN. Nothing in the product misbehaves; a test claims more than it checks, so the RED is against the test's own claim. Engineer an input on which the INTENDED call does not throw, and run two expectations against it: the flagged one goes green, and the narrowed one — `assertThrows(T.class, () -> onlyTheIntendedCall(input))` — goes red with "Expected T to be thrown, but nothing was thrown". That pair is the demonstration: the test survives a mutation it was written to catch. Verified by hand on this checkout (XStream 1.4.5, run under the surefire `--add-opens` line from pom.xml:551): `fromXML("<string>hello</string>")` RETURNS a `java.lang.String`, so the cast throws `ClassCastException` and `assertThrows(RuntimeException.class, () -> ((Contact) x.fromXML(p)).getFirstName())` is GREEN with nothing rejected at all — while `assertThrows(RuntimeException.class, () -> x.fromXML(p))` on the same input is RED.

WHEN NO SUCH INPUT EXISTS IT IS UNPROVABLE, and say which of the two reasons. Either no other call in the block can produce the expected type, or the intended call is the FIRST one and always throws, so the rest never execute — `fromXML("bullssjfs")` throws `StreamException` ("only whitespace content allowed before start tag ... position: START_DOCUMENT") and `getFirstName()` never runs. Unprovable is not the same as "the checker is wrong": the construct is there.

DO NOT REASON OUT WHICH CALL THROWS — RUN IT AND PRINT IT. The same expression throws from a different place depending on JVM flags. Under a bare `java`, XStream 1.4.5 dies in class initialisation (`ExceptionInInitializerError`, then `NoClassDefFoundError: TreeMapConverter`) — an Error, matching neither `RuntimeException` nor `StreamException`. Under surefire's `--add-opens java.base/java.util=ALL-UNNAMED` it gets as far as a `ConversionException` thrown by `fromXML` itself, so the second call in the chain is dead on today's JVM. Split the chain into separate statements in a scratch copy and print what each one returns or throws.

BEFORE ANY RED, CHECK THE FLAGGED TEST CAN FAIL AT ALL. `@Disabled`, a body with no assertion, or a `catch (Throwable t)` that prints and returns — VulnerableComponentsLessonTest:46-56 is exactly that, an enabled test whose handler swallows everything and whose `Disabled` import at line 12 is now unused. No observation made "inside" such a method counts for anything.

The component under test may be deliberately vulnerable — XStream is pinned at 1.4.5 in pom.xml:111 and the dynamic-proxy/EventHandler payload IS the lesson. That defends the payload and the pinned version; it does not defend an expectation that cannot say which call threw. A settlement that deletes the payload, widens `@Disabled`, or catches Throwable settles nothing.

WHAT GOES WRONG HERE.
Asserting the marker back at itself: a test that greps the source for `assertThrows` with two calls in the lambda, or counts calls by reflection. That asserts the checker's text, not a defect.

Splitting the chain and calling the split test's failure the RED. Moving the throwing call out of the expectation makes it fail by construction — that demonstrates your edit, not the defect. The RED must assert what the flagged test's NAME claims, on an input where the claim is false.

Calling it `by-design` because the payload is a deliberate WebGoat lesson. The pinned XStream 1.4.5 and the `calc.exe` proxy payload are intentional; the expectation's exception TYPE is not evidence anybody chose the ambiguity. `by-design` needs a comment, a suppression, or a name that says "any of these calls blowing up is the point".

Calling it provable from the first call alone. In `((Contact) x.fromXML(s)).getFirstName()` the second call cannot run if the first threw, so "two calls can throw" is not by itself an ambiguity — verify that an earlier call can SUCCEED on some input first.

Reading `@Disabled` as by-design. A disabled or swallow-everything test is a test that cannot fail; that is a reason no observation is available, not a reason the construct was intended.
