assertThrows\s*\(|assertThatThrownBy\s*\(|expectThrows\s*\(|@Test\s*\(\s*expected\s*=|catch\s*\(
One exception expectation standing over MORE THAN ONE call that could raise the expected type: an `assertThrows` lambda holding a chain like `((T) parse(s)).getField()`, a JUnit-4 `@Test(expected=...)` over a whole method body, or `try { ...; fail(); } catch (X e)`. The complaint is not that the test fails — it is that when it passes you cannot tell WHICH call threw, so the green does not mean what the method name says. An ordinary try/catch is this construct only when the catch stands in for the expectation; a catch that swallows and prints is a different defect, a test that cannot fail, and belongs under its own name.

READ THE CALLS IN ORDER FIRST, because most instances are harmless and the order is why. A later call runs only if the earlier one RETURNED, so a chain is ambiguous only when an earlier call can succeed while a later one throws something the expected type still accepts. The width of the expected type decides most of it: `Throwable`, `Exception` and `RuntimeException` accept a `ClassCastException` from a cast or an NPE from the follow-on call, while a narrow checked type usually accepts only the one call that can produce it. Assertions AFTER the expectation that check the message or the cause already pin the thrower and leave nothing ambiguous.

HOW YOU MAKE IT VISIBLE, and it is NOT the usual RED-then-GREEN. Nothing in the product misbehaves; a test claims more than it checks, so the RED is against the test's own claim. Engineer an input on which the INTENDED call does not throw, then run two expectations against it: the flagged one goes green, and the narrowed `assertThrows(T.class, () -> onlyTheIntendedCall(input))` goes red with nothing thrown at all. That pair is the demonstration — the test survives a mutation it was written to catch. When no such input exists the honest state is unprovable, and say which of the two reasons applies: no other call in the block can produce the expected type, or the intended call is the FIRST one and always throws, so the rest never execute. That is not the same as the checker being wrong; the construct is there.

DO NOT REASON OUT WHICH CALL THROWS — RUN IT AND PRINT IT. The same expression throws from a different place depending on the JVM, on the module opens the runner adds, and on what is resolved onto the classpath; a library that fails class initialisation raises an `Error` matching neither a `RuntimeException` expectation nor a narrow checked one. Split the chain into separate statements in a scratch copy and print what each one returns or throws. Check first that the flagged test can fail at all: with a disable annotation, no assertion, or a `catch (Throwable t)` that prints and returns, no observation made inside that method counts for anything.

WHAT GOES WRONG HERE.
Asserting the marker back at itself: grepping the source for an expectation with two calls in its lambda, or counting calls by reflection. That asserts the checker's text, not a defect.

Splitting the chain and calling the split test's failure the RED. Moving the throwing call out of the expectation makes it fail by construction. The RED must assert what the flagged test's NAME claims, on an input where the claim is false.

Calling it by-design from the reputation, name, package or directory of the code the test exercises, or because the test is disabled. Intent has to be shown by something checked in that DEPENDS on one expectation standing over several throwing calls — a comment or suppression naming the ambiguity, documentation saying the block is checked as a whole, an assertion on the message or the cause that already pins the thrower. Even a deliberate input only defends the input, not an expectation that cannot say which call threw. A test that cannot fail is a reason no observation is available, not evidence anybody chose the ambiguity — and deleting the input, disabling the test or widening the catch settles nothing.

Calling it provable from the first call alone. When the second call cannot run if the first threw, "two calls can throw" is not yet an ambiguity; verify that an earlier call can SUCCEED on some input.
