A value computed and stored into a variable no execution path can then read — an assignment or initializer overwritten on every path before any use, or one whose variable simply falls out of scope. The flagged line is an ordinary assignment to a local; the claim is about the dataflow around it, not about anything visible on the line. Do not confuse it with an unused VARIABLE, declared and never read anywhere, which is a weaker and different finding. And do not treat "assigned, then assigned again" as sufficient: an initializer that survives on even one path is live, so an `if / else if` chain with no final else leaves its initializer readable, and a `null` initializer that a following `if (x == null)` tests is read.

START FROM THE FACT THAT DECIDES MOST OF THESE. Deleting a dead store is behaviour-preserving by definition, so there is normally NO JUnit test that is RED before and GREEN after. Write that in the settlement instead of manufacturing a test; a test that passes before and after the fix has proven nothing.

WHAT YOU CAN ACTUALLY PUT IN JUNIT, in order of how often it applies. First, inertness of the guard: when the dead store is the whole body of a branch, that branch's condition provably cannot influence any observable output, and THAT is assertable — call the method twice with inputs differing ONLY in the flagged guard's truth value and assert the two results are equal. It is GREEN today, a characterization test rather than a RED, and its whole worth is its polarity, because it FAILS on the wrong repair described below. Second, when the discarded value came from a call with side effects (`x = it.next();`, `x = list.remove(0);`), the correct repair drops only the assignment, not the statement, and a test asserting the side effect still happened goes genuinely RED against an over-eager deletion. Third, when the dead store is inside a test method — `actual = f(a); actual = f(b); assertEquals(exp, actual);` — f(a) is never asserted and the coverage is fictional; perturb the first input, or break that path, and show the test still passes. In a test tree that is observable and is simply a bug.

CHECK WHAT HAPPENS IF THE VALUE BECOMES LIVE, because that is the repair an agent reaches for when it wants a RED. Making a discarded flag live is not a fix but a behaviour change, and the fact that the value is currently ignored may be exactly what keeps the surrounding feature working: a guard that starts suppressing a result its callers depend on can take a whole path out of service. A comment marking a method as scaffolding, or as not part of what the module is really about, is a reason to preserve its behaviour, not a licence to change it. Decide per site by asking what reads the variable, not by asking what repository you are in.

WHAT GOES WRONG HERE.
Asserting the marker back at itself: reading the file as text, or its bytecode, and asserting the assignment is gone. That tests your edit, not the defect, and the same trick "proves" any deletion.

Manufacturing a RED by making the dead value live and calling that the fix. The RED you get measures the behaviour you just introduced.

Concluding "no test can show it, therefore it is not a defect". The store is genuinely unreadable-from and removing it is right; only the "therefore" is wrong. Settle it as a behaviour-preserving cleanup that no test can distinguish, and say so explicitly.

Deleting a whole statement whose RHS advances an iterator, drains a queue, or otherwise mutates state — the assignment is dead, the call is not. And do not assume the flagged line is the only dead one: a declaration's initializer is often dead by the same argument as the assignment below it, so repairing one and leaving the other leaves the construct in place.
