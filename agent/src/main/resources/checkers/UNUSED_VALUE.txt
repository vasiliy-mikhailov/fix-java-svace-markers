UNUSED_VALUE flags a value that is computed and stored into a variable no execution path can then read — an assignment or initializer overwritten on every path before any use, or one whose variable simply falls out of scope. The flagged line itself is an ordinary assignment to a local; the checker's claim is about the dataflow around it, not about anything visible on the line. Do not confuse it with an unused *variable* (declared and never read anywhere, a weaker and different finding), and do not treat "assigned, then assigned again" as sufficient: an initializer that survives on even one path is live — `boolean allowed = true;` at src/main/java/org/owasp/webgoat/webwolf/requests/Requests.java:58 is followed by two assignments of `false`, but the if/else-if chain has no final else, so the initializer is read.

THE FLAGGED SHAPE. At AccountVerificationHelper.java:36, `likely = true;` is the entire body of `if (submittedAnswers.size() == secQuestionStore.get(verifyUserId).size())`, and the if/else at 39-50 assigns `likely` on BOTH arms immediately after. Nothing between them reads it. (Line 33's `boolean likely = false;` is dead for the same reason.)

START FROM THE FACT THAT DECIDES MOST OF THESE. Deleting a dead store is behaviour-preserving by definition, so there is normally NO JUnit test that is RED before and GREEN after. I measured rather than assumed: collapsing the method to `return contains0 && equals0 && contains1 && equals1;` produces identical results on every input I ran (2 wrong answers, 1 wrong answer, 2 foreign keys, 3 foreign keys, 2 correct answers — false/false/false/false/true both before and after). Write that in the settlement instead of manufacturing a test. A test that passes before and after the fix has proven nothing.

WHAT YOU CAN ACTUALLY PUT IN JUNIT, in order of how often it applies:

(1) Inertness of the guard — applies here. When the dead store is the whole body of a branch, that branch's condition provably cannot influence any observable output, and THAT is assertable. The class is a plain `new AccountVerificationHelper()` with a no-arg constructor, so no Spring context is needed (the existing BypassVerificationTest extends LessonTest and is a commented-out stub; ignore it and unit-test the helper directly). Call the method twice with inputs differing ONLY in the flagged guard's truth value: `{secQuestion0=x, secQuestion1=y}` (size 2, guard true) and `{secQuestion0=x}` (size 1, guard false). Both return false; assertEquals on the pair is an executable statement of the deadness. It is GREEN today — a characterization test, not a RED — and its whole worth is its polarity: it FAILS on the wrong repair described below.

(2) The discarded RHS has side effects. If the dead value came from a call that mutates something (`x = it.next();`, `x = list.remove(0);`), the correct repair drops only the assignment, not the statement, and a test asserting the side effect still happened goes genuinely RED against an over-eager deletion. Read the RHS before choosing a repair.

(3) The dead store is inside a test method. `actual = f(a); actual = f(b); assertEquals(exp, actual);` means f(a) is never asserted — the coverage is fictional. Demonstrate it by perturbing the first input, or breaking that path, and showing the test still passes. In the test tree this is observable and is just a bug.

CHECK WHAT HAPPENS IF THE VALUE BECOMES LIVE, because that is the repair an agent reaches for when it wants a RED. Here it is destructive and I measured it: change line 48's `} else {` to `} else if (!likely) {` and `didUserLikelylCheat({secQuestion2=x, secQuestion3=y})` goes false -> true. That map is the winning attack for the auth-bypass assignment — `verifyAccount` returns true for it because its `containsKey && !equals` tests are vacuous for absent keys — and `verifyAccount`'s own size check at line 59 means EVERY possible success submits exactly 2 answers. VerifyAccount.java:50 consults `didUserLikelylCheat` first and returns `failed(this).feedback("verify-account.cheated")`. So a live line 36 flags 100% of successes as cheating and no student can ever complete the lesson. The dead store is not itself a lesson — no assignment teaches "discard a value" — but it sits inside code a lesson depends on, and the comment at lines 30-31 ("not intended to be part of the 'vulnerable' code") marks this method as scaffolding, which is a reason to preserve its behaviour, not a licence to change it. Elsewhere in the tree — resolvers, containers, controllers, tests — the same construct carries no such weight; decide it per site by asking what reads the variable, not by asking what repository you are in.

WHAT GOES WRONG HERE.
Asserting the marker back at itself: reading AccountVerificationHelper.java as text, or its bytecode, and asserting the assignment is gone. That tests your edit, not the defect, and the same trick "proves" any deletion.

Manufacturing a RED by making the dead value live and calling that the fix. Measured above: `} else if (!likely) {` makes the auth-bypass assignment unsolvable, because every input that can pass verifyAccount has size 2 and would be reported as cheating.

Concluding "no test can show it, therefore it is not a defect." The store is genuinely unreadable-from and removing it is right; only the "therefore" is wrong. Settle it as a behaviour-preserving cleanup that no test can distinguish, and say that explicitly.

Treating "assigned, then assigned again" as sufficient evidence. It is dead only if EVERY path reassigns before a read. Requests.java:58's `boolean allowed = true;` is read (no final else). CourseConfiguration.java:139's `String[] paths = null;` is read by the `if (paths == null)` below it. Neither is this construct.

Deleting a whole statement whose RHS advances an iterator, drains a queue, or otherwise mutates state — the assignment is dead, the call is not.

Assuming the flagged line is the only dead one. Line 33 here is dead by the same argument; repairing 36 and leaving 33 leaves the construct in place.
