On the flagged line a value is used as a method receiver without ever having been null-tested, and that value arrived from a call permitted to return null — `.RET` means the null originates in a *returned value*, not in a parameter or a field. The `.STAT` flavour is the inferred kind: the analyzer concluded the callee may return null from how the surrounding code treats it — most other call sites of the same accessor are null-tested, this one is not — rather than from proving a concrete null-returning path. The report points at a *missing check*, not at a proof, and establishing that null is genuinely reachable is your job. The neighbouring construct constantly mistaken for it: on a line shaped `T x = (T) v.m();` two return values are in view, and the flagged one is NOT `m()`'s result being cast — it is `v`, the receiver, whose value was returned by a call on an earlier line.

HOW YOU MAKE IT VISIBLE.
Start from the asymmetry the inference picked up on. The sibling reads of the same accessor that ARE null-tested record what the code itself believes about nullability, and the untested one is the marker. Then look for an entry order that reaches the dereference before the value has been produced. State written by one request and read by another — a session or cache attribute populated by a different endpoint, with nothing on the server ordering the two — is the classic source, since `getAttribute` returns null for an absent name and any client that performs the read first arrives with null. A second tab, a restarted process or a direct request is enough.

Arrange the smallest thing that produces the null for real: construct the object directly rather than booting the framework, and prefer an empty request or session double over stubbing the accessor, since a genuinely empty session returns null with no mocking at all — a stronger arrangement than a stub that was told to.

ASSERT THE GRACEFUL OUTCOME, NOT THE EXCEPTION. Write one assertion that is RED before the fix and GREEN after without being rewritten: that the call returns the failure result or error response the caller should produce when the value is absent. Before reporting RED, read the NPE frame — the helpful message naming the flagged line and the null variable is what "failed for the right reason" means here, and "an NPE was thrown" is not enough. For GREEN, guard the read and return that graceful failure, checking every dereference of the same value; a second use further down means the guard must precede both.

Because STAT infers rather than proves, a marker of this kind can have no reachable null at all — the writer always runs before the reader, or the callee returns null on no path that arrives here. Settle those by refutation with the unreachability argument written out, not by bolting on a null check to quiet the tool.

WHAT GOES WRONG HERE.
`assertThrows(NullPointerException.class, …)` as the RED. It PASSES on today's defective code and FAILS after the fix — a regression lock on the defect, inverted. It also fails to pin the line: any other null argument satisfies it just as well.

Null-checking the wrong value: the result of the call that sits on the flagged line, because the cast or the assignment is what catches the eye. The NPE fires on the *receiver*, before that call or the assignment happen, so such a guard compiles, ships and changes nothing.

Driving the RED through a full-application integration test. Framework exception resolution turns the NPE into a 500 whose text no longer names the line, and any required parameter you omit yields a 400 instead — RED for entirely the wrong reason, and one that would still look RED after a correct fix.

Refusing the marker because of where it lives. The name, package or directory of the surrounding code decides nothing in either direction: code that reads as demonstration or sample material does not thereby intend its crashes, and a graceful failure return leaves its intended paths intact — while code that reads as critical is not thereby free of ordinary defects. Intent needs something checked in that DEPENDS on the dereference behaving as it does — a test asserting the throw, documentation instructing callers to expect it, a comment or suppression naming the choice. Absent that, read what the surrounding feature's success condition actually checks before deciding the construct is load-bearing.

"Fixing" it by making some other endpoint populate the state first, or by rerouting through a helper that null-checks different values. If the caller must still evaluate the flagged expression in order to call the helper, the dereference survives untouched.
