^\s*(?:final\s+)?(?:Connection|(?:Prepared|Callable)?Statement|ResultSet|\w*(?:InputStream|OutputStream|Reader|Writer)|ZipFile|Socket|Scanner)\s+\w+\s*=(?!=)
The flagged line ACQUIRES a resource into a bare local — `Statement statement = connection.createStatement(TYPE_SCROLL_SENSITIVE, CONCUR_UPDATABLE);` — and that handle is still outstanding on a path that leaves the method by throwing, so nothing ever calls close() on it. The `_EXCEPTION_EDGE` suffix is the discriminator and is the whole point: plain OBL_UNSATISFIED_OBLIGATION fires when an ordinary return drops the handle, whereas you get the EXCEPTION_EDGE variant when the ordinary return hands the resource, or something derived from it, to the caller (here `return statement.executeQuery(query)` gives the caller only the ResultSet), leaving the throw as the one edge on which the analyzer is certain nobody can still close it. Do not read it as ODR_OPEN_DATABASE_RESOURCE ("may fail to close Statement", no path reasoning — SpotBugs 4.10.3 reports that one separately, on line 63 of this same file), and do not read it as a leaked Connection: the Connection at line 56 IS in try-with-resources; it is the child Statement/ResultSet that is unmanaged.

Do not try to demonstrate exhaustion — you cannot, and the attempt yields a test that passes before AND after the fix. Measured on this checkout (HSQLDB 2.7.3): after `conn.close()` a statement left open still reports `isClosed()==false`, and in the running app the pooled connection reaps it anyway; the leak's lifetime is one request. WHAT GOES WRONG HERE.
- Asserting the marker back at itself: `verify(mockStatement, never()).close()` over a pure mock proves only that your mock recorded nothing. Keep a real database behind the proxy and assert the ledger AFTER `injectableQueryIntegrity` has returned, so that a fix closing the statement only on the happy path still fails.
- Testing the wrong edge. This variant names the throw. A test that exercises only the ordinary return would go green under a fix that closes in `catch` but not `finally`, and would miss that on the exception edge the caller has no `results.getStatement()` handle to fall back on. Force the SQLException.
- The tempting caller-side fix, `results.getStatement().close()` at lines 75/83, closes only on the path where a ResultSet exists — it leaves leaking precisely the path the checker is named after.
- Assuming, from the JDBC rule that `Statement.close()` closes its ResultSet, that the minimal try-with-resources on line 116 must break the lesson. Measured: it does not. HSQLDB keeps a TYPE_SCROLL_SENSITIVE/CONCUR_UPDATABLE result readable after its statement closes (`rs.isClosed()==false`, full read succeeds) and `SqlInjectionLesson9Test` stays 5/5 with that edit. It is still the worse fix — it returns a ResultSet whose Statement is closed, and it survives only on this driver. Measure rather than argue from the spec, in either direction.
- Blanket-fixing the neighbours. Lines 63, 93 and 94 carry their own plain OBL/ODR markers with different path traces, and lines 63-65 are the injectable query itself, so edits there are edits to the lesson.
- Verdict language: "leak" here does not mean unbounded. Say the handle is never discharged on the throw path; do not claim exhaustion you did not observe.
- Regex looseness: it also matches a resource declared on a continuation line of a multi-line try-with-resources, which is already managed. Read the two lines above a hit before believing it.
