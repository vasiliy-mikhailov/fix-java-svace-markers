^\s*(?:final\s+)?(?:Connection|(?:Prepared|Callable)?Statement|ResultSet|\w*(?:InputStream|OutputStream|Reader|Writer)|ZipFile|Socket|Scanner)\s+\w+\s*=(?!=)
The flagged line ACQUIRES a resource into a bare local, and that handle is still outstanding on a
path that leaves the method by THROWING, so nothing ever calls close() on it. The `_EXCEPTION_EDGE`
suffix is the discriminator and is the whole point: plain OBL_UNSATISFIED_OBLIGATION fires when an
ordinary return drops the handle, whereas you get this variant when the ordinary return hands the
resource, or something derived from it, to the caller — `return statement.executeQuery(query)` gives
the caller only the ResultSet — leaving the throw as the one edge on which the analyzer is certain
nobody can still close it. Do not read it as ODR_OPEN_DATABASE_RESOURCE, which says "may fail to
close Statement" with no path reasoning and is reported separately, sometimes on a neighbouring line
of the same method. And do not read it as a leaked Connection when the Connection is the one thing
already inside try-with-resources; it is the child Statement, ResultSet or stream that is unmanaged.

DO NOT TRY TO DEMONSTRATE EXHAUSTION. You cannot, and the attempt yields a test that passes before
AND after the fix. Whether an undischarged handle costs anything depends on the driver and on
whether a pool sits underneath: closing the owning connection may end the session and take every
statement on it down, while a pooled connection may return without cascading at all. Measure the
environment rather than assume either way, and keep the language honest — "leak" here does not mean
unbounded. Say the handle is never discharged on the throw path; do not claim exhaustion you did not
observe.

WHAT IS OBSERVABLE is the obligation itself, at the moment control leaves the method. Interpose a
recorder between the code and a real backend rather than mocking the backend away: a proxy over the
real connection or factory that wraps everything it returns in a recording proxy, notes close()
against an identity, and swallows close() on the parent so the ledger survives to the assertion.
Drive the exception edge by making one specific operation throw — pick something the method's own
inputs cannot influence, so the ordinary path still runs to that point. Then assert per resource
after the method has returned: "the handle created at the flagged line appears in the closed set."
Assert it on both the throwing run and the ordinary one, and a fix that closes only on the happy path
still fails, which is exactly what this variant claims.

WHAT GOES WRONG HERE.
- Asserting the marker back at itself. `verify(mockStatement, never()).close()` over a pure mock
proves only that your mock recorded nothing. Keep a real implementation behind the proxy and sample
the ledger AFTER the method under test returns.
- Testing the wrong edge. This variant names the throw. A test that exercises only the ordinary
return goes green under a fix that closes in `catch` but not `finally`, and misses that on the
exception edge the caller has no derived handle to fall back on. Force the failure.
- The tempting caller-side fix — recovering the parent from the returned object and closing it there
— closes only on the path where that object exists, leaving unclosed precisely the path the checker
is named after.
- Arguing from the specification instead of measuring, in either direction. Closing a Statement is
specified to close its ResultSet, so a minimal try-with-resources looks like it must break a caller
that reads the returned result; on some drivers it demonstrably does not. That still does not make it
the right fix, since it hands back a result whose owner is closed — but the answer comes from running
it, not from quoting the contract.
- Blanket-fixing the neighbours. Nearby acquisitions carry their own markers with different path
traces, and the line the marker points at is often also the line that builds the query or command;
edits there are behaviour changes, not obligation fixes.
- Regex looseness: it also matches a resource declared on a continuation line of a multi-line
try-with-resources, which is already managed. Read the two lines above a hit before believing it.
