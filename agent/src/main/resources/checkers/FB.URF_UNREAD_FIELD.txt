^\s*(?:@(?:AllArgs|RequiredArgs|NoArgs)Constructor\b|@(?:Data|Value)\b|private\s+(?:static\s+|final\s+|transient\s+|volatile\s+)*[\w.$<>\[\],\s]+?\s+\w+\s*[;=])
URF_UNREAD_FIELD says a non-public field is assigned somewhere but never loaded anywhere in the analyzed bytecode — written, never read. A getter counts as a read, so in practice the report means "no accessor, and no use inside the class either". Do not confuse it with its neighbours: UUF_UNUSED_FIELD is never read AND never written; UWF_UNWRITTEN_FIELD / UWF_NULL_FIELD is the mirror image (read but never written); URF_UNREAD_PUBLIC_OR_PROTECTED_FIELD is the same complaint about a field an off-analysis reader could still reach; SIC_INNER_SHOULD_BE_STATIC often lands on the same inner class and is a different claim entirely. Note also that the flagged line need not contain a field: SpotBugs anchors a field to where it is touched, and with Lombok the whole generated constructor carries the line of the annotation — at SampleAttack.java:71 the flagged line is literally `@AllArgsConstructor`, while the three unread fields are declared on 73-75.

HOW YOU MAKE IT VISIBLE.
The report is about absence, so a test can only see it through the consumer that was supposed to read the field. Find that consumer first; everything depends on which of two cases you are in.

CASE A — an external reader exists (this marker). SampleAttack$Item's three unread fields are the entire payload of `GET /lesson-template/shop/{user}` (SampleAttack.java:66-69), which returns `List<Item>` from a @RestController. `private class Item` has private fields, @AllArgsConstructor only, and no @Getter — so Jackson finds no properties and the data silently vanishes. Measured, not guessed: `MockMvcBuilders.standaloneSetup(new SampleAttack(new LessonSession())).build()` then `get("/lesson-template/shop/tom")` returns status 200 with body `[{},{}]`. RED is therefore a content assertion, e.g. `.andExpect(jsonPath("$[0].number").value("WG-1"))` plus `$[0].price` = 12.0 — it fails with "No value at JSON path". GREEN: add `@Getter` to Item, which is exactly what every sibling inner DTO in this repo already does (Servers.Server:30, ShopEndpoint.CheckoutCode:34, Requests.Tracert:37); measured result is `[{"description":"WebGoat promo","number":"WG-1","price":12.0},{...}]`. The same edit clears the checker, because an accessor is a getfield on each field. Converting Item to a record or to a public static class with accessors is equivalent. The existing ShopEndpointTest (src/test/java/org/owasp/webgoat/lessons/clientsidefiltering/ShopEndpointTest.java) is the ready-made template: standaloneSetup + jsonPath, no Spring context needed, and this controller is directly constructible with `new LessonSession()`.

The general form of Case A: the intended reader is outside Java — a JSON body, a Thymeleaf model, a persisted column, an ObjectOutputStream, browser JS naming the property. Assert on that artifact; the missing value IS the defect, a real observable regression rather than a style nit.

CASE B — no reader anywhere. Then say so plainly: no JUnit test can distinguish before from after, because removing a field nothing reads changes no observable behaviour. The only test available asserts on the field itself (reflection, or a getter added for the test), which proves nothing about the defect. The honest settlement is "real dead code, unprovable by test — removal is cleanup, not a demonstrated failure". Do not manufacture a RED to escape that.

How to tell which case you are in: grep for @Getter/@Data/record accessors on the type, for the field name in the lesson's .html/.js/.adoc and in SQL/JPA mappings, and check whether the enclosing type escapes through @ResponseBody, a ModelAndView, or serialization.

Finally: do NOT use a SpotBugs re-scan as your evidence. Measured here — a full-detector spotbugs 4.10.3 run over this package reports nothing on this class; the three URF instances appear only with `-Dspotbugs.visitors=UnreadFields` (all anchored to line 71). Tool silence is available before the fix as well as after, so it settles nothing.

WHAT GOES WRONG HERE.
1. Asserting the marker back at itself: `Item.class.getDeclaredField("number")` + setAccessible + assert "WG-1", or asserting getDeclaredFields().length == 3. That passes before and after; it proves the field is written, which nobody disputed, and reflection is itself a read.
2. Expecting an exception or a 500. Guessing FAIL_ON_EMPTY_BEANS and writing `status().isInternalServerError()` gives a RED that fails for the wrong reason — the endpoint really returns 200; only the body is `[{},{}]`. Assert on content.
3. "Fixing" by deleting the fields, the Item class, or the endpoint. Deletion is the textbook URF fix and the wrong one whenever the field is a data carrier: the adoc quotes this endpoint verbatim as the worked example of an extra endpoint (lesson-template-attack.adoc:69), so lesson authors copy it, and an example that serializes to `{}` teaches the bug.
4. Reading only the flagged line, seeing `@AllArgsConstructor`, and calling it a Lombok false positive. Line 71 is where Lombok's generated constructor writes the fields; the subject is lines 73-75.
5. Both blanket verdicts about WebGoat. This one is not a lesson: no lesson HTML or JS calls /lesson-template/shop, the solvable assignment in this class is the POST param1 check, and restoring the JSON breaks no assignment. But elsewhere in this repo a field's only reader may be a serialization hook (VulnerableTaskHolder.readObject reads taskAction), a Thymeleaf template, or browser JS — readers SpotBugs cannot see. Establish the reader before concluding in either direction.
6. Verdict slippage: "the field is now read by a getter" is not the same claim as "the endpoint now returns its data". Only the second is what the test showed; state the one you actually observed.
