^\s*(?:@(?:AllArgs|RequiredArgs|NoArgs)Constructor\b|@(?:Data|Value)\b|private\s+(?:static\s+|final\s+|transient\s+|volatile\s+)*[\w.$<>\[\],\s]+?\s+\w+\s*[;=])
URF_UNREAD_FIELD says a non-public field is assigned somewhere but never loaded anywhere in the analyzed bytecode — written, never read. A getter counts as a read, so in practice the report means "no accessor, and no use inside the class either". Do not confuse it with its neighbours: UUF_UNUSED_FIELD is never read AND never written; UWF_UNWRITTEN_FIELD / UWF_NULL_FIELD is the mirror image, read but never written; URF_UNREAD_PUBLIC_OR_PROTECTED_FIELD is the same complaint about a field an off-analysis reader could still reach; SIC_INNER_SHOULD_BE_STATIC often lands on the same inner class and is a different claim entirely. The flagged line need not contain a field at all: the tool anchors a field to where it is touched, and a constructor generated by an annotation processor carries the line of the annotation, so the marker can sit on `@AllArgsConstructor` while the unread fields are declared below it.

HOW YOU MAKE IT VISIBLE.
The report is about absence, so a test can only see it through the consumer that was supposed to read the field. Establish that consumer before concluding in either direction — a field's only reader may be a serialization hook, a template or client-side code, readers the analyzer cannot see, and equally a plausible-looking reader may turn out not to exist. Grep for accessors, records or @Data on the type, for the field name in templates, scripts, documentation and SQL/JPA mappings, and check whether the enclosing type escapes through serialization, a response body or a view model.

CASE A — AN EXTERNAL READER EXISTS. The intended reader is outside Java: a JSON body, a template model, a persisted column, an object stream, browser code naming the property. The classic shape is a small carrier type with private fields, a generated all-args constructor and no accessors, so the serializer finds no properties and every instance comes out as `{}` — the call succeeds, the content type is right, the data is silently gone. RED is therefore a CONTENT assertion on that artifact, and the failure you should see is "no value at that path". GREEN comes from giving the fields accessors — a getter, a record, or a type with real accessor methods; the same edit clears the checker, because an accessor compiles to a getfield. Use the cheapest seam that reaches the serializer. The missing value IS the defect, a real observable regression rather than a style nit.

CASE B — NO READER ANYWHERE. Then say so plainly: no test can distinguish before from after, because removing a field nothing reads changes no observable behaviour. The only test available asserts on the field itself, and that proves nothing about the defect. The honest settlement is real dead code, unprovable by test, removal as cleanup rather than a demonstrated failure. Do not manufacture a RED to escape that.

Re-scanning with the analyzer is a cross-check on a fix, never a substitute for the content assertion, and it is worthless unless the exact invocation is reported with it: this finding is emitted at a middling priority, so raising the reporting threshold drops it, and restricting the analysis to a subset of classes can drop it too while unrelated findings on the very same class survive. Silence is available before the fix as well as after.

WHAT GOES WRONG HERE.
Asserting the marker back at itself: reading the field by reflection and asserting its value, or counting getDeclaredFields(). That passes before and after, it proves the field is written — which nobody disputed — and reflection is itself a read.

Expecting an exception or a 500 from the serializer. Guessing that an empty bean will fail the request gives a RED that fails for the wrong reason; the call really does succeed and only the body is empty. Assert on content.

"Fixing" by deleting the fields or the type that holds them. Deletion is the textbook URF fix and the wrong one whenever the field is a data carrier: the defect is that the data never arrives, and deleting the data does not make it arrive.

Reading only the flagged line, seeing an annotation, and calling it a code-generation false positive. That line is where the generated constructor writes the fields; the subject is the field declarations.

Verdict slippage: "the field is now read by a getter" is not the same claim as "the consumer now receives its data". Only the second is what such a test shows; state the one you actually observed.
