@CookieValue\b|\.getCookies\s*\(|\b\w*[Cc]ookie(?:Value|Username|Token)\b|\baccessToken\b
A value that arrived on an inbound HTTP request cookie reaches a use that assumes trusted, well-formed data. The `.COOKIE` suffix names the taint SOURCE — a `@CookieValue` parameter, `HttpServletRequest.getCookies()`, `Cookie.getValue()` — not the sink, and the marker line may be either end of the flow: JWTVotesEndpoint.java:135 is the parameter declaration itself, while HijackSessionAssignment.java:56 is a use site three lines later, so follow the variable rather than judging the line you were handed. This is the READ side; the write side in the same files (`new Cookie(...)`, `response.addCookie`, `setSecure`/HttpOnly flags) is a different family and is not what this checker is complaining about.

HOW YOU MAKE IT VISIBLE.
Cookie taint splits into two shapes, and only one of them can be made to fail a test. Decide which you have by following the cookie variable to its first use that is not a null/emptiness check.

SHAPE A — CRASH (testable; there is a real one in this queue). JWTVotesEndpoint binds `access_token` at lines 135/172/195, parses it with `Jwts.parser().setSigningKey(JWT_PASSWORD).parse(...)`, then does `String user = (String) claims.get("user")` and `!validUsers.contains(user)` (line 144 in getVotes, 180 in vote). jjwt 0.9.1's `parse()` accepts an UNSIGNED token even with a signing key set — the in-tree test `solveAssignment` depends on exactly that — so any unauthenticated caller can supply a well-formed token whose claims omit `user`; the cast yields null and `String.contains(null)` throws NPE, which is not a `JwtException` and so slips past the catch at 149/186. I ran the exact chain on jjwt 0.9.1 outside Spring: token `eyJhbGciOiJub25lIn0.eyJhZG1pbiI6InRydWUifQ.` parses cleanly, `user` is null, `"TomJerrySylvester".contains(null)` -> `NullPointerException: Cannot invoke "java.lang.CharSequence.toString()" because "s" is null` at java.lang.String.contains.
The RED: copy `JWTVotesEndpointTest.unknownUserShouldSeeGuestView` (it already extends LessonTest, is @WithWebGoatUser, and drives MockMvc with a forged cookie) and delete the one line `claims.put("user", "Intruder")`. Keep its assertions unchanged — `status().isOk()` plus `jsonPath("$[0].numberOfVotes").doesNotExist()` — because that is what the endpoint does with any other unprivileged token. Assert the OUTCOME, never the exception: this app has no @ControllerAdvice mapping Exception (only two ResponseBodyAdvice classes), so depending on how MockMvc was built the NPE surfaces either as HTTP 500 or as an exception escaping `perform()`; both fail those assertions, and pinning either one bakes in an artifact of the test harness. The `vote` variant is the same edit against `unknownUserWithValidTokenShouldNotBeAbleToVote`, asserting `status().isUnauthorized()`. GREEN is a null guard at the flagged use (`user == null || "Guest".equals(user) || !validUsers.contains(user)`), which leaves the alg=none forgery — the actual lesson — completely intact, so `solveAssignment`, `tomShouldSeeNumberOfVotes` and `invalidTokenShouldSeeGuestView` stay green.

SHAPE B — TRUST (usually NOT demonstrable here; say so instead of faking it). At HijackSessionAssignment:56 the raw `hijack_cookie` becomes an authentication id, and at SpoofCookieAssignment:52 the raw `spoof_auth` becomes an identity; the complaint is that an attacker-chosen value is believed. The only test for that is "send a cookie the server never issued, assert access is granted" — and that test already exists and is already GREEN as the assignment's success criterion: `SpoofCookieAssignmentTest.success()` posts `spoof_auth=NjI2MTcwNGI3YTQxNGE1OTU2NzQ2ZDZmNzQ=` (which decodes to "tom") and asserts `lessonCompleted=true`; `HijackSessionAssignmentTest.testValidCookie` does the same with `hijack_cookie`. The lesson text names the very cookie as the target ("we are trying to predict the 'hijack_cookie' value", HijackSession_content0.adoc; "attempt to spoof the cookie and log in as Tom", SpoofCookie_content0.adoc), and the provider carries the comment `// weak id value and mechanism`. No RED exists there that is not the exercise being solved, and the fix that would create one (unguessable session ids, authenticated cookie encoding) deletes the assignment. Settle such a marker as intended-by-design and cite the assignment test plus the .adoc — not a blanket claim about the repository.
Crash shape is genuinely unreachable in those two: `SpoofCookieAssignment.cookieLoginFlow` wraps `EncDec.decode` in `catch (Exception e)` (so both the Base64 IllegalArgumentException and the `substring` StringIndexOutOfBounds are absorbed), `HijackSessionAuthenticationProvider.authenticate` guards empty ids with StringUtils and only does `sessions.contains(...)`, and `CSRFFeedback:58` null-checks the `getCookies()` array and reads only names. Also note `@CookieValue(required = false)` yields null when the header is absent and every flagged endpoint opens with `StringUtils.isEmpty(...)`, so "send no cookie" is never the RED.

The dividing question, before you write anything: is there an attacker-reachable cookie value that makes the flagged use THROW (null derived from the cookie and dereferenced, unchecked cast, index/substring arithmetic, a parse whose exception type is not the one caught)? If yes, that is a plain defect even inside a lesson file, because no assignment asks the student to produce a 500. If no, and the only complaint is that the value is believed, check whether the class sits under `lessons/`, implements `AssignmentEndpoint`, and has documentation naming that cookie; the same read in `container/` or `webwolf/` infrastructure has no lesson to protect and is a real finding — but it still needs an observable, e.g. asserting that a request carrying a cookie the server never issued is rejected.

WHAT GOES WRONG HERE.
Asserting the marker back at itself: writing "post a forged cookie, expect lessonCompleted=true" as if it proved something. That test is already in the tree twice (SpoofCookieAssignmentTest.success, HijackSessionAssignmentTest.testValidCookie), it is GREEN today, and it restates the assignment rather than exposing a defect.

Reaching for a junk cookie to force a crash. `invalidTokenShouldSeeGuestView` already sends `abcd.efgh.ijkl` and gets a clean 200 guest view, and SpoofCookie's `catch (Exception e)` absorbs every malformed encoding. A RED built on random garbage goes GREEN immediately and refutes the marker for the wrong reason. The JWT crash needs a token that PARSES and merely omits the `user` claim.

Fixes that break a lesson: rejecting `alg=none` / requiring a verified signature in JWTVotesEndpoint (kills solveAssignment and solveAssignmentWithBoolean), making HijackSessionAuthenticationProvider's ids unpredictable, or strengthening EncDec. The lesson-safe fix for the one real defect is a null check on the `user` claim, nothing more.

"Validate the cookie" as a fix at HijackSessionAssignment:56 — adding a format check on `cookieValue` changes no observable behaviour (the provider already tolerates empty and unknown ids), so it produces a GREEN that was never RED.

Verdict words that do not follow: "unvalidated" is a description, not a defect; "WebGoat, therefore intentional" is not a settlement either — CSRFFeedback's null-guarded `getCookies()` and JWTVotesEndpoint's unguarded null claim sit in the same lesson tree, one careful and one not.
