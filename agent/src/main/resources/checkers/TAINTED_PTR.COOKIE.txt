@CookieValue\b|\.getCookies\s*\(|\b\w*[Cc]ookie(?:Value|Username|Token)\b|\baccessToken\b
A value that arrived on an inbound HTTP request cookie reaches a use that assumes trusted,
well-formed data. The `.COOKIE` suffix names the taint SOURCE — a `@CookieValue` parameter,
`HttpServletRequest.getCookies()`, `Cookie.getValue()` — not the sink, and the marker line may be
either end of the flow: sometimes the parameter declaration, sometimes a use site further down.
Follow the variable rather than judging the line you were handed. This is the READ side; the write
side in the same files (`new Cookie(...)`, `response.addCookie`, the `Secure` and `HttpOnly` flags)
is a different family.

TWO SHAPES, AND ONLY ONE CAN BE MADE TO FAIL A TEST. Decide which you have by following the cookie
variable to its first use that is not a null or emptiness check.

CRASH SHAPE — testable. Ask whether an attacker-reachable cookie value makes the flagged use THROW:
a null derived from the cookie and then dereferenced, an unchecked cast, index or substring
arithmetic, a parse whose exception type is not the one the surrounding catch names. The classic is
a cast of a missing entry — a claim absent from a token, an absent map key — which yields null
silently; the next call dereferences it, and the resulting NullPointerException is not the library
exception the enclosing catch was written for, so it escapes the handler. That is a plain defect
even where the surrounding feature's own behaviour is intended, because nothing documents or depends
on an unhandled 500.
Build the RED from an existing test of the ordinary rejected-but-handled path by removing the single
thing that makes the value well-formed, keeping that test's assertions unchanged — that is what the
endpoint should do with any other unprivileged input. Assert the OUTCOME, never the exception:
depending on how the harness was built and whether the application maps exceptions at all, an
escaping runtime exception surfaces either as a 500 or as an exception thrown out of the call, and
pinning either bakes in an artifact of the harness. GREEN is the minimal guard at the flagged use.

TRUST SHAPE — usually not demonstrable; say so instead of faking it. Here the complaint is that an
attacker-chosen value is believed: a raw cookie becomes an identity or a session id. The only test
for that is "send a cookie the server never issued, assert access is granted" — and where believing
it is the point of the code, that test already exists and is green as the feature's own success
criterion, while the fix that would create a RED (unguessable ids, an authenticated encoding)
deletes the feature. Settle such a marker on the code's own documentation and tests, not on a
blanket claim about the repository — the identical read in infrastructure code has no feature to
protect and is a real finding, though it still needs an observable, such as asserting that a request
carrying a cookie the server never issued is rejected. An optional cookie binding also yields null
when the header is absent, and such endpoints normally open with an emptiness check, so "send no
cookie" is never a RED.

WHAT GOES WRONG HERE.
Asserting the marker back at itself: "post a forged cookie, expect the success response" as if it
proved something, when that is documented behaviour and is green today.

Reaching for a junk cookie to force a crash. Malformed values are usually already absorbed — a broad
`catch (Exception e)` around a decode, an emptiness guard, a lookup that returns false for unknown
ids — so a RED built on random garbage goes GREEN immediately and refutes the marker for the wrong
reason. A crash needs a value that PARSES and merely omits or alters one field.

Fixing past the defect: deleting the feature when what was observable was one missing guard, or
adding a format check where the downstream already tolerates empty and unknown values, which changes
no observable behaviour and produces a GREEN that was never RED.

Verdict words that do not follow: "unvalidated" is a description, not a defect; and the reputation of
the code around the flagged line — its name, its package, what the surrounding directory is for — is
not a settlement either, in either direction. Intent has to come from something checked in that
DEPENDS on the cookie being believed: documentation telling a caller to send it, a test asserting
that it is honoured. Absent that, the identical read is an ordinary defect, and a carefully
null-guarded cookie read and a careless one routinely sit one file apart in the same package.
