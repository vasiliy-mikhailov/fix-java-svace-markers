(?:this\s*\.\s*)?getClass\s*\(\s*\)\s*\.\s*getResource(?:AsStream)?\s*\(
Fires on `getClass().getResource(...)` / `getClass().getResourceAsStream(...)` invoked on `this` inside an instance method of a public, non-final class: `getClass()` returns the RUNTIME class, so the package and the class loader that resolve the resource are chosen by whoever subclasses you, not by the file you are reading. Two neighbouring constructs are routinely mistaken for it and are not it: `Foo.class.getResource(...)`, where the class literal is fixed at compile time (the detector clears its state on a class constant), and `getClass().getClassLoader().getResourceAsStream(...)`, which is a ClassLoader call with different naming rules. A leading `/` does not suppress the warning — it only drops it to LOW priority, because an absolute name fixes the package half of the hazard and leaves the class-loader half intact.

DECIDE WHICH OF TWO CLAIMS YOU ARE PROVING, because they need different tests and usually only one is reachable.

(1) The inheritance claim. If the resource name is RELATIVE, it is cheap and genuine: declare a subclass of the flagged class in a DIFFERENT package, call the inherited method on an instance of it, and the lookup now resolves against the subclass's package and returns null. That is a real RED with no gymnastics. If the name is ABSOLUTE the trick proves nothing — the package is irrelevant once the name starts with `/`, and only a class loader with a different resource view could change the answer; building such a loader in-process tests the JDK rather than the code under analysis. Say that plainly instead of faking it.

(2) The claim that actually pays on an absolute name: does the name resolve AT ALL on today's classpath? Run the lookup and look. Resources get moved by refactoring while the string literal that names them does not, so a flagged line is worth resolving before it is worth arguing about.

Such a broken lookup can sit unnoticed for years because the consumer of the stream is null-tolerant: a copy-to-bytes helper that returns an empty array on a null input produces no exception and no log entry, and the caller answers a request with a correct status, a correct content type and an empty body. THE SYMPTOM IS EMPTINESS, NOT A THROW. Assert on the bytes or the content the caller ultimately produces, never on the literal and never on `getResourceAsStream` returning null. And when you write the settlement, say what the test actually proved: that this resource lookup is broken, not that inheritance broke it.

WHAT GOES WRONG HERE.
Asserting the marker back at itself: a test whose body asserts that `obj.getClass().getResourceAsStream(<the same literal>)` is null restates the flagged line and passes forever. Assert on the output of the method that consumes the stream — that is the observable a caller depends on.

Expecting an exception. `assertThrows(NullPointerException.class, ...)` will not go RED wherever the stream consumer tolerates null, which is the common case.

Subclassing to demonstrate an absolute-name marker. Existing subclasses that sit in the same package change nothing about the lookup, and neither would a different-package subclass while the name begins with `/`.

A verdict that does not follow: "the path is absolute, therefore the checker is wrong." Absolute removes only the package hazard, the detector still reports the call, and the absolute name may itself be the wrong name.

Silencing rather than proving: switching to `TheClass.class.getResourceAsStream(...)` satisfies the checker while leaving a broken lookup in place. A test that stays RED after that edit is the correct signal that nothing was fixed.
