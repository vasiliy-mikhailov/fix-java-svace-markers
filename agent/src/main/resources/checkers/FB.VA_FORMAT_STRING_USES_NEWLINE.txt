(?:String\.format|\.formatted|\bprintf|\.format)\s*\(
It fires on a format-family call (String.format, printf, Formatter/PrintWriter/PrintStream.format) whose constant format string contains a literal newline character, and asks for %n — which expands to System.lineSeparator() — instead of a hardcoded LF; it never throws and is purely about line-ending portability. It is reported on the CALL line, not where the format string is declared: the marker sits on AccessControlIntegrationTest.java:46, `.body(String.format(userTemplate, this.getUser(), this.getUser()))`, while the newline lives in the text block declared at 37-40 — so expect to follow the constant, sometimes into another file (e.g. Assignment7.TEMPLATE, ResetLinkAssignment.TEMPLATE). Do not confuse it with its VA_FORMAT_STRING_ARG_MISMATCH / BAD_CONVERSION siblings, which are about placeholders versus arguments and blow up at runtime; here the two %s and two arguments match fine, and a text block trips the detector exactly as a "\n" escape does, because a closing """ on its own line puts a real newline into the constant.

HOW YOU MAKE IT VISIBLE.
A test can only see this defect when two things hold: the formatted text has a real line-ending contract (console output, a report or local text file someone reads line-wise), and the running JVM's separator differs from LF. The mechanism, verified on this checkout's toolchain (JDK 26, macOS) rather than assumed: `%n` emits System.lineSeparator(), `\n` always emits LF, and System.lineSeparator() is captured during JVM start-up. That start-up fact is where agents usually give up ("the separator is fixed, no test can vary it") and the conclusion does not follow — the same mistake the DM_DEFAULT_ENCODING queue made. What is genuinely dead: System.setProperty("line.separator","\r\n") inside a test, junit-pioneer @SetSystemProperty, and surefire <systemPropertyVariables> all change System.getProperty but leave lineSeparator() and %n alone (measured inside a real surefire 3.5.6 fork: property bytes [90,90], lineSeparator() still [10], String.format("a%nb") still [97,10,98]). What works is a -D on the actual JVM command line: `java -Dline.separator=$'\r\n'` gave lineSeparator()=[13,10], "a%nb"->[97,13,10,98], "a\nb"->[97,10,98]; via Maven, surefire <argLine>-Dline.separator=ZZ</argLine> gave "a%nb"->"aZZb" while "a\nb" stayed LF. A sentinel like ZZ is easier to assert than CRLF and just as decisive. So the honest RED, for a site whose output really is platform text, is: run the test JVM with -Dline.separator=ZZ (argLine, or fork a JVM from the test with ProcessBuilder if you cannot touch the pom), call the production method, assert the produced text ends with System.lineSeparator() — fails with \n, passes once the constant uses %n.

For this marker that test is unavailable, and would be dishonest even if it were. Trace where line 46's string goes: it is the JSON body of a REST-assured POST to access-control/users (`.body(...)` on 46 feeding `.post(...)` on 47). LF versus CRLF inside an HTTP request body is not a line-ending contract; switching that template to %n would make the payload depend on the host OS, which is strictly worse than the flagged code. Nothing can exercise it either: userTemplate is a local variable in private assignment3() of a class extending the abstract IntegrationTest, compiled from src/it/java by build-helper and run by failsafe against a live WebGoat instance (surefire excludes **/*IntegrationTest.java), so no unit test can reach the string and no integration run asserts on its bytes. The settlement is therefore "no defect, nothing to demonstrate", not "provable but unproven". If someone insists on silencing the marker, the only edit that cannot change behaviour is deleting the trailing newline from the text block (a `\` line-continuation before the closing delimiter) — and say plainly that no test distinguishes before from after, so that is a cosmetic edit, not a proven fix.

Rule for the rest of the family: follow the formatted string to its destination before deciding anything. Destined for a console, a hand-assembled log line, or a text file a human or a line-oriented reader consumes — provable by the -Dline.separator recipe above, and %n is the right fix. Destined for a wire format or markup — an HTTP body, JSON, an HTML email body such as Assignment7.TEMPLATE or ResetLinkAssignment.TEMPLATE, where the renderer collapses the newlines anyway — LF is correct and %n is a regression. Note also that this checker never lands on a lesson's vulnerability: a newline in a format string is nobody's teaching material, so "WebGoat is deliberately broken" is not the reason to leave line 46 alone; the reason is that no line-ending contract exists at that call.

WHAT GOES WRONG HERE.
Asserting the marker back at itself: `assertThat(String.format(userTemplate, "a", "b")).endsWith(System.lineSeparator())` restates the checker's preference as if it were a requirement — under a default JVM it passes before and after (both LF) and proves nothing; under -Dline.separator=ZZ it fails, but for a JSON HTTP body that failure encodes the rule, not a defect. Building the RED on System.setProperty("line.separator", ...), @SetSystemProperty, or surefire <systemPropertyVariables>: measured to leave lineSeparator() and %n at LF, so the test goes GREEN before any fix and reads as a passing proof of nothing. Concluding "the line separator is fixed at JVM start, therefore unobservable": true premise, wrong conclusion — a test may start a JVM, or surefire may pass -Dline.separator on argLine. Assuming the source must contain a backslash-n and calling it a false positive when line 46 shows none: the newline comes from the text block's closing """ sitting on its own line at 37-40. Reading the VA_ prefix as an argument mismatch and hunting a missing %s: the two %s and the two getUser() arguments match, nothing throws. "Fixing" a payload site by swapping to %n (line 46's HTTP body, Assignment7's HTML mail template): that makes the bytes on the wire OS-dependent, and the WebGoat integration suite needs a booted server, so nothing will catch the regression. Finally, planning any verification that calls assignment3(): it is private, on a failsafe-only integration test requiring live WebGoat and WebWolf instances — there is no seam.
