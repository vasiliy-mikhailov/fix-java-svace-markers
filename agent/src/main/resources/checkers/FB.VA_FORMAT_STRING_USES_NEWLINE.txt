(?:String\.format|\.formatted|\bprintf|\.format)\s*\(
It fires on a format-family call (String.format, printf, Formatter/PrintWriter/PrintStream.format) whose constant format string contains a literal newline character, and asks for `%n` — which expands to System.lineSeparator() — instead of a hardcoded LF. It never throws; it is purely about line-ending portability. It is reported on the CALL line, not where the format string is declared, so expect to follow the constant to a field, a local or another file entirely. A text block trips the detector exactly as a `\n` escape does, because a closing `"""` on its own line puts a real newline into the constant — "the source shows no backslash-n, therefore false positive" is wrong. Do not confuse it with the VA_FORMAT_STRING_ARG_MISMATCH / BAD_CONVERSION siblings, which are about placeholders versus arguments and blow up at runtime.

HOW YOU MAKE IT VISIBLE.
A test can only see this defect when two things hold: the formatted text has a real line-ending contract, and the running JVM's separator differs from LF. System.lineSeparator() is captured during JVM start-up, and this is where agents give up — "the separator is fixed, so no test can vary it". The premise is true and the conclusion does not follow.

What is genuinely dead: System.setProperty("line.separator", ...) inside the test, extensions that set system properties around a test method, and system-property blocks in the test runner's configuration. They all change what System.getProperty returns while leaving System.lineSeparator() and `%n` at LF, so a test built on them goes GREEN before any fix and reads as a passing proof of nothing. What works is `-Dline.separator` on the actual JVM command line — the runner's fork arguments, or a JVM the test starts itself. A sentinel value is easier to assert than CRLF and just as decisive. The honest RED, for a site whose output really is platform text, is: run the JVM with the separator set, call the production method, and assert the produced text ends with System.lineSeparator(). It fails while the constant holds LF and passes once it uses `%n`.

FOLLOW THE FORMATTED STRING TO ITS DESTINATION BEFORE DECIDING ANYTHING. Destined for a console, a hand-assembled log line, or a text file that a human or a line-oriented reader consumes — the contract is real, the recipe above proves it, and `%n` is the right fix. Destined for a wire format or markup — an HTTP body, JSON, an HTML mail body, anything whose renderer collapses newlines — LF is correct and `%n` is a REGRESSION, because it makes the bytes on the wire depend on the host OS. Where no line-ending contract exists, the state to reach is that there is nothing to demonstrate, not that it is provable but unproven. If the marker must be silenced anyway, the only edit that cannot change behaviour is removing the trailing newline from the constant (a `\` line-continuation before a text block's closing delimiter) — and say plainly that no test distinguishes before from after, so that is cosmetic, not a proven fix.

WHAT GOES WRONG HERE.
Asserting the marker back at itself: a test that the formatted string ends with System.lineSeparator() restates the checker's preference as if it were a requirement. Under a default JVM it passes before and after, both being LF; under a forced separator it fails, but for a payload with no line-ending contract that failure encodes the rule rather than a defect.

Reading the VA_ prefix as an argument mismatch and hunting a missing conversion. This report says nothing about placeholders versus arguments; a mismatch is a different report and it throws at runtime, whereas this one cannot.

Checking for a seam only after writing the test. If the only caller is a private method of a class the test runner does not execute, or the string is a local variable inside it, there is nothing to call and the RED cannot exist. Establish the entry point first.
