FB.PATH_TRAVERSAL_IN (find-sec-bugs "Potential Path Traversal, file read") fires on the line where a
path is built or opened from a value the taint pass could not prove constant. It marks the sink, never
a proven flow — a configuration property, an HTTP parameter, an authenticated username and a
`String[] args` element are indistinguishable to it, so the marker by itself says nothing about whether
attacker data arrives. Its sibling FB.PATH_TRAVERSAL_OUT covers the write sinks; do not swap them, and
note one line can carry both, since `new File(dir, name)` is an IN sink even when the code then writes
through it.

HOW YOU MAKE IT VISIBLE. THE OBSERVABLE IS CONTAINMENT, NOT STRING SHAPE. Arrange a base directory,
plant a file with distinctive content OUTSIDE it, drive the real entry point with a traversing payload,
and assert either that the bytes returned to the caller equal the outside file's content, or that
`sink.getCanonicalPath().startsWith(base.getCanonicalPath() + File.separator)` fails. PREFER THE
CONTAINMENT ASSERTION TO THE APPLICATION'S OWN SUCCESS SIGNAL. A handler can accept a one-level escape
and reject a deeper one — a segment count or length check, a whitelist consulted after one
normalisation pass, a parent directory that exists at `..` and not at `../..` — so a RED anchored on
whatever the application reports as success flips with the DEPTH of the payload you happened to pick,
red at one `../` and green at two, and what gets settled is the payload rather than the line. Canonical
containment is depth-independent: the resolved path either is still inside the intended directory or it
is not.

JDK MECHANICS, or the test cannot fail for the right reason. getPath and getAbsolutePath DO NOT
NORMALIZE: `new File(new File("/base/dir"), "../x").getAbsolutePath()` is `/base/dir/../x`, and
`startsWith(base)` on that string returns TRUE with the file sitting outside — canonicalize both sides.
The two-arg File constructor COLLAPSES a leading `/` in the child, so `new File(base, "/etc/passwd")`
is `/base/dir/etc/passwd` and an absolute payload escapes nothing there; only `..` segments do. But
`Paths.get("/base/dir").resolve("/etc/passwd")` is `/etc/passwd`, because resolve takes an absolute
other WHOLESALE. Two sinks in one method can answer the same payload differently; pick the payload for
the sink you flagged.

MATCH THE PAYLOAD TO THE FILTER TOO. Where a sanitiser strips a fixed substring, the naive payload is
the one it removes and the doctored one survives: a single-pass `replace("../","")` turns `../x` into
`x`, but more than one doctored shape defeats it — `..././x` and `....//x` both come out as `../x`,
because the strip is never re-applied to its own output, and one shape being rejected says nothing
about the others. The mirror is as fatal — `..././x` against an UNFILTERED sink canonicalizes to a
literal three-dot directory and escapes nothing. Watch which representation each layer reads: a guard
inspecting the raw, still-percent-encoded query while the sink reads the decoded parameter is passed by
percent-encoding the dots, and a literal payload is rejected before the sink is reached. The question
runs upward too — before assuming a client-supplied multipart filename reaches the sink unmodified,
check that no layer strips path segments from it.

WHERE NO TRUST BOUNDARY IS CROSSED. When every non-constant segment comes from deployment
configuration, the only party who can set it is whoever starts the JVM, who already owns the
filesystem. You CAN turn a test red by setting the property to a traversing value, but that asserts
only that `new File(s)` returns a file at `s` — the marker back at itself. Settle such a line as
not-demonstrable-because-no-trust-boundary-is-crossed and name the input as deployment configuration.
A path from `String[] args` inside a command-line `main` is the same shape, since accepting a path from
argv is that program's whole interface, as is a method handed an already-constructed `File` by its
caller. But do not call a configuration source benign without opening the file that supplies its
default; knowing what it resolves to is what makes the argument work.

IDENTITY-DERIVED SEGMENTS NEED ONE LOOKUP FIRST. Where a username or tenant id is spliced into the
path, find the application's own constraint on that value before settling either way. A test that
constructs a user object named `../x` bypasses that validator and proves nothing about the shipped
system — and yet the constraint may not be universal, since a route that creates a user from an
external identity provider's name with no validated form in the path can admit what the form rejects.

THE INTENDED/DEFECT DISCRIMINATOR IS MECHANICAL. Ask whether anything checked in DEPENDS on the escape
SUCCEEDING: documentation telling a caller to pass a path that leaves the base directory, a test
asserting the outside file's bytes come back, an annotation or suppression naming the choice, or helper
code written to detect the escape and act on it — code that canonicalizes a path in order to CONFIRM it
left the base directory, rather than to reject it, is the tell. If yes, a containment fix turns a
passing test red; report it as demonstrated and depended-upon rather than patching. If no, a
containment test is a legitimate new observation. Apply it per LINE: a client-supplied name and an
internally generated one are different lines even three lines apart in one method.

WHAT GOES WRONG HERE. Asserting the marker back at itself, by checking the string for `..` or by
feeding the configuration property a traversing value and watching a File land where you put it. Taking
a green from `startsWith` on a non-canonical path. Choosing a payload that cannot fail for the right
reason. Forgetting that an endpoint requiring authentication answers an unauthenticated test with a
login redirect, or that a copy to an absolute target throws when the target's PARENT does not exist —
so the absolute payload writes nothing and "no file appeared outside" passes before the fix as well;
prefer a relative `../` payload landing in a directory that exists. Adding containment inside a shared
helper, which repairs every endpoint routed through it at once, including any whose tests depend on the
escape. And the verdict that does not follow: reading intent off the reputation, name, package or
directory of the surrounding code, in either direction — neither that code of this sort is meant to be
breakable so the marker is intended, nor that a project of this sort would never ship a traversal.
Intent is carried by something checked in that depends on the escape succeeding, and by nothing else;
with none of that present the line in front of you is an ordinary handler with an ordinary defect.
