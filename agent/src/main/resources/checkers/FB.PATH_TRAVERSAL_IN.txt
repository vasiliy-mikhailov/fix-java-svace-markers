FB.PATH_TRAVERSAL_IN (find-sec-bugs "Potential Path Traversal, file read") fires on the line where a path is *built or opened* from a value the taint pass could not prove constant: `new File(...)`, `new FileInputStream/FileReader/RandomAccessFile/ZipFile(...)`, `Paths.get`/`Path.of`, `Path.resolve(String)`, and the `Files.*` read entry points. It marks the sink, never a proven flow — a Spring `@Value` property, an HTTP `@RequestParam`, an authenticated username and a `String[] args` element are indistinguishable to it, so the marker by itself says nothing about whether attacker data arrives. Its sibling FB.PATH_TRAVERSAL_OUT covers the write sinks (`FileOutputStream`, `FileWriter`, `Files.write`); do not swap them, and note that one line can carry both, because `new File(dir, name)` is an IN sink even when the code goes on to write through it.

JDK MECHANICS, MEASURED IN THIS CHECKOUT — get these wrong and the test cannot fail for the right reason:
  * `new File(new File("/tmp/base/dir"), "../x").getAbsolutePath()` == `/tmp/base/dir/../x`. getPath/getAbsolutePath DO NOT NORMALIZE. A `startsWith(base)` assertion on them PASSES while the file is outside — a silent false GREEN. Only `getCanonicalPath()` (or `toPath().normalize()`) settles it; canonical is `/private/tmp/base/x`.

  * `Paths.get("/tmp/base/dir").resolve("/etc/passwd")` == `/etc/passwd`. `resolve` takes an absolute other WHOLESALE. So FileServer.java:75 (`destinationDir.toPath().resolve(getOriginalFilename())`) and FileServer.java:79 (`new File(destinationDir, getOriginalFilename())`) answer the same payload differently.
