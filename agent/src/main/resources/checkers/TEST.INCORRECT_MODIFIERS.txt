@(TestFactory|TestTemplate|ParameterizedTest|RepeatedTest|Test|BeforeEach|AfterEach|BeforeAll|AfterAll)\b
The checker asserts that a method carrying a test-framework annotation is declared with modifiers that let the framework's discovery actually select it. The marker's line is the ANNOTATION, so the modifiers to read are on the line below it. Most often it fires on default (package-private) access and is complaining about the absent `public` — the JUnit 3/4 rule. Do not confuse that with the modifiers that genuinely disable a Jupiter test: `private`, `static` and `abstract`, which look almost identical in a diff and are the only ones with a runtime consequence, along with a test class that has no accessible no-arg constructor.

UNDER JUPITER, `public`, `protected` AND DEFAULT ACCESS ARE INDISTINGUISHABLE — the engine reflects and calls `setAccessible`, including on a package-private method inherited from a superclass in another package. Adding `public` is green before and green after, and no test can separate the two states. Check which framework is actually on the classpath before resting on "not public, therefore never runs": that sentence is true of JUnit 4 and false of Jupiter, and a verdict resting on it is wrong for a right-sounding reason.

HOW YOU MAKE IT VISIBLE.
THE ONLY QUESTION WORTH ASKING IS "would the runner still select this method?", and you can ask the framework instead of running anything. Put `org.junit.platform:junit-platform-launcher` in test scope — build plugins inject it at runtime, so it is often absent from the test COMPILE classpath even where tests run fine — then build a discovery request selecting the class, open a launcher session, and call `discover()` rather than `execute()`, asserting that a descriptor for the method appears among the test plan's descendants. `discover()` walks the descriptor tree without invoking a single test body or lifecycle method, which makes it usable against classes that would otherwise need infrastructure the environment does not have.

That machinery separates the two halves of this family. A package-private annotated method is discovered and executes normally. Make the same method `private` or `static` and NOTHING is discovered while the build stays green: Jupiter emits only a WARNING-severity discovery issue saying the method must not be private and will not be executed. A silently vanishing test is the real defect here, and the discovery assertion is what turns it red — the count is short before the fix and correct after. To fail the build itself rather than an assertion, the configuration parameter `junit.platform.discovery.issue.severity.critical=WARNING` promotes that warning to a `DiscoveryIssueException`. Where the flagged modifier is merely non-public on Jupiter code the same machinery produces no red, and that discovery output is itself the evidence for saying so rather than manufacturing one.

WHAT GOES WRONG HERE.
Asserting the marker back at itself. Reflecting over `getModifiers()` and asserting `Modifier.isPublic` goes red before and green after while proving nothing — it restates the marker, and the framework's answer to the same question is "it runs either way".

Inferring the rule from the marker's presence. A tree will usually hold many unflagged annotated methods with exactly the modifiers the flagged one has, sometimes in the same package and source root, so "the checker flags non-public test methods" does not survive contact with the directory. Open the declaration and read the modifier that is actually there.

Attributing a "no tests ran" observation to this checker. Build plugins select test classes by class-name pattern, so a class whose name matches neither the include nor the exclude patterns is never run for a reason unrelated to modifiers. Changing a modifier will not fix that, and renaming to fix it would newly run a dormant suite.

Borrowing a by-design verdict from the reputation, name, package or directory of the code around the marker. That has no purchase on a test-tree modifier: these files are the harness that proves the code, not the code, and a method the runner silently skips is an ordinary defect. Intent is shown only by something checked in that DEPENDS on the modifier being what it is — a comment or suppression naming the choice, documentation telling a caller to declare it that way, a meta-annotation or engine configuration that selects on access. Absent that, the identical declaration is a defect. The converse error is just as easy: nothing nearby is disqualified from being deliberate either. Decide from the flagged line.
