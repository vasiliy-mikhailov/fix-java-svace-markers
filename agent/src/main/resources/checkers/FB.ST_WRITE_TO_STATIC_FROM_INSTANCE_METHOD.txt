The checker fires on an assignment whose target is a static (class-level) field, executed from a non-static context — an instance method, a constructor, or an instance initializer — so state owned by the class is published by code owned by one object. Three neighbours are routinely mistaken for it and are NOT this checker: READING a static field from an instance method; MUTATING the object a static field points at (`registry.put(...)` where the field itself is never assigned); and assigning the field from a `static { }` block or a static method, which is usually LI_LAZY_INIT_*.

HOW YOU MAKE IT VISIBLE.
The field is one slot per class; the writer is one per object. Nothing is observable while exactly one instance writes exactly once and every read happens after — the ordinary singleton case, and the reason this marker is usually latent rather than live. So the failing observation must be at a CONSUMER: some object's output changes because of a write it has no relationship to, or because of WHEN that write happened. Crucially the consumer must have CAPTURED something independently of the static. A consumer that re-reads the static on every call can demonstrate nothing, because "the global holds what was written last" is the design, not the defect. Output-versus-field is not the line that matters; captured-versus-re-read is.

ORDERING is the arrangement that works, and it is deterministic. Find a consumer that snapshots the static at construction or on first use. Clear the static, construct an early consumer, perform the flagged write with a distinguishable value, construct a late consumer, exercise both with identical input and assert both reflect the write. RED is the early one still answering from the pre-write state: same class, same configuration, different behaviour depending on when an instance method happened to run. GREEN by closing the capture-versus-publish gap — read at the point of use, or inject the dependency instead of reaching for the global. Be honest in the write-up when the fix lands at the reader rather than at the write.

CLOBBERING is the checker's literal claim — a second writer overwriting the first — and it is real only if a second writer can exist without changing configuration. Where one component performs the write and nothing else can, state that plainly; it is why the defect is latent. Beware the clobbering test that goes RED through a consumer which re-reads the global at use time: that is the assert-the-marker-back-at-itself trap wearing an output assertion, and the only fix that clears it, first-writer-wins, is worse than the defect. A cross-container variant is worth naming even when the test settles on ordering: a consumer created in one module can be governed by a static only another module ever writes, so it reads null or stale data forever. If that chain was established by reading rather than running, say so and confirm the RED before claiming it.

FOR THE FAMILY GENERALLY — a static counter, cache, flag or config slot assigned from an instance method: exercise instance A and record its answer, construct or exercise instance B, then re-run A's identical input and assert the original answer. RED is A answering differently because B existed. Or run one scenario twice in a single JVM and assert the second run matches the first. Both work only where something was captured or accumulated.

WHEN IT GENUINELY CANNOT BE SHOWN: the write happens once from a framework-created singleton, every read is strictly after it, every reader re-reads the static, and no consumer captures state. Then there is no observable difference. Say exactly that, name the single writer, and settle it as a design smell with no demonstrable defect rather than manufacturing a race.

WHAT GOES WRONG HERE.
Asserting the marker back at itself: write through one instance, write through a second, assert the static now holds the second value. That "fails" identically on a static holder working exactly as designed — it proves `static` means shared, not that anything is broken. The assertion must be on a consumer's output, never on the field.

Building the RED on the missing `volatile`. A writer-stores / reader-never-sees test is tempting, but Java memory model visibility failures are not reproducible on demand: a green run proves nothing and a red run may be coincidence. `volatile` stays a defensible remediation, just not a testable one.

The wrong fix: dropping `static`. The field is often static precisely because its readers are objects the container never wired — built by an extension registry, a service loader, a factory — and cannot be handed an injected reference, so removing `static` does not compile at those call sites and deletes the class's reason to exist. Where the field is a registry or cache the code deliberately shares, de-staticing changes semantics rather than fixing a defect. Fix the publication, keep the sharing.

Verdict words that do not follow: "written only once at start-up, therefore fine" is a claim about today's wiring, not about the construct — scope it that way, and note how close a configuration change is to a second writer. In the other direction, do not conclude intent from the surrounding code being unusual by design; but where cross-instance shared state may BE the mechanic the surrounding feature depends on, read that feature's own documentation before changing it.

Housekeeping: a test that clears or overwrites the static and does not restore it poisons every later test in the same JVM fork. Restore the previous value afterwards, or fork the test.
