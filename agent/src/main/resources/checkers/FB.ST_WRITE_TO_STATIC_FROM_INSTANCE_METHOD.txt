The checker fires on an assignment whose target is a static (class-level) field, executed from a non-static context — an instance method, a constructor, or an instance initializer — so state owned by the class is published by code owned by one object. On the flagged line that is `context = applicationContext;` (EnvironmentExposure.java:28) inside the `setApplicationContext` instance callback, writing the `private static ApplicationContext context` declared at line 20. Three neighbours are routinely mistaken for it and are NOT this checker: reading a static field from an instance method (line 23's `context.getEnvironment()` — a read, not a write); mutating the object a static field points at (`usersToTomPassword.put(...)`, ResetLinkAssignment.java:114, where the field is never assigned); and assigning the field from a `static { }` block (SecurityQuestionAssignment.java:27-28) or from a static method — that last one is usually LI_LAZY_INIT_*.

HOW YOU MAKE IT VISIBLE.
The field is one slot per class; the writer is one per object. Nothing is observable while exactly one instance writes exactly once and every read happens after — the ordinary singleton case, and the reason this marker is usually latent rather than live. So the failing observation must be at a CONSUMER: some object's output changes because of a write it has no relationship to, or because of when that write happened. Two arrangements work for the flagged shape; both are plain JUnit 5 plus spring-test, already on the classpath via spring-boot-starter-test (pom.xml:398).

(1) Clobbering — the checker's actual claim, and it cannot be repaired at the consumer. Two contexts alive in one JVM is not hypothetical here: StartWebGoat.java:20-33 boots a WebWolf child context and then a WebGoat child context in the same process. Today only the WebGoat scan (`org.owasp.webgoat.container`) creates this `@Component`, so only one write happens — state that plainly, it is why the defect is latent. Arrange the second writer explicitly: two `GenericApplicationContext`s (or two mocks whose `getEnvironment()` returns distinct `MockEnvironment`s, `org.springframework.mock.env.MockEnvironment`) carrying `webgoat.build.version=A` and `=B`. Call `new EnvironmentExposure().setApplicationContext(ctxA)`. Build the renderer that belongs to A the way production does — `var doc = Asciidoctor.Factory.create(); doc.javaExtensionRegistry().inlineMacro("webGoatVersion", WebGoatVersionMacro.class);` (the registration at AsciiDoctorTemplateResolver.java:67-73). Then `new EnvironmentExposure().setApplicationContext(ctxB)`. Then `doc.convert("webGoatVersion:x[]", Options.builder().build())` and assert the output contains "A". RED: it contains "B" — a renderer wired to one context emits a different context's configuration, and nobody touched the renderer. GREEN only by changing how the write publishes: reject or ignore a second context, key the lookup per context, or clear on `ContextClosedEvent`. Do not assert on `EnvironmentExposure.getEnv()` itself; assert on the rendered string.

(2) Ordering — cheaper and fully deterministic, but be honest that it can also be fixed at the reader rather than at the write. `UserInterceptor.java:18` snapshots the static at construction (`private Environment env = EnvironmentExposure.getEnv();`) and `postHandle` (lines 39-47) puts `oauth`=FALSE in the model whenever that snapshot is null. Null the static first (`ReflectionTestUtils.setField(EnvironmentExposure.class, "context", null)`), construct `early = new UserInterceptor()`, run the flagged write with a context whose environment holds `spring.security.oauth2.client.registration.github.client-id=real-id`, then construct `late = new UserInterceptor()`. Call `postHandle` on each with `MockHttpServletRequest`/`MockHttpServletResponse`, `new Object()` as handler and a fresh `ModelAndView` each (null authentication is handled, line 36). Assert both models contain `oauth`=TRUE. RED: `early` yields FALSE and `late` yields TRUE — same class, same context, a different login page depending on when an instance method ran.

For the family generally (a static counter, cache, flag or config slot assigned by an instance method): same recipe, easier. Exercise instance A and record its answer, construct or exercise instance B, then re-run A's identical input and assert the original answer — RED is A answering differently because B existed. Or run one scenario twice in a single JVM and assert the second run matches the first.

When it genuinely cannot be shown: if the write happens once from a framework-created singleton, every read is strictly after it, and no second writer can be constructed without changing configuration, then there is no observable difference. Say exactly that, name the single writer, and settle it as a design smell with no demonstrable defect. Do not manufacture a race to reach a RED.

WHAT NOT TO DO: the clobbering test through the Asciidoctor macros. It is tempting — install ctxA(version=A), create the renderer, install ctxB, convert `webGoatVersion:x[]`, assert "A" — and it does go RED with "B". It proves nothing. `WebGoatVersionMacro.process` (line 25), like WebWolfMacro:31 and WebGoatTmpDirMacro:25, calls `EnvironmentExposure.getEnv()` at CONVERT time; the Asciidoctor instance captures no context. I ran it: the same `doc` object prints A while A is installed and B after the B write. The assertion has no grounding, and the only fix that clears it — first-context-wins — would make a genuine second context render the first one's properties. That is the "assert the marker back at itself" trap in disguise; output-vs-field is not the line, captured-vs-re-read is.

FOR THE FAMILY GENERALLY (a static counter, cache, flag or config slot assigned from an instance method): exercise instance A and record its answer, construct or exercise instance B, then re-run A's identical input and assert the original answer — RED is A answering differently because B existed. Or run one scenario twice in a single JVM and assert the second run matches the first. Both work only where something was captured or accumulated; a pure re-read of the global cannot show the defect.

WHEN IT GENUINELY CANNOT BE SHOWN: if the write happens once from a framework-created singleton, every read is strictly after it, every reader re-reads the static, and no consumer captures state, then there is no observable difference. Say exactly that, name the single writer, and settle it as a design smell with no demonstrable defect. Do not manufacture a race, and do not build the RED on the missing `volatile` — JMM visibility failures are not reproducible on demand, so a green run proves nothing and a red run may be coincidence (`volatile` remains a defensible remediation, just not a testable one).

WHAT GOES WRONG HERE.
Asserting the marker back at itself: `new EnvironmentExposure().setApplicationContext(a); new EnvironmentExposure().setApplicationContext(b); assertSame(bEnv, EnvironmentExposure.getEnv())`. That "fails" identically on a static holder working exactly as designed — it proves `static` means shared, not that anything is broken. The assertion must be on a consumer's output (the rendered `webGoatVersion:x[]` string, the `oauth` model attribute), never on the field.

Building the RED on the missing `volatile`. The field is non-volatile and written after construction, so a "writer thread stores, reader thread never sees it" test is tempting; JMM visibility failures are not reproducible on demand, a green run proves nothing and a red run may be coincidence. `volatile` stays a defensible remediation — it is just not a testable one.

The wrong fix: dropping `static` from line 20. `getEnv()` is static precisely because the Asciidoctor macros in the same package (WebWolfMacro.java:31, WebGoatVersionMacro.java:25, WebGoatTmpDirMacro.java:25) are instantiated by Asciidoctor's extension registry and not by Spring — the class javadoc, lines 13-16, says so. Removing `static` does not compile at those call sites and deletes the class's reason to exist. Same across the family: when the static field is a registry or cache the code deliberately shares, de-staticing changes semantics rather than fixing a defect. Fix the publication, keep the sharing.

Verdict words that do not follow. "Written only once at start-up, therefore fine" is a claim about today's `scanBasePackages`, not about the construct — scope it, and note the two-child-context boot at StartWebGoat.java:20-33 is one configuration change away from a second writer. The reverse is worse: "WebGoat is deliberately vulnerable, so this is intentional." This is container infrastructure that renders lesson text; no assignment turns on it. But when this checker lands under `lessons/` — ResetLinkAssignment's static maps (lines 47-49), JWTVotesEndpoint's static counters (lines 57, 59) — cross-user shared state may BE the lesson mechanic, so read that lesson's `.adoc` before changing it. Under `src/test/**` and `container/**` a defect is just a defect.

Housekeeping trap in arrangement (2): nulling the static and not restoring it poisons every later test in the same fork, including any `@SpringBootTest` that renders a macro. Restore the previous value in `@AfterEach`, or fork the test.
