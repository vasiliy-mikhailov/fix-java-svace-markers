(?:\breturn\s+(?:this\.)?\w+\s*;)|@Getter|(?:\brecord\s+\w+\s*\()|(?:\b(?:private|protected)\s+(?:final\s+)?[A-Za-z_$][\w.$]*(?:<[^<>;]*>)?(?:\[\])?\s+\w+\s*[;=])
EI_EXPOSE_REP fires on a public accessor that hands back the object stored in a field — an explicit `return this.foo;`, a getter generated by Lombok `@Getter`, or a record component — when that field's type is mutable: an array, a collection, or any class SpotBugs cannot prove immutable. The complaint is aliasing, not secrecy: the caller receives the field itself rather than a copy and can change the owner's state without going through the owner. Its sibling EI_EXPOSE_REP2 is the opposite direction, a constructor or setter storing a caller-supplied mutable object *into* the field. REP is the way out, REP2 the way in; the same field frequently carries both, and a test that settles one does not settle the other.

HOW YOU MAKE IT VISIBLE.
Mutate through the reference the accessor returned, then observe the change on the owner through a SECOND read. The strongest form reads through an independent path — a different method that consults the same field, so a getter-only patch cannot fake the GREEN. Shape:

  var owner = new Thing(new ArrayList<>(List.of(element)));
  owner.getItems().clear();
  assertThat(owner.getItemCount()).isEqualTo(1);   // RED: it is 0

No container and no mocking is needed; this is a plain unit test.

SPLIT THE FAMILY BEFORE YOU WRITE ANYTHING. Where the field is initialised internally with a fresh mutable object (`new ArrayList<>()`, `new HashSet<>()`, `new boolean[n]`), the alias exists unconditionally and the RED needs no assumptions. Where the field is whatever a caller handed in, the test must first hand a mutable object in through the public constructor. That is legal and the RED is real, but say so in the finding when every production call site passes an immutable list — the exposure is latent, not currently exploited.

THE FIX/GREEN RULE, which decides whether your RED survives the patch. "Mutate, then read the owner" only turns GREEN if the copy handed out is itself mutable. Under `List.copyOf`, `Collections.unmodifiable*`, or a record compact constructor doing the same, the mutation throws UnsupportedOperationException and the test ERRORS rather than passing. Either fix with a mutable copy (`new ArrayList<>(this.items)`), or write the assertion to tolerate both fix styles: perform the mutation inside a `try` that swallows UnsupportedOperationException with a comment saying an unmodifiable copy is also a fix, then assert the owner's second read. Arrays are unaffected — `.clone()` returns a mutable copy.

SOME OF THESE MARKERS CANNOT BE MADE RED, and that is a settlement, not a failure to try. A field whose value is already an unmodifiable collection (built by `Stream.toList()`, `List.of`, `Collections.unmodifiable*`) hands out an alias no caller can use — the first mutation throws — while the checker sees only the declared type and a bare field read. An accessor that exists to publish a container-managed singleton has no copy to make, and copying would break the identity its callers depend on. A field holding a live external handle whose sharing is the whole point — an open connection, a session, a browser page — likewise. Refute those on the evidence you read, do not manufacture a test.

WHAT GOES WRONG HERE.
Reading the flagged line, finding nothing there, and calling it a false positive. Where the accessor is generated the reported line is the compiler's best guess and lands on a field declaration, a javadoc line, a record header, a constructor, an import, or a blank line; line numbers also drift as the file is edited. Find the field the checker means and ask which public method hands it out.

Asserting the fix instead of the defect. `assertThat(x.getFoo()).isNotSameAs(x.getFoo())` and `assertThrows(UnsupportedOperationException.class, () -> x.getFoo().add(...))` both go GREEN on the patch, but their RED reads "the objects were the same" or "no exception was thrown" — neither shows that anything was corrupted. Mutate, then read the owner.

Mutating the object you passed *into* the constructor. That demonstrates EI_EXPOSE_REP2; copy on the way out and the test still fails, so it never proves this marker. Mutate only what the accessor returned.

Constructing the owner with an immutable collection. `List.of(...)` makes the mutation throw, so the test fails before the fix and fails identically after it — a permanent spurious RED that looks like the genuinely-unprovable case arriving somewhere it does not belong. Use `new ArrayList<>(...)`.

If you do fix: accessors are often wire format. A defensive copy that serializes identically is safe; deleting the accessor is not. Lombok cannot carry a defensive copy, so the fix means dropping `@Getter` on that one field and hand-writing the accessor; for a record component it means a compact constructor.
