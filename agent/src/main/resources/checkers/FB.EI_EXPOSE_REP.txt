(?:\breturn\s+(?:this\.)?\w+\s*;)|@Getter|(?:\brecord\s+\w+\s*\()|(?:\b(?:private|protected)\s+(?:final\s+)?[A-Za-z_$][\w.$]*(?:<[^<>;]*>)?(?:\[\])?\s+\w+\s*[;=])
EI_EXPOSE_REP fires on a public accessor that hands back the object stored in a field — an explicit `return this.guesses;` / `return allHints;`, or a getter generated by Lombok `@Getter` or by a record component — when that field's type is mutable: an array, a collection, or any class SpotBugs cannot prove immutable (Spring Security's `User`, Playwright's `Page`/`Locator`). The complaint is aliasing, not secrecy: the caller receives the field itself rather than a copy, and can change the owner's state without going through the owner. Its sibling EI_EXPOSE_REP2 — roughly 80 markers in this same queue, on the same files and sometimes the identical line (ReportCardController.java:57 carries both) — is the opposite direction, a constructor or setter storing a caller-supplied mutable object *into* the field; REP is the way out, REP2 the way in, and a test that settles one does not settle the other.

HOW YOU MAKE IT VISIBLE.
The defect is observable and cheap in a plain JUnit test, with no Spring context: mutate through the reference the accessor returned, then observe the change on the owner through a *second* read. The strongest form has an independent read path.

Cleanest RED in this family — the quiz endpoints (CIAQuiz:58, JWTQuiz:53, SqlInjectionQuiz:70, CrossSiteScriptingQuiz:67), all `public boolean[] getResults() { return this.guesses; }` over a field the class initialises itself (`boolean[] guesses = new boolean[solutions.length];`):
  var q = new CIAQuiz();
  q.getResults()[0] = true;
  assertThat(q.getResults()[0]).isFalse();   // RED: it is true — the array handed out IS the field
GREEN with `return this.guesses.clone();`. These are `@RestController` singletons, so the array is process-wide state: one caller edits what the next GET serves.

Independent-read-path form — Course.java:48 `return this.lessons;`, while `getTotalOfLessons()` reads `this.lessons.size()`:
  var c = new Course(new ArrayList<>(List.of(new HttpBasics())));   // HttpBasics is a concrete Lesson
  c.getLessons().clear();
  assertThat(c.getTotalOfLessons()).isEqualTo(1);                   // RED: it is 0
Same shape for LessonResourceScanner:23 (`@Getter private final Set<String> lessons = new HashSet<>()`): construct it with `new PathMatchingResourcePatternResolver()` (real lessons are on the classpath) or a three-method stub resolver returning a `UrlResource("file:/x/lessons/sql/y.html")`, then `scanner.getLessons().clear()` and assert `applyPattern("/%s/x")` is still non-empty. And for WebGoatUser:32 / WebWolfUser:29, where the flagged line is a constructor and the real accessor is the Lombok `getUser()` over `@Transient private User user`: `u.getUser().eraseCredentials()` leaves `u.getUser().getPassword()` null while the entity's own `getPassword()` still returns the password — the same `User` the class delegates `isEnabled()`/`equals()`/`hashCode()` to.

Split the family before you write anything. Where the field is initialised internally with a fresh mutable object (`new HashSet<>()`, `new ArrayList<>()`, `new boolean[n]` — LessonResourceScanner:23, Lesson:16, LessonMenuItem:43, the four quizzes, `new Assignment(name)` which passes `new ArrayList<>()`), the alias exists unconditionally and the RED needs no assumptions. Where the field is whatever a caller handed in (Course:48, AttackResult:17/19, `Assignment(name, path, hints)`, the ReportCard record), the test must first hand a mutable object in through the public constructor; that is legal and the RED is real, but say so in the finding, because every in-repo call site passes `List.of(...)` or `.toList()`.

Some of these markers cannot be made RED, and that is the correct settlement, not a failure to try. HintService:39 `return allHints;` — the field is built by `Stream.toList()`, which is unmodifiable (verified on this JDK: `add` throws UnsupportedOperationException). The very first mutation throws, which proves the alias is harmless rather than present; SpotBugs sees only `List` and a bare field read. ReportCardController:57 is the same at its one construction site (line 48 `.toList()`). The two `@Bean public UserDetailsService userDetailsServiceBean() { return userDetailsService; }` (container/WebSecurityConfig, webwolf/WebSecurityConfig:75) return the Spring singleton the container is asking for — there is no copy to make, and making one breaks bean identity. The Playwright page objects (LessonPage:19 `private final Page page`, and the `Locator` fields) hand out a live browser handle whose sharing is the design; the field is final, and any demonstration needs a real browser under `-Pintegration-tests`, not a unit test. Refute these on the evidence, do not manufacture a test.

If you do fix: the accessors are wire format. AttackResult's getters are the JSON of every assignment response and `getResults()` is a `@ResponseBody` endpoint — `.clone()` and `List.copyOf(...)` serialize identically, deleting `@Getter` does not. Lombok cannot carry a defensive copy, so the fix means dropping `@Getter` on that one field (or `@Getter(AccessLevel.NONE)`) and hand-writing the accessor; for the record, a compact constructor with `List.copyOf`.

WHAT GOES WRONG HERE.
Reading the flagged line, finding nothing there, and calling it a false positive. container/WebSecurityConfig.java:77 is a blank line in this checkout — `return userDetailsService;` sat there before commit c596b729 and is now at line 86 (webwolf/WebSecurityConfig:75 is the same construct, undrifted). Where the accessor is generated the line is the compiler's guess, not the code: LessonResourceScanner:23, AttackResult:17/19, Lesson:16, Assignment:29 land on field declarations; LessonMenuItem:49 on a Javadoc `* @param children the children to set` (the real `return children;` is line 43); ReportCardController:57 on a record header; WebGoatUser:32 and WebWolfUser:29 on constructors; HttpBasicsLessonPage:15/16 on `import lombok.Getter;` and a blank line. Find the field the checker means and ask which public method hands it out.

Asserting the fix instead of the defect. `assertThat(x.getFoo()).isNotSameAs(x.getFoo())` and `assertThrows(UnsupportedOperationException.class, () -> x.getFoo().add(...))` both go GREEN on the patch, but their RED reads "the objects were the same" / "no exception was thrown" — neither shows anything was corrupted. Mutate, then read the owner.

Mutating the object you passed *into* the constructor. That demonstrates EI_EXPOSE_REP2; copy on the way out and the test still fails, so it never proves this marker. Mutate only what the accessor returned.

Copying the setup of the existing HintServiceTest (`new Course(List.of(lesson))`). `List.of` is immutable, so the mutation throws UnsupportedOperationException and looks like GREEN on unfixed code — the same trap that makes HintService:39 genuinely unprovable, arriving by accident somewhere it does not belong.
