@(?:All|Required)ArgsConstructor|@(?:Data|Setter|Builder)\b|@Value(?!\s*\()|\brecord\s+\w+\s*\(|this\.\w+\s*=\s*\w+\s*;
EI_EXPOSE_REP2 asserts that a constructor or setter stores a caller-supplied reference to a mutable object (array, collection, Date/Calendar, or any type SpotBugs does not know to be immutable) directly into a field, so the caller keeps a live handle on the object's internals. It is the INCOMING side; its neighbour EI_EXPOSE_REP is the OUTGOING side, where a getter returns the field itself — the same field usually carries both, and they are separate markers with separate fixes. In this repository the flagged line is very often a Lombok annotation rather than a statement: `@AllArgsConstructor` at HammerHead.java:15 and `@RequiredArgsConstructor` at DatabaseConfiguration.java:22 ARE the constructors, generated over the `private final` fields declared below them in declaration order.

HOW YOU MAKE IT VISIBLE.
THE CENTRAL FACT: you do not have to find an existing call site that mutates after handing the object over. There usually isn't one. EI_EXPOSE_REP2 is a property of the class's constructor contract, not of today's callers — so THE TEST IS THE HOSTILE CALLER. You construct the object yourself with a collection or array you keep a handle on, mutate your handle afterwards, and observe the object reporting the changed value. This is the same shape of mistake as concluding a test cannot vary the default charset: "no caller in the repo does this" is true and does not settle the marker, because the test is allowed to be the caller that does.

THE FAMILY SPLITS IN TWO, and which half a marker is in decides whether a RED is even possible.

(A) VALUE the object is supposed to own — array, collection, mutable entity captured as state. Demonstrable, cleanly, with a plain JUnit 5 + AssertJ test (spring-boot-starter-test is on the classpath; no context, no fork).

  src/main/java/org/owasp/webgoat/container/lessons/Assignment.java:49 — `this.hints = hints;` with class-level `@Getter`:
      List<String> hints = new ArrayList<>(List.of("hint 1"));
      Assignment a = new Assignment("test", "/HttpBasics/attack1", hints);
      hints.set(0, "MUTATED");
      assertThat(a.getHints()).containsExactly("hint 1");
  RED: the assert reports ["MUTATED"]. GREEN after `this.hints = List.copyOf(hints);` in the constructor. `hints` is `@Transient`, so the copy does not disturb Hibernate — on a MAPPED collection, replacing the injected instance with an immutable copy breaks dirty-checking and is the wrong fix.

  Array variant, src/main/java/org/owasp/webgoat/container/assignments/AttackResult.java:46,48 — `Object[] feedbackArgs` / `outputArgs`, read back via `@Getter`. Same shape; GREEN after `feedbackArgs == null ? null : feedbackArgs.clone()`.

  When the class has no getter for the field, observe through BEHAVIOUR instead — this is better anyway, because it pins the RED to the constructor rather than to the getter. src/main/java/org/owasp/webgoat/container/session/Course.java:19 stores the caller's `List<Lesson>`; assert on `getTotalOfLessons()` after clearing your own list, not on `getLessons()`.

(B) COLLABORATOR the object is supposed to talk to — a Spring bean, repository, DataSource, resolver, or singleton handed in by the container. BOTH FLAGGED LINES ARE THIS HALF, and for them the honest answer is that no test can make a defect visible.
  - DatabaseConfiguration.java:22 holds `DataSourceProperties properties` (line 26), a `@ConfigurationProperties` bean bound once at start-up and read in `dataSource()`. There is no copy to make: you would be inventing a clone of a framework bean, and a snapshot would silently drift from the bound configuration.
  - HammerHead.java:15 holds `Course course` (line 18), the singleton built by `CourseConfiguration.course()` (CourseConfiguration.java:97) AFTER all assignments are attached. `Course.setLessons` (Course.java:61) has no caller anywhere under src — grep it. Nothing outside mutates the injected object, and nothing in `HammerHead` promises a snapshot; holding the live reference IS the design.
  The settlement here is a refutation, and its reason must be the grep, not the vibe: name the field, state that the injected instance is a container-managed singleton with no second holder that mutates it, and that the class requires the live object rather than a snapshot. Do not write that refutation without running the search — the search is the entire content of the claim.

DISCRIMINATOR, when you are unsure which half you are in: try to write the defensive copy. If `new ArrayList<>(x)` / `x.clone()` / `new Date(x.getTime())` compiles and the program still behaves, it is (A). If the copy requires a copy constructor you would have to invent for a framework type, or would freeze something the code needs live, it is (B).

MECHANICS THAT BITE HERE:
  - Lombok: there is no constructor body in the source. Delombok mentally — `@AllArgsConstructor` at HammerHead:15 IS `HammerHead(Course course) { this.course = course; }`. If you fix a Lombok-generated constructor you must REPLACE the annotation with an explicit constructor; adding a copy elsewhere leaves the generated one intact and the marker standing.
  - Several flagged holders are private inner classes (`ShopEndpoint.CheckoutCodes` at ShopEndpoint.java:23-26 stores `List<CheckoutCode>`; `Servers.Server`) or have private constructors (AttackResult's 5-arg one). Construct them through the enclosing class's public path or with `setAccessible(true)`. What is NOT acceptable is proving the family on a reachable sibling class and attaching that GREEN to the marker's line.
  - Varargs setters such as `AttackResultBuilder.feedbackArgs(Object... args)` (AttackResultBuilder.java:22-25) are flagged even though every call site in the repo passes loose values, where javac synthesizes a fresh array and no alias exists. Passing an explicit `Object[]` is legal Java, so the RED is still writable — "it's varargs" is not a refutation.

WEBGOAT CAVEAT: this repository teaches no lesson about mutable exposure, so "WebGoat is deliberately vulnerable" is not a valid reason to refute an EI_EXPOSE_REP2 marker. But a copy inside a lesson class can still break the lesson for an unrelated reason — object identity the attack path depends on, a gadget chain in the deserialization lesson, or a JSON shape the front-end reads. Read the lesson's assignment before editing a class under `org.owasp.webgoat.lessons`; the container classes and the test tree carry no such risk.

WHAT GOES WRONG HERE.
- ASSERTING THE MARKER BACK AT ITSELF: `assertThat(a.getHints()).isSameAs(hints)` or `assertSame(args, r.getFeedbackArgs())`. That asserts the aliasing exists, which nobody disputes; it goes GREEN only by breaking `==`, which is not what the fix is for. The failing observation must be a VALUE the object reports wrongly after an outside mutation.
- MIXING UP THE TWO HALVES OF EI_EXPOSE: mutating through the object the GETTER returned proves EI_EXPOSE_REP, not REP2. On Assignment.hints, AttackResult.feedbackArgs and Course.lessons both defects sit on the same field, so a sloppy test passes for the wrong reason and stays RED after the constructor is correctly fixed — which then gets misread as "the fix didn't work".
- HANDING IN AN IMMUTABLE COLLECTION: `List.of(...)`, `Collections.emptyList()`, `Arrays.asList(...)`. The mutation throws UnsupportedOperationException and the test ERRORS instead of failing the assert; an error is not this marker's RED. Use `new ArrayList<>(...)`. Note that `CourseConfiguration.getHints()` (CourseConfiguration.java:168-173) really does pass `List.of(...)` and `Collections.emptyList()`, and `new Assignment(name)` passes a fresh `new ArrayList<>()` it drops immediately — every production call site is immune, which is exactly what tempts an agent into "unprovable". It is provable; the test supplies the aliasing call.
- SHALLOW COPY AGAINST A DEEP MUTATION: `new ArrayList<>(lessons)` still shares the `Lesson` objects, and `Lesson.addAssignment` (Lesson.java:18-20) mutates them in place. If your RED mutated an ELEMENT rather than the collection, the copy leaves it RED and you will conclude the fix is wrong. Match the mutation to the copy.
- WRITING THE HOSTILE-CALLER TEST FOR A HALF-(B) MARKER ANYWAY: hand `HammerHead` a `Course`, call `course.setLessons(...)`, assert `attack()` redirects elsewhere. It goes RED and a defensive copy makes it GREEN — and it proves nothing, because `setLessons` has no caller in the tree and nothing in `HammerHead` promises a snapshot. Green-by-construction on an invented requirement is not a proof; the settlement for those two lines is a refutation.
- "LOMBOK GENERATED IT, SO IT IS NOT OUR CODE." The generated constructor is part of the class's public API and is what every caller uses. Equally wrong: reading HammerHead:15 or DatabaseConfiguration:22, seeing an annotation rather than a statement, and reporting that the line holds no relevant construct.
- PATCHING THE GETTER to make a REP2 test go green — that fixes the other checker and leaves the flagged constructor untouched.
