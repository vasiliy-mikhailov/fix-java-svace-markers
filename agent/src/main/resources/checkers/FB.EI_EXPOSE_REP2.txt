@(?:All|Required)ArgsConstructor|@(?:Data|Setter|Builder)\b|@Value(?!\s*\()|\brecord\s+\w+\s*\(|this\.\w+\s*=\s*\w+\s*;
EI_EXPOSE_REP2 asserts that a constructor or setter stores a caller-supplied reference to a mutable object — array, collection, Date/Calendar, or any type SpotBugs does not know to be immutable — directly into a field, so the caller keeps a live handle on the object's internals. It is the INCOMING side; its neighbour EI_EXPOSE_REP is the OUTGOING side, where a getter returns the field itself. The same field usually carries both, and they are separate markers with separate fixes. The flagged line is often not a statement at all: a Lombok `@AllArgsConstructor` or `@RequiredArgsConstructor` IS the constructor, generated over the fields declared below it in declaration order, and a record header IS the canonical constructor. Check as well that the field's type is actually mutable — a holder whose fields are all String and primitives carries no REP2, and a line that merely matched the regex is not a marker.

HOW YOU MAKE IT VISIBLE.
THE CENTRAL FACT: you do not have to find an existing call site that mutates after handing the object over. There usually isn't one. EI_EXPOSE_REP2 is a property of the constructor's contract, not of today's callers — so THE TEST IS THE HOSTILE CALLER. Construct the object yourself with a collection or array you keep a handle on, mutate your handle afterwards, and observe the object reporting the changed value. "No caller in the repository does this" is true and does not settle the marker, because the test is allowed to be the caller that does.

  List<String> items = new ArrayList<>(List.of("a"));
  Thing t = new Thing(items);
  items.set(0, "MUTATED");
  assertThat(t.getItems()).containsExactly("a");   // RED: it reports ["MUTATED"]

Where the class has a method that consults the field and reports something derived from it, observe through THAT instead of through the getter. It pins the RED to the constructor; asserting through the getter lets a getter-side patch turn the test green and settles the constructor's marker with the wrong fix.

THE FAMILY SPLITS IN TWO, and which half a marker is in decides whether a RED is possible at all.
(A) VALUE the object is supposed to own — array, collection, mutable value captured as state. Demonstrable with a plain unit test, as above.
(B) COLLABORATOR the object is supposed to talk to — a container-managed bean, repository, DataSource, resolver or singleton handed in by the framework. There is no copy to make: you would be inventing a clone of a framework object, and a snapshot would silently drift from the live one. The settlement is a refutation whose reason must be a search, not a feeling: name the field, state that the injected instance is a singleton with no second holder that mutates it, and that the class requires the live object rather than a snapshot. The search is the entire content of that claim.

DISCRIMINATOR, when you are unsure which half you are in: try to write the defensive copy. If `new ArrayList<>(x)` / `x.clone()` / `new Date(x.getTime())` compiles and the program still behaves, it is (A). If the copy needs a copy constructor you would have to invent for a framework type, or would freeze something the code needs live, it is (B). Run it on every marker — the halves are not distinguishable by package or by file name.

MECHANICS THAT BITE HERE. There is no constructor body in the source when Lombok generated it, so fixing means REPLACING the annotation with an explicit constructor — a copy added elsewhere leaves the generated one intact and the marker standing. For a record the fix is a compact constructor (`public Thing { items = List.copyOf(items); }`), not a field assignment, which does not compile in a record. A private or inner holder may need reflection when the enclosing class's public path never accepts a caller-supplied object; a non-static inner class's constructor takes the enclosing instance first. What is NOT acceptable is proving the family on a reachable sibling class and attaching that GREEN to the marker's line. Varargs setters are flagged even where every call site passes loose values and javac synthesizes a fresh array — passing an explicit array is legal Java, so the RED is still writable and "it's varargs" is not a refutation. On a field mapped by an ORM, replacing the injected collection with an immutable copy breaks dirty-checking and is the wrong fix; a transient field carries no such constraint. And a defensive copy can break code that depends on object identity or on a shared live view — a serialization chain, a wire shape a client reads — so read what the class is for before copying.

WHAT GOES WRONG HERE.
Asserting the marker back at itself: `assertThat(t.getItems()).isSameAs(items)` asserts the aliasing exists, which nobody disputes, and goes GREEN only by breaking `==`, which is not what the fix is for. The failing observation must be a VALUE the object reports wrongly after an outside mutation.
Mixing up the two halves: mutating through the object the GETTER returned proves EI_EXPOSE_REP, not REP2. Where both defects sit on one field a sloppy test passes for the wrong reason and stays RED after the constructor is correctly fixed — which then gets misread as "the fix didn't work".
Handing in an immutable collection — `List.of(...)`, `Collections.emptyList()`, `Arrays.asList(...)`. The mutation throws UnsupportedOperationException and the test ERRORS instead of failing the assert; an error is not this marker's RED. Use `new ArrayList<>(...)`. That every production call site happens to pass an immutable list is exactly what tempts an agent into "unprovable"; the test supplies the aliasing call.
Shallow copy against a deep mutation: `new ArrayList<>(items)` still shares the elements, so if your RED mutated an ELEMENT rather than the collection the copy leaves it RED and you will conclude the fix is wrong. Match the mutation to the copy.
Writing the hostile-caller test for a half-(B) marker anyway. It goes RED and a defensive copy makes it GREEN, and it proves nothing, because nothing outside mutates the injected object and nothing in the holder promises a snapshot. Green-by-construction on an invented requirement is not a proof.
"Lombok generated it, so it is not our code." The generated constructor is part of the class's public API and is what every caller uses. Equally wrong: seeing an annotation rather than a statement on the flagged line and reporting that the line holds no relevant construct.
Patching the getter to make a REP2 test go green — that fixes the other checker and leaves the flagged constructor untouched.
