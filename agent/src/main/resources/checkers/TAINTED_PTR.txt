(?:prepareStatement|createStatement|execute(?:Query|Update)?|\w+(?:Query|Exec)\w*|new\s+File|Paths\.get|Path\.of|\.resolve)\s*\(
TAINTED_PTR reports a caller-controlled value — a request parameter, a header, an uploaded filename — reaching a sink that INTERPRETS it (a JDBC statement string, a filesystem path) with no validation in between. It is not the "unvalidated integer / index / allocation size" family: nothing here has to be numeric. The marker lands either on the sink call or on the call one frame above it that forwards the still-raw values into the method doing the concatenation, so read in both directions before concluding there is no sink.

`PreparedStatement` ON THE FLAGGED LINE IS NOT EVIDENCE AGAINST THE REPORT. One statement can mix a real placeholder for one column with raw concatenation for another — `"... where item_count = ? and owner_id = " + ownerValue`, with a `setInt(1, itemCount)` below it — and placeholders protect only the arguments actually bound. Some positions cannot be parameterised at all: an ORDER BY expression, a table name, an identifier. There the fix is a whitelist rather than a bind, and the absence of one is what the marker is about.

ESTABLISH WHICH ARGUMENT IS ACTUALLY TAINTED before aiming a demonstration at it. When several values reach the sink, the one nearest the marker is often the safe one: a parameter routed through `Integer.parseInt` and `setInt` cannot carry a payload, and a guard earlier in the method may reject anything but a fixed value in one parameter while the other passes through untouched. A test aimed at the wrong argument cannot fail for the right reason.

HOW YOU MAKE IT VISIBLE.
ASSERT THE EFFECT AT A BOUNDARY — the rows that come back, an authentication that should not have succeeded, a file created outside the intended directory, a process that started — never the query text and never the string that was passed. A real engine is the point: the defect is that the database or the filesystem PARSES what you sent, so a mocked DataSource or Connection proves nothing, and `verify(connection).prepareStatement(contains("or 1=1"))` proves less than nothing. A response that echoes the assembled query back at you is the same mistake in HTTP costume: it shows concatenation happened, which the marker already said, not that anything parsed it.

WHERE THE SINK RETURNS NOTHING RICH ENOUGH TO ASSERT ON, use an oracle. A caller-supplied expression that changes the ORDER of the returned rows can only have done so if the engine parsed it as syntax; an unknown identifier that produces an error carrying the whole statement verbatim is a second observable.

GET THE POLARITY RIGHT. A test that sends a payload and asserts the injection SUCCEEDS is green before any fix and stays green forever. Assert the safe property — only the requested row comes back, a wrong password does not authenticate, the resolved path stays inside the intended directory — so it fails on the current code and passes once the value is bound or validated.

WHAT GOES WRONG HERE.
Deciding from the reputation of the code instead of the flagged line. The name, package or directory the sink sits in is not evidence in EITHER direction: "the code around it is understood to be careless, so a defect is a defect" and "the code around it is understood to want this, so it is intended" are the same failure. Intent must be shown by something checked in that REQUIRES the interpretation to happen — documentation instructing a caller to send this payload to this path, a test asserting that the value is parsed as syntax. Where that exists, binding the parameter removes behaviour something else depends on and leaves the feature with no reachable success path; that breakage is the signal, not the class's package or its name. Absent it, the identical construct is an ordinary defect.

A build that dies for toolchain reasons — a release level the installed JDK does not support, a dependency missing from the compile classpath — is a toolchain problem and says nothing about whether the marker can be proved.
